## 1. 今回の位置づけ

### 活動全体の前提

| 項目 | 内容 |
|---|---|
| 当面の目標 | ヒアリングした本人の課題を解決する。まずは砂盃さん個人の業務改善を目指す |
| 今後の対象 | 石井さんをはじめ、他のメンバーにも順次ヒアリングする |
| 最終ゴール | AIで課題を解決するサービス案、またはツール案を矢野さんに提案し、承認を得る |
| 期限 | 現時点では2か月を想定。最長で半年まで延長可 |
| 解決策の範囲 | 新規開発のほか、既存AIツールの活用や運用の見直しも含む |
| 矢野さんの期待 | **生成AI以外のAIを使った解決方法を考えること** |
| 使える技術 | AzureのAIサービスはこのリポジトリの環境で使用可能。他のサービスは利用申請が必要だが、発案時点では利用できる前提で考えてよい |

### 今回のゴール

終了時に、次の3点を説明できる状態を目指します。

1. **課題の大きさ：** 砂盃さんの負担が大きい業務はどれか。頻度と時間はどのくらいか
2. **課題の中身：** どの工程で、なぜ困っているのか
3. **解決策の材料：** 生成AI以外のAIを検討できるデータが、どこにどの程度あるか

今回は解決策を決めたり、砂盃さんに提案したりしません。

## 7. 解決策の仮説（聞き手用）

矢野さんの期待を踏まえ、生成AI以外の候補を先に整理します。**すべて未検証の仮説です。当日は提案せず、必要なデータがあるかの確認だけに使います。**

| 課題の仮説 | 生成AI以外の候補 | 必要なデータ | 確認する質問 | 懸念点 |
|---|---|---|---|---|
| 作業時間の見積もりがずれ、計画が崩れる | 回帰モデルによる所要時間の予測 | 予定と実績の時間、作業の種類 | Q3、Q7 | 実績の記録がなければ、記録から始める必要がある |
| 毎日の時間配分を考える負担が大きい | 数理最適化による予定の割り当て | タスク、期限、所要時間、会議の予定 | Q3、Q7 | 所要時間の見積もりが前提になる |
| 遅れに気づくのが遅い | 進捗履歴を使った遅延リスクの予測 | 章立てごとの進捗、更新履歴 | Q4、Q11 | 毎月の周期なので、過去の件数が少ない可能性がある |
| 連絡の確認と作業の整理に時間がかかる | テキスト分類による要対応の仕分け | 過去のMattermostメッセージ、対応の結果 | Q11の補足 | 負担が小さければ優先度は低い。利用できる範囲の確認が必要 |
| 定例の宿題の確認に手間がかかる | 音声認識、話者識別、固有表現抽出による発言や担当者の抽出 | 定例の録画や音声、議事録 | Q10、Q11 | 宿題の抽出は生成AIのほうが扱いやすい可能性がある |
| 企画書の相談タイミングを判断しにくい | 過去の版とレビュー結果を使った分類 | 企画書の各版、レビュー結果 | Q5〜Q7 | 件数が少なく、機械学習には不向きな可能性が高い |
| 調査情報の収集と整理が重い | 文書のクラスタリング、類似文書の検索 | 調査資料、ニュース、競合情報 | Q13の補足 | 新規業界ごとに対象が変わる |

### 判断するときの注意

- **データ量を最優先で確認します。** 生成AI以外の機械学習では、過去データの量と質が成否を大きく左右します。個人の業務データだけでは足りない場合があります。
- **AIが不要な場合も選択肢に残します。** 例えば、企画書の相談基準はチェックリストやレビュー観点の明文化で解決する可能性があります。
- **生成AIの案も比較用に残します。** 矢野さんへの提案では、生成AI以外の案を優先しつつ、生成AIのほうが適している場合はその理由を説明できるようにします。
- **Azureの提供状況は、提案前に確認します。** 候補となるサービスの提供状況や料金は、この資料では確認していません。

## 8. 当日の注意

### 発言の扱い（事前に方針を決定）

砂盃さんの上長である矢野さんが提案先で、聞き手2人は砂盃さんの部下です。話しにくい内容が出る可能性があるため、次の扱いを提案します。

- [ ] 個人の発言をそのまま矢野さんへ共有しない
- [ ] 提案資料に使う内容は、砂盃さんに事前に確認してもらう
- [ ] 録音と文字起こしの閲覧者を、聞き手2人に限定する

### 立場の違いへの配慮

- **部下の話題：** 朝会の進捗確認や資料の催促は、聞き手自身に関わる場合があります。特定の人ではなく、作業の流れとして聞きます。
- **上長の話題：** 矢野さんや田渕さんのレビューは、人の評価ではなく、指摘の種類と手戻りの量を聞きます。
- **定例での指摘：** 「建設的ではない指摘」の話題は、発言者を特定せず、準備や手戻りへの影響だけを確認します。
- **個人の課題にしない：** 本人は「自分が改善すべきこと」と話しています。能力ではなく、判断の材料や仕組みに話を向けます。

### 避ける進め方

- AIでできるかどうかを、その場で答える
- 「AIで解決できそうですよね」と誘導する
- 「生成AI以外だと」と手法の話を持ち出す
- 録画や資料を見ればわかることを聞く

- [ ] 事実、本人の解釈、聞き手の解釈を分けて記録を整理する
- [ ] 聞けなかった◎の質問を洗い出す

### 候補の評価

課題ごとに次の表で評価し、次の検討対象を絞ります。

| 観点 | 確認すること | 課題A | 課題B | 課題C |
|---|---|---|---|---|
| 負担の大きさ | 月に何時間かかっているか | | | |
| 本人の解決意欲 | 「なくしたい」と明言したか | | | |
| データの有無 | 記録の量と質は十分か | | | |
| 生成AI以外への適合 | 予測、分類、最適化などとして定義できるか | | | |
| 解決手段 | 運用の見直し、既存ツール、新規開発のどれか | | | |
| 実現性 | 2か月で試作できるか。半年なら可能か | | | |
| 展開の可能性 | 他のメンバーにも使えるか | | | |

### 第3回に向けて

- 候補の課題を1〜2個に絞り、「この課題は、このデータで、こう解決できそう」という仮説を持っていきます。
- 共有いただける記録があれば、件数や形式を確認し、実現性を判断します。
