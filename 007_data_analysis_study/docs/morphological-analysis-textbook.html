第1章 形態素解析とは何か

形態素解析(けいたいそかいせき、morphological analysis)とは、文章を「意味を持つ最小の単位」である形態素に分割し、それぞれに品詞・読み・原形などの情報を付与する処理です。日本語の自然言語処理(NLP)のほぼすべての入口として使われてきた、最も基本的なテキスト解析技術です。

1.1 具体例 — 実際に分割してみると

例文「私は大学でコンピューターを勉強しています。」を、Pythonの形態素解析ライブラリJanomeで解析した実測結果が以下です。語の区切れ目と品詞が同時に得られます。

実行例 1-1: Janomeによる形態素解析(実測) 
文: 私は大学でコンピューターを勉強しています。

私        名詞      大学      名詞
は        助詞      で        助詞
コンピューター  名詞   を        助詞
勉強      名詞      し        動詞
て        助詞      い        動詞
ます      助動詞     。        記号
※ 計12形態素

ここで重要なのは、「勉強しています」が5つの形態素「勉強 / し / て / い / ます」に分解される点です。辞書にある「勉強」という語に、活用を持つ「する」(→し)、接続助詞「て」、補助動詞「いる」(→い)、助動詞「ます」がつながった文法的な構造として分解されています。これは単なる文字列分割ではなく、文法的な知識を使った分割です。

1.2 なぜ日本語では必須なのか

英語は I / have / a / pen のようにスペースで単語が区切られているため、split()すれば単語列が手に入ります。一方日本語は「今日は良い天気です」のように語の間に区切りがありません(分かち書きが存在しない)。機械にとって、どこからどこまでが1語なのかは自明ではありません。

さらに日本語は、次のような難しさを持ちます。

  • 表記が同じでも語が異なる: 「先」は名詞(優先の「先」)にも動詞の連用形(「先立つ」)にもなり得る。品詞は周辺文脈で決まる
  • 活用と複合語: 「食べさせられた」「非ステロイド性抗炎症薬」のように、文法的な連接と長い複合語が重なる
  • 新語・固有名詞: 「エージェント基盤」のような新語は辞書に登録されない限り未知語(前後の文脈からの推定)になる

この「どこで切るか」と「それぞれの品詞は何か」を決めるのが形態素解析の仕事であり、その判断は辞書と統計モデル(後述)を使って自動的に行われます。

1.3 最小構成で動かしてみる

初学者が最初に触るのに向いているのは、純Pythonで動くJanomeです(インストールが簡単で、ネイティブ依存がありません)。

# ターミナル
pip install janome

# parse.py
from janome.tokenizer import Tokenizer

t = Tokenizer()
text = "私は大学でコンピューターを勉強しています。"
for tok in t.tokenize(text):
    print(tok.surface, tok.part_of_speech.split(",")[0])
ポイント
この段階で暗記することは何もありません。「辞書を引いて、文法的につながりやすい切り方を選ぶ」という2段構えの処理だ、というイメージだけ持ってください。詳細は第2章で扱います。

第2章 形態素解析の仕組み

2.1 3つの工程

市販の形態素解析器(MeCab、Sudachi、Janomeなど)は、いずれも次の3工程で動きます。

  1. 辞書引き(ラティス生成): 文中の各位置から、辞書に登録された語をすべて列挙し、網目状(ラティス)の候補グラフを作る
  2. コスト計算: 各候補の語に「この語が出やすいか」(生起コスト)と、隣り合う語の「つながりやすさ」(連接コスト)を付ける
  3. 最適解の選択(ビタビアルゴリズム): 文全体のコスト合計が最小になる分割経路を動的計画法で探索する

例として実測の「東京都に住む」をJanome(IPA辞書)で解析すると 東京 / 都 / に / 住む と切れます。文字列上は「東京都」も辞書には存在しますが、「東京」+「都」の組み合わせの方が文全体として自然(コストが低い)と判定されている、というわけです。

実行例 2-1: 辞書とコストの影響(実測) 
文: 東京都に住む        →  東京 / 都 / に / 住む     (Janome・IPA辞書)
文: エージェント基盤でRAGを実装する
                        →  エージェント / 基盤 / で / RAG / を / 実装 / する
                            (辞書に登録がある語は1語として切れる)
実務の教訓
形態素解析の精度はアルゴリズムより辞書の質で決まります。「同じMeCabでも辞書が違えば結果が変わる」というのは実務で必ず遭遇する話です。

2.3 統計モデルの進化: HMMからCRFへ

「どの分割が自然か」をどう学ぶかは、時代とともに次のように進化しました。

手法種類考え方代表実装
ルールベース人手文法規則を人間が書く黎明期の解析器

第3章 AI・機械学習における変遷の歴史

本章がこの教材の核心です。形態素解析は「機械学習のタスクそのもの」として発展し、その後「機械学習パイプラインの前処理」として使われ、さらに「LLM時代には置き換えられる対象」へと位置づけが変わりました。全体像を先に示します。

  • 1980年代〜90年代前半
    ルールベースの解析。文法規則を人手で記述する。研究段階。日本語解析の黎明期。
  • 1990年代後半〜2000年代
    統計的HMMの時代。コーパスから遷移確率を学習する ChaSen(奈良先端大)、JUMAN(京都大学)が登場し、ルールベースを置き換え。
  • 2001〜2006年
    CRFの導入とMeCabの登場。工藤拓氏が開発。2006年3月に初版公開。HMMのChaSenより精度・速度とも向上し、以後デファクトスタンダードに。CRFパラメータ推定にはL-BFGSを使用。
  • 2013年頃
    分散表現(word2vec)の時代。Mikolovらが word2vec を発表。形態素解析の出力を単語ベクトル化して使う「形態素解析=機械学習の前処理」という形が標準化。テキスト分類・感情分析・検索の定番パイプラインになる。
  • 2016年
    BPEの登場。Sennrichらの論文で、機械翻訳の未知語対策として文字列の頻度ベース分割(Byte Pair Encoding)が提案される。後のLLMトークナイザの原型。
  • 2018年
    Transformer / BERTとSentencePiece。BERT(Devlinら)と SentencePiece(Kudo & Richardson)が登場。日本語BERT(東北大BERTなど)では「形態素解析で分かち書き → サブワード化」の二段構成がとられた。この時期はまだ形態素解析が入口。
  • 2019〜2023年
    LLMの時代。GPT-2/3、Llamaなどは日本語も含め文を形態素解析せず、BPE / SentencePieceだけで直接サブワード化。日本語LLMのトークナイザ設計の試行錯誤が続く(LLM-jp Tokenizer など)。
  • 2025年
    SB Intuitionsの日本語ModernBERT検証: 約4.4Tトークンで事前学習した日本語ModernBERTのトークナイザに、事後的に形態素解析器(MeCab / Juman++ / Sudachi)を差し込む実験を公開。性能への影響は小さいと報告されつつ、系列長は伸びる(例: 9トークン→13トークン)というコスト増も明らかに。
  • 2026年(現在)
    用途の分化が完了。LLMの内部ではサブワード分割が標準。一方で、検索エンジン(ElasticsearchのKuromoji / Sudachiアナライザ)、テキストマイニング、RAGのハイブリッド検索など、品詞や語単位が要る処理では形態素解析が現役で使われ続けている。

3.1 3つの時代のイメージ

時代形態素解析の位置づけ代表技術
〜2010年代前半タスクそのもの(品詞タグ付けという機械学習問題)HMM → CRF(MeCab)、コーパスと辞書
2013〜2018年頃機械学習の前処理(分散表現に入れる前の入り口)MeCab + word2vec / BERT(二段構成)
2018年〜現在LLMでは置き換え、実務の一部で現役継続BPE / SentencePiece(Unigram)と併存
初学者の理解の要(かなめ)
「形態素解析はもう古い。LLMはトークナイザで分割する」という言説をよく見かけます。しかし正確には、LLMのトークナイザが分割方式(SentencePiece等)を選んだだけで、形態素解析の技術(辞書+統計モデル)自体は検索・分析・辞書運用など別レイヤーとして今も現役です。ものを捨てる話ではなく「レイヤーの分化」だと捉えるのが実務では正解です。

第4章 サブワード分割 — LLM時代の分割技術

4.1 なぜサブワードなのか

単語単位の語彙を持つと、次の問題が起きます。

  • 語彙が爆発する(英語だけでも数十万語)
  • 未登録語(OOV、未知語)を表現できない
  • run / runs / running のような語形変化をすべて別語彙として持つのは非効率

そこで登場したのが、「頻度の高い文字列は1トークン、まれな文字列は細かく分解」するサブワード分割です。語彙サイズ(例: 32,000〜128,000)を事前に固定でき、どんな未知語も必ず既知のトークン列に分解できるため、LLMの標準方式になりました。

4.2 3つの代表アルゴリズム

手法分割の決め方主な採用例
BPE (Byte Pair Encoding)頻度の高い文字ペアを順にマージ(圧縮アルゴリズムに類似)GPT系、Llama、Mistral
WordPieceコーパスの尤度(確率)を最も上げるペアを結合BERT系(英語・多言語)
Unigram (SentencePiece)大きな候補語彙から不要な語を確率ベースで削る(逆方向)T5、Gemma、日本語ModernBERT、LLM-jp

なお、SentencePieceはソフトウェア名であり、アルゴリズム名ではありません(BPEモードもUnigramモードも選択できます)。またSentencePieceは分かち書き済みテキストを要求せず、生テキストから直接学習できるため、日本語・中国語のような言語にとくに有利です。

4.3 実際に学習して分割してみる(実測)

青空文庫の2作品(走れメロス・吾輩は猫である、計約33万文字)で、SentencePiece(Unigram、語彙4000)を実際に学習させた結果を示します。同じ文を形態素解析(Janome)と比較してみましょう。

実行例 4-1: 形態素解析 vs サブワード分割(実測) 
文: 私は大学でコンピューターを勉強しています。

【形態素解析 Janome】                12形態素
私 / は / 大学 / で / コンピューター / を / 勉強 / し / て / い / ます / 。

【サブワード分割 SentencePiece】     18トークン
▁ / 私は / 大 / 学 / で / コ / ン / ピ / ュ / ー / タ / ー / を / 勉 / 強 / して / います / 。

※ 「コンピューター」は学習コーパス(明治・大正の小説)に出現せず、
  1文字ずつの片仮名トークンに分解された。
※ 「私は」「して」「います」のように、頻度が高かった文字列は
  語の境界をまたいで1トークンになる。

形態素解析が「意味と文法の単位」で切るのに対し、サブワード分割は「コーパス中での頻度」だけで切ります。そのため上の例のように「私は」が1トークンになったり、見慣れない語がバラバラになったりします。これは欠陥ではなく設計であり、モデルはトークン埋め込みと文脈で意味を復元します。

実行例 4-2: 未知語の挙動(実測) 
文: エージェント基盤でRAGを実装する

【形態素解析】 エージェント / 基盤 / で / RAG / を / 実装 / する   (辞書に登録あり)
【サブワード】 ▁ / エ / ー / ジ / ェ / ン / ト / 基 / 盤 / で / R / A / G / を / 実装 / する
               (「エージェント」「RAG」は学習データに無く、文字(やアルファベット)単位まで分解)

4.4 形態素解析とサブワード分割の対比

観点形態素解析サブワード分割
原理辞書+文法(接続コスト)コーパスの統計(頻度・確率)のみ
分割単位意味を持つ最小単位(形態素)頻度で決まる任意の文字列
品詞・読み・原形得られる得られない
未知語辞書登録が必要(なければ推定)自動的に細かく分解して必ず表現
言語知識言語ごとの辞書が必要(日本語専用)言語非依存(同じ手順が全言語で動く)
速度辞書引き+最適化探索高速な文字列パターンマッチ

第5章 現在のAIモデルでの使われ方

5.1 LLMの標準トークナイザ

現在の主要LLM(GPT、Claude、Gemini、Llama、日本語LLMなど)は、文を形態素解析せずサブワード分割でトークン化します。英語・日本語とも同じ仕組みで、出力は「語彙IDの列」(例: 220 → 3012 → 7 → ...)になり、そのまま埋め込み層に入ります。トークナイザの設計(語彙サイズ・分割方式)は、コスト(トークン数=計算量と料金)と性能の両方に効くため、今でもモデル開発の重要トピックです(日本語LLMでは、日本語テキストを少ないトークン数で表現できるかが熱心に研究されています。例: LLM-jp Tokenizer)。

5.2 日本語特化モデル: 二段構成は今も残る

一方、日本語に特化したエンコーダ型モデル(BERT系)には、「形態素解析で分かち書き → サブワード化」の二段構成をとるものが今も多くあります。SB Intuitionsのブログ(2025年5月)による主要モデルの整理は次の通りです。

モデル形態素解析器辞書サブワード化
東北大bert-base-japaneseMeCabIPA辞書WordPiece
東北大bert-base-japanese-v3MeCabUniDic LiteWordPiece
LINE distilbert-base-japaneseMeCabUniDic LiteSentencePiece(BPE)
早稲田roberta-base-japaneseJuman++JumanDICSentencePiece(Unigram)
studio-ousia/luke-japaneseなし—SentencePiece(BPE)
sbintuitions/modernbert-ja-130mなし—SentencePiece(Unigram)

近年のモデルは「形態素解析なしのダイレクト分割」が主流になりましたが、HuggingFace transformersの BertJapaneseTokenizer はMeCab / Juman++ / Sudachi の3解析器に対応し、「形態素解析を挟みたいユースケース」を今でも公式にサポートしています。2025年に公開されたSB Intuitionsの日本語ModernBERTの検証では、学習済みモデルのトークナイザに事後的に形態素解析器を挟み込んでも下流タスクの性能低下は小さかった一方、系列長が伸びる(コスト増)ことも確認されています。

実務で覚えるべき1点
トークン系列が長いほど計算コストとAPI料金が増えます。日本語テキストの処理効率を論じる場面では、「トークナイザの分割方式」が直接効いてくることを意識してください。

5.3 形態素解析が今も必須の現場

LLM時代の2026年現在、次のような実務では形態素解析が欠かせません(ai-soukenの2026年7月整理に基づく)。

用途形態素解析の役割
検索エンジン(Elasticsearch / OpenSearch)Kuromoji / Sudachi アナライザが内部で形態素解析し、単語単位のインデックスを作る。型番・固有名詞の完全一致検索に強い
テキストマイニングアンケート・SNS・コールセンターログを形態素に分解し、単語頻度・共起・感情分析へ
RAGのハイブリッド検索ベクトル検索(意味)と形態素解析+BM25(キーワード)を統合。型番や固有名詞の取りこぼしを防ぐ

演習1: Janomeで形態素解析し、名詞だけ抽出する

目的: 形態素解析の基本出力と品詞フィルタを習得する。

from janome.tokenizer import Tokenizer
from collections import Counter

t = Tokenizer()
text = "今日は良い天気です。明日は雨が降るかもしれません。"

tokens = t.tokenize(text)
for tok in tokens:
    surface = tok.surface
    pos = tok.part_of_speech.split(",")
    print(f"{surface}\t{pos[0]}_{pos[1]}")

# 名詞だけ取り出して頻度集計
nouns = [tok.surface for tok in t.tokenize(text)
         if tok.part_of_speech.startswith("名詞")]
print("名詞:", Counter(nouns))

演習5(チャレンジ): 「形態素解析→サブワード化」の二段構成を体験する

目的: 日本語BERT系で使われた二段構成(第5章)の意味を理解する。

from janome.tokenizer import Tokenizer

# ① 形態素解析で分かち書き(単語ごとの列を作る)
t = Tokenizer()
text = "私は大学でコンピューターを勉強しています。"
words = [tok.surface for tok in t.tokenize(text)]
print("形態素列:", words)

# ② 各語をさらに細かく分割する(簡易サブワード化=先頭の2文字で切る)
def subword(w):
    return [w[:2], w[2:]] if len(w) > 2 else [w]

tokens = [sw for w in words for sw in subword(w)]
print("サブワード列:", tokens)

本物のBERTでは②にWordPieceやSentencePieceを使い、品詞タグ付け・固有表現抽出などのタスクで「語の境界を意識したトークン列」を利用します。二段構成の「系列長が伸びる」というコストとのトレードオフ(第5章)も、自分でトークン数を数えて確認してみましょう。

この章のゴール確認
4つのライブラリ(Janome / SudachiPy / SentencePiece / 標準ライブラリの組み合わせ)を一度動かせたら、あなたはもう「日本語テキストの前処理」を0から組める状態です。現場ではこの4つ+クリーニングで、かなりの分析タスクが始められます。

第7章 練習問題と解答

基礎問題

Q1. 形態素解析によって得られる情報を、具体例とともに3つ挙げなさい。

Q2. 英語にはスペース区切りがあるのに、日本語で形態素解析が(ほぼ)必須な理由を説明しなさい。

Q3. ChaSen(HMM)とMeCab(CRF)の違いを、機械学習の観点で1文で説明しなさい。

Q4. 形態素解析とサブワード分割の違いを、「辞書」「品詞」「未知語」「言語依存量」の4点で表にしなさい。

Q5. 近年のLLMが日本語を形態素解析せずサブワード分割する理由を2つ挙げなさい。

解答

A1. ① 分割(どこで語が区切れるか。例:「勉強しています」→「勉強/し/て/い/ます」)② 品詞(例:「は」は助詞)③ 読み・原形(例:「スモモ」の読み、辞書形の推定)。

A2. 日本語には分かち書き(語の間の空白)がなく、文字列だけでは「どこからどこまでが1語か」が機械に自明でないため。「東京都」が「東京+都」か1語かといった曖昧性も、文法的な接続の自然さで判定する必要がある。

A3. HMMは「単語列と品詞列が共起する確率」を最大化する生成モデル、CRFは「文が与えられたときの品詞列の条件付き確率」を文脈素性付きで直接学習する識別モデルであり、CRFの方が素性を柔軟に使えて精度が高い。

A4. 辞書: 必要(形態素解析)/不要・統計から構築(サブワード)。品詞: 得られる/得られない。未知語: 辞書登録が要る/自動で細かく分解。言語依存量: 高い(言語ごとに辞書)/低い(同一手順が全言語で動く)。

A5. ① 辞書・言語知識が不要で、言語非依存のパイプラインを全言語で共用できる(データ効率・運用コストの面で有利)② 頻度ベースで未知語を必ず表現でき、語彙サイズを固定して系列長と計算コストを制御できる。加えてトークナイザを事前学習の一部として設計・最適化できる。

応用問題

Q6. 社内文書検索で「エージェント基盤」という社内用語が正しく1語としてヒットしない。対処法を2つ提案しなさい。

Q7. アンケート20,000件の自由記述から名詞頻度を出したところ、「円」「様」「ご」のような不自然な語が上位に来た。原因と対策を述べなさい。

解答

A6. ① 形態素解析器のユーザ辞書(システム辞書)に「エージェント基盤」を登録し、分割を固定する ② 検索エンジンのアナライザも含め、新語に強いSudachi辞書へ切り替える(もしくはNEologd由来の辞書と比較する)。分析対象の検索が「完全一致のキーワード検索」であれば、ベクトル検索とのハイブリッド化も検討する。

A7. 原因: 敬語・依頼文(「〜してください」「ご検討のほど」)の語が名詞扱いされている、カタカナ語・助詞相当の残り、「様」(宛名)を含む住所データの混入など、データの性質と品詞フィルタの甘さ。対策: ①品詞フィルタを「名詞,一般/固有名詞」に絞る ②除外語リスト(ストップワード)で「円」「様」「ご」等を除く ③テキストの正規化(全角半角、記号、改行)とマークアップ除去を前処理に追加する。
