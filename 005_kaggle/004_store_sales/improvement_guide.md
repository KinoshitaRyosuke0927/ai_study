# 店舗売上時系列予測モデル 精度向上ガイド

機械学習初学者向けに、店舗売上の時系列予測モデルを構築・改善していく思考プロセス・手法・実践を時系列でまとめた学習教材です。

---

## はじめに：時系列回帰問題とは

このコンペティションでは、エクアドルのスーパーマーケットチェーン「Favorita」の  
**商品カテゴリ × 店舗 × 日付** ごとの売上を予測します。

| 観点 | 内容 |
|---|---|
| 問題の種類 | 回帰（Regression）：連続値の予測 |
| 目的変数 | sales（売上数量） |
| 評価指標 | RMSLE（Root Mean Squared Log Error） |
| 特徴 | 時系列データ・多変量・外部データあり |

### RMSLE とは

```
RMSLE = √( 1/n × Σ (log(1 + y_pred) - log(1 + y_true))² )
```

- 予測値と実際値の「対数スケールでの誤差」を測る指標
- 値が小さいほど精度が高い
- 大きな売上値の誤差と小さな売上値の誤差を**同じ重みで評価**する特性がある

> **実装上のポイント**  
> `log1p(sales)` を目的変数として学習すると、RMSE ≈ RMSLE が成立する。  
> 予測後に `expm1()` で元のスケールに戻すことで、一貫した評価が可能になる。

## 精度改善の基本的な考え方

| アプローチ | 内容 |
|---|---|
| **データ側の改善** | 特徴量の追加・加工・選択 |
| **モデル側の改善** | アルゴリズムの変更・ハイパーパラメータの最適化 |

> **重要な原則**
> - まずシンプルなモデルでベースラインを確立する
> - 変更は1つずつ行い、各変更の効果を測定する
> - 「複雑にすれば良い」とは限らない

## ステップ1: データの理解（EDA）

### 何をするか

予測に使えるデータが何種類あるかを調べ、それぞれの特徴を把握する。

### 利用可能なデータ

| ファイル | 内容 |
|---|---|
| train.csv | 学習データ（日付・店舗・商品カテゴリ・売上） |
| test.csv | テストデータ（学習データ最終日から15日間） |
| stores.csv | 店舗のメタ情報（都市・州・タイプ・クラスター） |
| oil.csv | 日別原油価格（エクアドルは産油国） |
| holidays_events.csv | 祝日・イベント情報 |
| transactions.csv | 店舗ごとの日別取引件数 |

### EDA で判明した重要な事実

```
1. 学習データは 2013年〜2017年8月15日（約5年間、300万行超）
2. テストデータは 2017年8月16〜31日（15日間）
3. 原油価格は週末・祝日が欠損（市場休場のため）→ 補間が必要
4. 取引件数は売上と高い相関を持つ → 重要な特徴量候補
5. 商品カテゴリ（family）の違いが売上に最も大きく影響
6. 給料日（15日・月末）に売上が増加する傾向あり
```

## ステップ2: 特徴量選択（feature_selection.py）

### 何をするか

予測に本当に役立つ特徴量を「データで証明」しながら絞り込む。

### 実施した手順

| ステップ | 内容 |
|---|---|
| ① 特徴量を全部作る | 日付・店舗・商品・原油・祝日・取引件数など24候補を一括作成 |
| ② 全特徴量でCV評価 | LightGBM + TimeSeriesSplit で全24特徴量のCV RMSE を計算 |
| ③ 重要度を計算 | Feature Importance で各特徴量の貢献度をランキング |
| ④ 段階的に除外 | 重要度の低い特徴量を20%ずつ除外してCV RMSEを比較 |
| ⑤ 最適セットを決定 | 最もCV RMSEが低い特徴量セットを採用 |

### TimeSeriesSplit とは

時系列データ専用のCV（交差検証）手法。

```
通常の k-fold:
  fold1: [検証][学習][学習][学習][学習]  ← 未来のデータで過去を予測 → 不正
  fold2: [学習][検証][学習][学習][学習]

TimeSeriesSplit:
  fold1: [学習] → [検証]
  fold2: [学習][学習] → [検証]
  fold3: [学習][学習][学習] → [検証]
  → 常に「過去で未来を予測」する正しい評価
```

> **なぜ通常の k-fold を使ってはいけないか**  
> 時系列データを shuffle すると「未来のデータで過去を学習」することになり、  
> 実際のテスト環境（未来の予測）とは全く異なる条件で評価されてしまう。

### 特徴量選択の結果

| 除外率 | 残特徴量数 | CV RMSE |
|---|---|---|
| 0%（全部） | 24 | 0.6308 |
| 20% | 19 | 0.6313 |
| 40% | 14 | 0.6306 |
| 60% | 9 | 0.6362 |
| **80%** | **4** | **0.6185** ← 最良 |

**採用特徴量（4つ）**: `family_enc`, `store_nbr`, `onpromotion`, `transactions_lag7`

> **重要な発見**  
> 特徴量を減らした方がCV RMSEが下がった。  
> これは「多くの特徴量 → 過学習」のリスクを示している。  
> ただし、最終モデルでは汎化性能を考慮して22の特徴量を採用した。

## ステップ3: ベースラインモデルの構築（store_sales_1st.py）

### 何をするか

EDAと特徴量選択の結果をもとに、安定した基準となるモデルを構築する。

### 採用した特徴量（22個）

```python
NUM_FEATURES = [
    "family_enc", "onpromotion", "has_promo",        # 商品（最重要）
    "store_nbr", "type_enc", "cluster", "city_enc", "state_enc",  # 店舗
    "year", "month", "day", "dayofweek", "dayofyear",
    "weekofyear", "is_weekend", "is_month_start", "is_salary_day",  # 日付
    "oil_price", "oil_change_7d",                    # 原油価格
    "is_national_holiday", "holiday_type_enc",       # 祝日
    "transactions_lag15",                            # 取引件数
]
```

### 取引件数に lag15 を使う理由

```
テストデータは「学習データ最終日の翌日から15日間」
  → テスト1日目: 1日前の取引件数を参照できる（lag1）
  → テスト15日目: 15日前の取引件数を参照できる（lag15）

lag7 を使うと:
  テスト8日目以降は「参照先がテスト期間内」になりリークが発生
  → テストデータ作成時点では未来の取引件数は不明のためエラー
```

**lag15 を使えば、テスト全15日間でリークなく使用できる。**

### LightGBM を使う理由

| モデル | 特徴 |
|---|---|
| RandomForest | 複数の木を独立して学習し、多数決で予測 |
| **LightGBM** | 前の木の「失敗」を次の木が補正しながら学習（勾配ブースティング） |

LightGBMは大規模データに強く、時系列の複雑なパターンを捉えるのに適している。

### ハイパーパラメータの最適化

`RandomizedSearchCV` で探索、`TimeSeriesSplit` で正しい時系列CV評価を実施。

```python
# 全組み合わせを試す GridSearch と異なり、
# 確率分布からランダムにサンプリングして効率的に探索する
param_dist = {
    "n_estimators":      randint(200, 1000),
    "learning_rate":     uniform(0.01, 0.19),
    ...
}
gs = RandomizedSearchCV(..., n_iter=50, cv=tscv)
```

**探索に時間がかかる理由**: 50回の試行 × 5 foldのCV × 大規模データ（300万行）

> **TUNE フラグの設計**  
> `TUNE = True` で新規探索、`TUNE = False` で探索済みパラメータを即使用。  
> 一度良いパラメータが見つかったら `BEST_PARAMS` に保存し、再利用できる設計にした。

## ステップ4: ラグ特徴量の追加（store_sales.py）

### 何をするか

時系列データの強みを活かす「ラグ特徴量」と「ローリング統計量」を追加する。

### ラグ特徴量とは

```
ラグ特徴量: N日前の売上をそのまま特徴量として使う
  sales_lag_16 = 16日前の売上
  sales_lag_28 = 4週間前（同じ曜日の売上に近い）
  sales_lag_365 = 昨年同日の売上（年次季節性の把握）
```

### なぜ lag >= 16 にするか

```
テストデータは15日間（8/16〜8/31）
  lag_16 を使うと:
    テスト1日目(8/16): 8/1の売上を参照 ← 学習データ内 ✓
    テスト15日目(8/31): 8/15の売上を参照 ← 学習データ内 ✓

  lag_15 を使うと:
    テスト2日目(8/17): 8/2の売上を参照 ← 学習データ内 ✓
    テスト15日目(8/31): 8/16の売上を参照 ← テストデータ = データリーク ✗
```

**lag >= 16 であれば、テスト全期間でデータリークなく使用できる。**

### ローリング統計量とは

```
ローリング統計量: 直近N日間の統計値（平均・標準偏差）
  sales_roll7_mean  = 直近7日間の平均売上
  sales_roll28_std  = 直近28日間の標準偏差（売上の変動幅）
```

リークを防ぐため、shift(16) してから rolling を計算する：
```python
sales_shifted = grp.shift(16)              # 16日前にシフト
df["sales_roll7_mean"] = sales_shifted.rolling(7).mean()
# → 最低でも16日前以降のデータのみ参照
```

### ラグ特徴量計算の重要な実装上のポイント

```python
# NG: train と test を別々にシフトすると、
#     test の先頭行が参照したい過去データ（train末尾）に届かない
test["sales_lag_16"] = test["sales"].shift(16)  # NaN になる

# OK: train + test を結合してからシフトする
combined = pd.concat([train, test.assign(sales=np.nan)])
combined["sales_lag_16"] = combined.groupby(["store_nbr","family"])["sales"].shift(16)
# → test の先頭行が train 末尾のデータを参照できる
```

## ステップ5: 問題発生 — 精度の大幅悪化

### 何が起きたか

ラグ特徴量を追加したモデルが、ベースラインより**圧倒的に精度が悪い**状態になった。  
学習データでの精度は上がっているにもかかわらず、テストデータでは悪化 → **過学習**が疑われた。

### 調査1: ラグ特徴量のNaN率確認

まず「データの質」を調べるため、各ラグ特徴量のNaN率を出力した。

```
=======================================================
ラグ特徴量 NaN率（train）
=======================================================
  sales_lag_16       :   1.0%  (  28,512 行)
  sales_lag_21       :   1.2%  (  37,422 行)
  sales_lag_28       :   1.7%  (  49,896 行)
  sales_lag_365      :  21.7%  ( 650,430 行)  ← 問題
  sales_roll7_mean   :   0.6%  (  17,826 行)
  sales_roll28_mean  :   0.0%  (      16 行)
  sales_roll7_std    :   0.7%  (  21,389 行)
  sales_roll28_std   :   0.0%  (      17 行)

年別 sales_lag_365 NaN率:
  2013年: 100.0%  ( 648,648 行)  ← 2012年のデータが存在しないため
  2014年:   0.3%  ( 648,648 行)
  2015年:   0.0%  ( 648,648 行)
  2016年:   0.0%  ( 650,430 行)
  2017年:   0.0%  ( 404,514 行)
```

**判明した原因**: `sales_lag_365`（1年前の売上）は参照先の2012年データが存在しないため、  
2013年分648,648行（全体の21.7%）が全てNaN。これを中央値で補完した結果、  
「意味のない値」が大量のデータに注入されてモデルの学習を妨げていた。

> **NaN補完の問題点**  
> ラグ特徴量のNaNは「過去データが存在しない」ことを意味する。  
> これを全体の中央値で補完することは、「過去の売上は中央値です」という  
> 誤情報をモデルに与えることになる。

## ステップ6: 精度悪化への対処

### 対処A: 学習データを2016年以降に絞り込む

`sales_lag_365` のNaNが問題なら、1年前（2015年）のデータが存在する期間のみ使えばよい。

```python
train_feat = combined[
    (combined["sales"].notna()) & (combined["date"] >= "2016-01-01")
].copy()
```

| 絞り込み | データ量 | lag_365 NaN率 |
|---|---|---|
| 全期間 | 3,000,888行 | 21.7% |
| 2016年以降 | 1,054,944行 | 0% |
| **2014年以降** | 約2,000,000行 | **0.3%** |

→ 2016年以降に絞り込んでも精度は改善しなかった。  
→ データ量が1/3に減ったことで**過学習が逆に悪化**した可能性がある。

### 対処B: モデルの複雑さを下げる（正則化強化）

```python
param_dist = {
    "max_depth":         randint(3, 7),       # 上限10→7: 深い木を制限
    "num_leaves":        randint(15, 63),      # 上限127→63: 葉の数を制限
    "reg_alpha":         uniform(0.1, 1.9),   # 下限0→0.1: L1正則化を強化
    "reg_lambda":        uniform(1.0, 3.0),   # 範囲を上方シフト: L2正則化を強化
    "min_child_samples": randint(30, 100),    # 下限10→30: 最小サンプル数を増加
}
```

**正則化とは**: モデルが複雑になりすぎることにペナルティを与えて過学習を抑制する仕組み。

### 対処C: sales_lag_365 を除外する

NaNが多く問題を起こしていた `sales_lag_365` を特徴量から除外した。

### 対処D: 学習データを2014年以降に変更

2016年以降への絞り込みがデータ量を減らしすぎた可能性を考慮し、2014年以降に緩和。

```python
train_feat = combined[
    (combined["sales"].notna()) & (combined["date"] >= "2014-01-01")
].copy()
```

### 結果：いずれの対処でも精度は改善しなかった

## ステップ7: 根本原因の分析

複数の対処を試みたが精度が改善しなかった。改めて根本原因を分析した。

### 根本原因1: ラグ特徴量がモデルを「局所的」にした

**ベースラインモデルの特徴量**（曜日・月・店舗タイプなど）は  
時系列全体を通じて使える**汎用的なパターン**を学習する。

```
例: dayofweek=5（土曜）→ 売上が高い  ← 年間を通じて安定
    month=12（12月）→ 売上が高い    ← 毎年繰り返す
```

**ラグ特徴量**は「直前の売上」に依存するため、モデルが**局所的なパターン**に過度に依存する。

```
例: sales_lag_16 = 8/1の売上 → 8/17の売上に使う
    8/1が特殊な日（プロモーション等）だった場合、誤った情報を引き継ぐ
```

### 根本原因2: CVスコアと実テストのズレ

```
TimeSeriesSplit の CV:
  検証期間 = 学習データの「中間期間」（2014〜2016年など）
  ラグ特徴量が豊富に使えてCV RMSEが低く見える

実際のテスト:
  テスト期間 = データの「最末端」（2017年8月16〜31日）
  直前の2週間のパターンがそのまま未来に影響する
  → その期間に異常な動きがあると予測が大きく外れる
```

**CVスコアが良くても実テストが悪い** ＝ CVが実テスト環境を正しく模擬できていない。

### 根本原因3: 学習データの削減

| 要因 | 影響 |
|---|---|
| ラグ特徴量のNaN対策で2016年以降に絞り込み | 学習データが1/3に激減 |
| データ量の減少 | モデルが学べるパターンが狭まる |
| 少ないデータ × 複雑な特徴量 | 過学習が加速する |

### 教訓のまとめ

| 失敗 | 原因 | 学べること |
|---|---|---|
| ラグ特徴量を追加したら精度が悪化した | 学習データのNaN（lag_365の21.7%）+ 過学習 | 特徴量追加前に品質確認（NaN率など）が必須 |
| データを絞り込んだら過学習が悪化した | 学習データの削減 | NaN対策とデータ量のトレードオフを意識する |
| 複数の対処をしても改善しなかった | CVと実テストのズレが根本原因 | CVスコアの改善だけでは不十分。Kaggleへの提出で確認することが重要 |
| 「より複雑にすれば良くなる」は誤り | 特徴量は汎化性能が高いものを選ぶ必要がある | シンプルで汎用的な特徴量 > 複雑で局所的な特徴量 |

## ステップ8: 比較と評価（calc_score.py）

### 何をするか

ベースラインモデル（`submission_1st.csv`）を「正解」として、  
改善モデル（`submission.csv`）の精度を RMSLE で定量的に評価する。

```python
rmsle = np.sqrt(np.mean((np.log1p(y_pred) - np.log1p(y_true)) ** 2))
```

### この計測が有効な理由

Kaggleに実際に提出しなくても、  
**ベースライン比でどれだけ改善・悪化したかを即座に確認できる**。  
試行錯誤のサイクルを短縮し、効率的に改善方向を探ることができる。

```
  → lag16/21/28/365 + ローリング統計量 × 8特徴量を追加
    ↓
【問題発生】精度の大幅悪化
    ↓
ステップ5: 原因調査
  → NaN率確認: sales_lag_365 が 2013年100%・全体21.7% NaN
    ↓

  → 正則化強化

    ↓

    ↓
ステップ7: 根本原因の分析
  → ラグ特徴量による「局所依存」の強まり
  → CV検証環境と実テスト環境のズレ

```

### 各ステップで使った手法と目的

| ステップ | 主な手法 | 目的 |
|---|---|---|
| EDA | カテゴリ別集計・相関分析・Feature Importance | データの特性とパターンを把握する |
| 特徴量選択 | LightGBM + TimeSeriesSplit + 段階的除外 | 本当に有効な特徴量をデータで証明する |
| ベースライン | LightGBM + RandomizedSearchCV + TimeSeriesSplit | 比較基準を確立する |
| ラグ特徴量 | shift() + groupby() + rolling() | 時系列固有のパターンをモデルに与える |
| 原因調査 | NaN率集計・年別分析 | 精度悪化の根拠を数値で確認する |
| 評価 | RMSLE（Kaggle公式指標） | ベースラインとの差を定量比較する |

## 時系列問題に特有の注意点（まとめ）

```
1. CVには必ず TimeSeriesSplit を使う
   → 通常の k-fold は「未来で過去を学習」するため時系列では不正

2. ラグ特徴量はリーク防止に注意する
   → テスト期間N日間をカバーするには lag > N が必要

3. train+test を結合してからラグを計算する
   → test 単独で shift() しても過去データが参照できない

4. NaN率を必ず確認する
   → 補完は「意味のある値」でなければモデルに悪影響を与える

5. 特徴量追加がCV RMSEを改善しても、実テストが改善するとは限らない
   → CVと実テストのズレ（過学習・分布シフト）が潜んでいる可能性がある

6. 「複雑にすれば良い」は誤り
   → 汎用的でシンプルな特徴量の方が、時系列の実テストでは安定することがある
```

## 機械学習改善の一般的な進め方（まとめ）

精度改善は以下のサイクルを繰り返すことで行う。

```
①  ベースラインを作る（シンプルなモデル・少ない特徴量から始める）
    ↓
②  仮説を立てる（「この特徴量を追加すれば良くなるはず」など）
    ↓
③  実装して CV スコアを測定する
    ↓
④  改善した → 採用、改善しなかった → 廃棄
    ↓
⑤  Kaggle に提出して実際のスコアを確認する
    ↓
⑥  CVスコアと提出スコアに大きな差がある → データリーク・過学習を疑う
    ↓
⑦  ①に戻る
```

> **最も大切なこと**  
> 「なぜその手法を使うのか」「何の問題を解決しようとしているのか」を  
> 常に意識しながら改善を進めること。  
> 手法を目的にするのではなく、**「精度を上げるための手段」として使うことが重要**。
