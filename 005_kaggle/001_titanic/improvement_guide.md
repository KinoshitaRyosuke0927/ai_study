# タイタニック生存予測モデル 精度向上ガイド

機械学習初学者向けに、モデルの精度を向上させるための考え方・手法・実践プロセスを時系列でまとめた学習教材です。

---

## はじめに：機械学習の精度改善の基本的な考え方

精度改善には大きく2つのアプローチがあります。

| アプローチ | 内容 | 本資料での対応 |
|---|---|---|
| **データ側の改善** | 特徴量の追加・加工・選択 | ステップ2〜5 |
| **モデル側の改善** | アルゴリズムの変更・ハイパーパラメータの最適化 | ステップ3、6 |

> **重要な原則**
> - まずシンプルなモデルを作り、ベースラインを確立する
> - 変更は1つずつ行い、各変更の効果を測定する
> - 「複雑にすれば良くなる」とは限らない。少ないデータでは特にシンプルさが重要

## ステップ1: ベースラインモデルの作成

### 何をしたか

最小限の特徴量と RandomForest でシンプルなモデルを作成した。

```python
features = ["Pclass", "Sex", "SibSp", "Parch"]
model = RandomForestClassifier(n_estimators=100, max_depth=5, random_state=1)
model.fit(X, y)
```

### なぜこの4特徴量か

データを見たときに「これは生存と関係があるはず」と直感的にわかる列を選んだ。

| 特徴量 | 生存との関係 |
|---|---|
| `Pclass` | 等級が高い（1等）ほど救助が優先された |
| `Sex` | 「女性・子供優先」の原則があった |
| `SibSp` | 兄弟姉妹・配偶者の数（家族で助け合い） |
| `Parch` | 親・子供の数（家族で助け合い） |

### ベースラインを作る重要性

> これ以降のすべての改善は「ベースラインと比べて良くなっているか」を基準に判断します。  
> ベースラインがないと、改善の効果を測定できません。

---

## ステップ2: 特徴量エンジニアリングと欠損値処理

### 何をしたか

データに含まれる他の列を活用し、新しい特徴量を追加した。また、欠損値（空白のデータ）に対処した。

### 欠損値処理とは

機械学習モデルは欠損値（NaN）をそのまま扱えないため、何らかの値で補完する必要がある。

| 列 | 欠損率 | 補完方法 | 理由 |
|---|---|---|---|
| `Age` | 約20% | Title別の中央値 | 年齢は敬称（Mr/Mrs等）と相関が高い |
| `Fare` | 1件 | 全体の中央値 | 欠損が少ないので単純補完で十分 |
| `Embarked` | 2件 | 最頻値 | 欠損が少ないので最も多い値で代替 |

### 追加した特徴量

| 特徴量 | 作り方 | 直感的な意味 |
|---|---|---|
| `Title` | Nameから敬称を抽出（Mr/Mrs/Miss/Master等） | 社会的地位・年齢層を反映 |
| `HasCabin` | Cabin欠損有無を0/1に変換 | 欠損≒3等客室と相関 |
| `FamilySize` | `SibSp + Parch + 1` | 家族の総人数 |
| `IsAlone` | FamilySize==1 を0/1に変換 | 一人旅かどうか |

### 特徴量エンジニアリングの考え方

```
「このデータの背景にある現実」を考える

例: Name列に「Mr. Smith」という形式で敬称が含まれている
  → 敬称は年齢・性別・社会的地位を反映している
  → これを Title として抽出すれば有用な情報になる
```

## ステップ3: より高性能なモデルへの切り替え

### 何をしたか

RandomForest から **XGBoost・LightGBM** に切り替え、**GridSearchCV** でハイパーパラメータを最適化した。

### ハイパーパラメータとは

モデルの「設定値」のこと。たとえば RandomForest の `max_depth=5` がこれにあたる。  
適切な値はデータによって異なるため、試行錯誤で探す必要がある。

### XGBoost・LightGBM とは

どちらも**勾配ブースティング**という手法で、決定木を直列に積み重ねてエラーを修正し続けるモデル。

```
学習データ → [木1] → 誤差 → [木2（誤差を修正）] → 誤差 → [木3] → ... → 最終予測
```

RandomForest は複数の木を「独立して」学習するのに対し、XGBoost・LightGBM は前の木の「失敗」を次の木が補正していく点が異なる。

### GridSearchCV とは

指定したパラメータの**全組み合わせ**を試して、最も精度が高い組み合わせを見つける手法。

```
n_estimators: [100, 200]  × 2通り
max_depth:    [3, 4, 5]   × 3通り
learning_rate:[0.05, 0.1] × 2通り
─────────────────────────────────
合計: 12通りを全て試す → 最良の組み合わせを採用
```

### cross_val_score（交差検証）とは

データを k 個に分割し、1つを検証用・残りを学習用として k 回評価する手法。  
「たまたま都合の良いデータ分割で精度が高く出た」という偶然を排除できる。

```
データ全体 [1][2][3][4][5]

1回目: [検証][学習][学習][学習][学習]
2回目: [学習][検証][学習][学習][学習]
...（5回繰り返す）

→ 5回の平均精度を「真の精度の推定値」とする
```

## ステップ4: 問題発生 — 複雑にしたのに精度が下がった

### 何が起きたか

特徴量を増やし、より高性能なモデルに切り替えたにもかかわらず、Kaggle へ提出したスコアが**最初のシンプルなモデルより低くなった**。

### 原因の分析

#### 原因1: 過学習（Overfitting）

> **過学習とは**  
> モデルが学習データを「覚えすぎて」しまい、未知のデータに対応できなくなる現象。

```
理想的なモデル: 「データの本質的なパターン」を学習する
過学習したモデル: 「学習データ特有のノイズ」まで覚えてしまう

→ 学習データでは高精度、テストデータでは低精度
```

タイタニックのデータは891件しかない。特徴量を増やすほど過学習のリスクが上がる。

#### 原因2: データリーク（Data Leakage）

> **データリークとは**  
> テストデータの情報が「前処理の段階で」学習に混入してしまうこと。  
> CV スコアは高く見えるが、実際の提出スコアは低くなる。

具体例：Title の Rare 判定を train+test を結合して行っていた。

```python
# 問題のあるコード
combined = pd.concat([train_data, test_data])  # test のデータを混ぜている
rare_titles = combined["Title"].value_counts()[...].index  # test の情報が混入
```

これは「試験の答案を見ながら勉強する」ようなものであり、本番（提出）では通用しない。

#### 原因3: モデル選択バイアス

「GridSearchCV で最良パラメータを見つけた後、同じデータで cross_val_score を計算する」という手順に問題があった。

```
問題: パラメータ選択 と 性能評価 に同じデータを使っている
結果: 「良く見えるモデルを選ぶ」という行為自体が、評価スコアを楽観的にする
```

## ステップ5: 精度改善アプローチの見直し

### アプローチA: 特徴量の逐次追加

**なぜ「全部載せ」をやめたか**

特徴量を一度にすべて追加するのではなく、**1つずつ追加して CV スコアが改善した場合のみ採用**するように変更した。

```python
base_features = ["Pclass", "Sex", "SibSp", "Parch"]  # ベースライン

for feat in candidates_to_add:
    score = cv_score(selected_features + [feat])  # 追加した場合のスコアを測定
    if score > base_score:
        selected_features.append(feat)  # 改善した → 採用
        base_score = score
    # 改善しなかった → 採用しない
```

**このアプローチで学べること**

- 「特徴量が多いほど良い」は間違い
- 各特徴量が「本当に予測に貢献しているか」をデータで確認することが重要
- 直感や理論で「使えそう」と思った特徴量でも、データが答えを持っている

### アプローチB: データリークの修正

train データだけで統計量を計算し、test にも同じ基準を適用するように修正した。

```python
# 修正後: train だけで Rare 判定
rare_titles = train_data["Title"].value_counts()[...].index
train_data["Title"] = train_data["Title"].replace(rare_titles, "Rare")
test_data["Title"]  = test_data["Title"].replace(rare_titles, "Rare")  # 同じ基準を適用
```

**データリークを防ぐ原則**

> 前処理で使う統計量（平均・中央値・最頻値など）は**常に train データだけで計算し**、  
> その値を test データに適用する。

### アプローチC: Age の影響を明示的に検証

Age は約20%が欠損しており、補完した値は「推定値」に過ぎない。  
補完値がノイズになっていないかを、**あり/なしを直接比較**して判断した。

```python
score_without_age = cv_score(selected_features)           # Age なし
score_with_age    = cv_score(selected_features + ["Age"]) # Age あり

# スコアが上がった場合のみ採用
if score_with_age > score_without_age:
    selected_features.append("Age")
```

**このアプローチで学べること**

- 欠損値補完は「ないよりまし」とは限らない
- 補完値（推定値）がモデルにノイズを与える可能性がある
- 仮説（「補完がノイズかもしれない」）を立て、実験で確認する姿勢が重要

## ステップ6: Nested CV の導入

### モデル選択バイアスの解決

GridSearchCV でパラメータを選んだ後に cross_val_score で評価すると、評価スコアが楽観的になる問題を解決した。

**解決策: Nested CV（二重交差検証）**

GridSearchCV を「一つの推定器」として cross_val_score に渡すことで、パラメータ選択と性能評価を**別々のデータ分割**で行う。

```
外側CV（cross_val_score）: 汎化性能の評価
  └─ 内側CV（RandomizedSearchCV）: ハイパーパラメータ探索

→ パラメータ選択に使ったデータ で評価しないため、スコアが正直になる
```

```python
inner_cv = RandomizedSearchCV(estimator, param_dist, n_iter=100, cv=5, ...)
outer_scores = cross_val_score(inner_cv, X, y, cv=5, scoring="accuracy")
# outer_scores = 「バイアスのない」汎化性能の推定
```

> **注意**  
> Nested CV のスコアは以前の方法より低く出る場合があります。  
> しかしこれは「精度が下がった」のではなく「より正直なスコアになった」ということです。  
> 実際に Kaggle に提出したときの精度に近い値が得られます。

## ステップ7: RandomizedSearchCV への切り替え

### GridSearchCV の限界

探索するパラメータが増えると組み合わせ数が爆発的に増え、時間がかかりすぎる。

```
6つのパラメータ × 各5通り = 5^6 = 15,625通り × 5-fold = 78,125回の学習
```

### RandomizedSearchCV の利点

全組み合わせを試す代わりに、**確率分布からランダムにサンプリング**する。

```python
# 連続した範囲を指定できる
param_dist = {
    "n_estimators": randint(100, 600),      # 100〜599 の整数から無作為抽出
    "learning_rate": uniform(0.01, 0.30),   # 0.01〜0.30 の実数から無作為抽出
}
RandomizedSearchCV(estimator, param_dist, n_iter=100, ...)  # 100通りだけ試す
```

- GridSearch では「指定した値の中でのベスト」しか見つけられない
- RandomizedSearch では「連続した範囲の中」から探せるため、より良い値を見つけやすい

## ステップ8: VotingClassifier によるアンサンブル

### アンサンブルとは

複数のモデルの予測を組み合わせて最終予測を出す手法。  
「多数決」に近い考え方で、1つのモデルが間違えても他のモデルで補正できる。

### ソフト投票（Soft Voting）

各モデルが出力する「予測確率」を平均して最終判定する。単純な多数決（ハード投票）より精度が高いことが多い。

```
RandomForest → 生存確率 0.65 ─┐
XGBoost      → 生存確率 0.72 ─┼─ 平均 0.68 → 生存（0.68 > 0.5）
LightGBM     → 生存確率 0.67 ─┘
```

```python
voting = VotingClassifier(
    estimators=[("rf", tuned_rf), ("xgb", tuned_xgb), ("lgbm", tuned_lgbm)],
    voting="soft",
)
```

**なぜアンサンブルが効くのか**

3つのモデルはそれぞれ異なるアルゴリズムで学習しているため、**異なる種類のエラーを犯す**。  
多数決を取ることで、あるモデルのエラーが他のモデルによって打ち消される。

## 精度改善プロセス全体の振り返り

### 時系列まとめ

```
ステップ1: シンプルな4特徴量 × RandomForest でベースライン作成
    ↓
ステップ2: 特徴量エンジニアリング（Title・FamilySize等）・欠損値処理を追加
    ↓
ステップ3: XGBoost・LightGBM に切り替え、GridSearchCV でチューニング
    ↓
【問題発生】Kaggle スコアがベースラインより低下
    ↓
ステップ4: 原因分析（過学習・データリーク・モデル選択バイアス）
    ↓
ステップ5: アプローチA（逐次追加）・B（リーク修正）・C（Age検証）を実施
    ↓
ステップ6: Nested CV でバイアスのない評価を導入
    ↓
ステップ7: RandomizedSearchCV で広いパラメータ空間を効率探索
    ↓
ステップ8: VotingClassifier でアンサンブル → 最終モデル
```

### 失敗から学ぶこと

| 失敗 | 原因 | 教訓 |
|---|---|---|
| 特徴量を増やしたら精度が下がった | 過学習 | 少ないデータでは「シンプルさ」が重要 |
| CV スコアは高いのに提出スコアが低い | データリーク | 前処理の統計量は train のみで計算する |
| チューニング後のスコアが楽観的 | モデル選択バイアス | 評価とチューニングは別データで行う |

## 機械学習改善の一般的な進め方（まとめ）

精度改善は以下のサイクルを繰り返すことで行う。

```
① ベースラインを作る
    ↓
② 仮説を立てる（「この特徴量を追加すれば良くなるはず」等）
    ↓
③ 実装して CV スコアを測定
    ↓
④ 改善した → 採用。改善しなかった → 却下
    ↓
⑤ Kaggle に提出して実際のスコアを確認
    ↓
⑥ CV スコアと提出スコアに差がある → データリーク・過学習を疑う
    ↓
⑦ ① に戻る
```

> **最も大切なこと**  
> 「なぜこの手法を使うのか」「何を解決しようとしているのか」を  
> 常に意識しながら改善を進めること。手法を目的にしないこと。
