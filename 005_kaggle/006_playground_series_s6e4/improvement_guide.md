## クラス不均衡の対策：どんな方法があるか？

精度向上の前に、まず「クラス不均衡」という根本的な課題を理解する必要があります。

### 対策の分類

| 大分類 | 手法 | 概要 |
|--------|------|------|
| **データレベル** | オーバーサンプリング（SMOTE等） | 少数クラスを人工的に増やす |
| **データレベル** | アンダーサンプリング | 多数クラスを減らして均衡化 |
| **アルゴリズムレベル** | `class_weight='balanced'` | 損失計算時に少数クラスを重く扱う |
| **アルゴリズムレベル** | `is_unbalance=True`（LightGBM）| 自動でクラス重みを調整 |
| **評価指標** | Balanced Accuracy Score | 各クラスを均等に評価する指標を使う |

### なぜ今回は「アルゴリズムレベルの対策」を最初に選んだか

```
選択の理由：

データ数が 63万件 と大規模
  → SMOTE（人工データ生成）を全データに適用すると時間がかかりすぎる
  → まず class_weight でデータを変えずにモデル側で吸収する方が高速

High クラスが 3.3% と少ないが、0% ではない
  → 完全に無視されているわけではない
  → 重み付けだけである程度対処できる可能性が高い
```

> **重要な原則**  
> 試行コストの低い方法から順番に試す。  
> 時間のかかる方法（SMOTE等）は、シンプルな方法で限界が見えてから試せばよい。

## ステップ1: ベースラインモデルの作成

### 何をしたか

`class_weight='balanced'` を設定した **RandomForest** で最初のモデルを作成した。

```python
model = RandomForestClassifier(
    n_estimators=300,
    class_weight="balanced",   # 少数クラス（High）を自動で重み付け
    random_state=42,
    n_jobs=-1,
)
```

### なぜ RandomForest を選んだか

| 理由 | 説明 |
|------|------|
| 解釈しやすい | `feature_importances_` で重要な特徴量がわかる |
| 実装が簡単 | sklearn の 1クラスで完結 |
| 頑健性が高い | 外れ値や欠損値に比較的強い |
| 基準として使いやすい | 最初のモデルに向いている |

### 5-Fold CV で評価する理由

```
データ全体 [1][2][3][4][5]

1回目: [検証][学習][学習][学習][学習]
2回目: [学習][検証][学習][学習][学習]
...（5回繰り返し）

→ 5回の平均スコアが「真の精度の推定値」となる
  偶然良いデータ分割だっただけ、という可能性を排除できる
```

### StratifiedKFold を使う理由

```python
skf = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)
```

通常の KFold ではなく **StratifiedKFold** を使うのは、  
各 fold で Low / Medium / High の比率が元のデータと同じになるようにするため。

```
StratifiedKFold なし（運が悪いと）:
  fold1: Low=70%, Medium=27%, High=3%
  fold2: Low=50%, Medium=45%, High=5%  ← 評価が不安定

StratifiedKFold あり（常に安定）:
  fold1: Low=58.7%, Medium=37.9%, High=3.3%
  fold2: Low=58.7%, Medium=37.9%, High=3.3%  ← 安定した評価
```

### 結果

```
=== 5-Fold CV Balanced Accuracy ===
  Fold 1: 0.9571
  Fold 2: 0.9580
  Fold 3: 0.9582
  Fold 4: 0.9584
  Fold 5: 0.9582
  Mean : 0.9580  ±0.0005

Train Balanced Accuracy : 1.0000  ← 問題あり
```

**Kaggle スコア: 0.95865**

### 結果の読み取りと問題点の発見

```
Train = 1.0000（完璧）
CV    = 0.9580
差分  = 0.0420  ← 過学習が発生している！
```

**過学習（Overfitting）とは**：  
モデルが学習データを「丸暗記」してしまい、未知のデータに対応できなくなる現象。

```
理想的なモデル: データの「本質的なパターン」を学習する
過学習したモデル: 学習データ特有の「ノイズ」まで覚えてしまう

→ 学習データでは高精度、テストデータでは低精度
```

RandomForest は深さ無制限（`max_depth=None`）なので、  
各決定木が学習データを完全に分類できるまで分岐し続けてしまう。  
これが Train=1.0 の原因。

## ステップ2: LightGBM への切り替え

### なぜ LightGBM に切り替えたか

| 比較項目 | RandomForest | LightGBM |
|----------|-------------|---------|
| 学習方式 | 複数の木を**独立して**学習、多数決で予測 | 前の木の「失敗」を次の木が修正しながら学習（勾配ブースティング）|
| 過学習抑制 | 深さ無制限だと過学習しやすい | `early_stopping` で自動的に最適な木の本数を決定 |
| 速度 | 遅め | 高速（大規模データに強い）|
| 実績 | 安定して高性能 | Kaggle の表形式コンペで最も実績がある |

### 勾配ブースティングとは

```
学習データ → [木1] → 誤差 → [木2（誤差を修正）] → 誤差 → [木3] → ... → 最終予測

RandomForest: 複数の木が「独立して」学習して多数決
LightGBM:    複数の木が「前の失敗を引き継いで」順番に学習
```

### Early Stopping の仕組み

```python
model = lgb.train(
    params,
    dtrain,
    num_boost_round=2000,          # 最大2000本の木まで学習
    valid_sets=[dval],             # 検証データで性能を監視
    callbacks=[
        lgb.early_stopping(stopping_rounds=100),  # 100本改善なしで停止
    ],
)
```

```
木が増えるにつれて検証スコアがどう変化するか：

木の本数  検証スコア
   100    0.9580
   200    0.9610  ↗ 改善中
   287    0.9618  ↗ ここが最高
   387    0.9615  ↘ 100本改善なし → 停止
   ...（2000本まで学習しなくていい）
```

**Early Stopping の利点**：  
- 過学習が始まる前に自動停止 → 過学習を抑制できる  
- 無駄な計算をしない → 高速化  
- 毎 fold で最適な木の本数が自動決定される

### OOF（Out-of-Fold）予測とは

```python
oof_probs  = np.zeros((len(X), 3))   # 全データ分の予測確率を格納
test_probs = np.zeros((len(X_test), 3))

for fold, (tr_idx, val_idx) in enumerate(skf.split(X, y), 1):
    # 学習・検証
    oof_probs[val_idx] = model.predict(X_val)  # 検証データの予測を保存
    test_probs += model.predict(X_test) / 5    # テスト予測は5fold の平均
```

```
OOF（Out-of-Fold）の仕組み：

Fold1: [学習][学習][学習][学習] → [検証の予測を保存]
Fold2: [学習][学習][学習][学習] → [検証の予測を保存]
...
すべての fold の検証予測を結合 → 全データの予測が完成

→ この OOF スコアが「データリークのない正直な精度推定値」
```

**テスト予測に 5fold の平均を使う理由**：  
単一モデルより予測のブレが減り、安定したスコアになる。

### 結果

```
=== 5-Fold CV Balanced Accuracy ===
  Fold 1: 0.9608  (best iter=321)
  Fold 2: 0.9622  (best iter=287)
  Fold 3: 0.9626  (best iter=289)
  Fold 4: 0.9607  (best iter=311)
  Fold 5: 0.9618  (best iter=293)
  OOF  : 0.9618
```

**Kaggle スコア: 0.96179**

| モデル | CV OOF | Kaggle スコア | 改善幅 |
|--------|--------|--------------|--------|
| RandomForest（baseline） | 0.9580 | 0.95865 | — |
| LightGBM | 0.9618 | 0.96179 | **+0.00314** |

## ステップ3: 特徴量エンジニアリング

### 特徴量エンジニアリングとは

```
元のデータにある情報を「別の角度から表現」することで、
モデルが学習しやすい新しい特徴量を作る作業。

例：
  Temperature_C = 26.97
  Wind_Speed_kmh = 3.85
                     ↓ 組み合わせる
  Temp_x_Wind = 26.97 × 3.85 = 103.9
  （気温が高くて風が強いほど蒸発しやすい → 灌漑必要量に影響）
```

### なぜ特徴量エンジニアリングをするのか

LightGBM などの決定木モデルは、**特徴量を1つずつ個別に**参照してデータを分割する。  
2つの特徴量の組み合わせから生まれるパターンを検出するには  
多くの分岐が必要になり、非効率。

```
LightGBM が見ているもの（個別）:
  「Temperature_C > 25 か？」
  「Wind_Speed_kmh > 10 か？」

特徴量エンジニアリング後:
  「Temp_x_Wind > 200 か？」
  （気温と風速の複合効果を1回の分岐で判定できる）
```

### どんな特徴量を作ったか

作成の発想は「農業・気象の常識」から来ている。

| 特徴量名 | 計算式 | 農業的な意味 |
|---------|--------|------------|
| `Temp_x_Humidity` | 気温 × 湿度 | 蒸発散量の代理変数（高いほど水が蒸発しやすい）|
| `Water_balance` | 降水量 − 土壌水分×10 | 水分収支（負 → 灌漑が必要な状態）|
| `Temp_x_Wind` | 気温 × 風速 | 風による蒸発促進（重要度 Top5 に入った）|
| `Sun_x_Temp` | 日照時間 × 気温 | 太陽エネルギーによる蒸発散 |
| `Moisture_rain_ratio` | 土壌水分 ÷ 降水量 | 降水に対して土壌がどれだけ保水できているか |
| `OC_x_Moisture` | 有機炭素 × 土壌水分 | 土壌の保水力の複合指標 |
| `Rain_per_area` | 降水量 ÷ 農地面積 | 単位面積あたりの降水量 |
| `Irr_moisture_diff` | 前回灌漑量 − 土壌水分 | 追加灌漑の必要度 |
| `num_mean` | 数値列の行ごとの平均 | 外れ値レコードの検出 |
| `num_std` | 数値列の行ごとの標準偏差 | データのばらつき具合 |

### コードの分離設計：features.py を独立させた理由

```
006_playground-series-s6e4/
├── features.py          ← 特徴量エンジニアリング専用（新規）
├── s6e4_lgbm_fe.py      ← features.py を使った学習（新規）
├── s6e4_lgbm.py         ← 既存のまま
└── s6e4_baseline.py     ← 既存のまま
```

**分離した理由**：

```python
# どのファイルからでも同じ特徴量を使い回せる
from features import add_features

train = add_features(train)
test  = add_features(test)
```

後で Optuna チューニングやアンサンブルを追加するときも、  
`from features import add_features` の1行で同じ特徴量が使える。  
特徴量の定義が1か所にまとまり、修正漏れも防げる。

### 特徴量エンジニアリングはいつ適用するか

```
【重要】エンコード前に適用する

1. データ読み込み
2. 特徴量エンジニアリング（ここで適用）← 元の数値列を使って計算
3. カテゴリ変数をエンコード
4. モデル学習
```

```python
train = add_features(train)   # ← 先にやる
test  = add_features(test)

# その後にエンコード
for col in cat_cols:
    le = LabelEncoder()
    train[col] = le.fit_transform(train[col])
    test[col]  = le.transform(test[col])
```

エンコード後だと、元の「Soil_Moisture」や「Rainfall_mm」などの  
数値列を正しく参照できなくなる。

## ステップ4: Optuna でハイパーパラメータ自動探索

### ハイパーパラメータとは

```
ハイパーパラメータ = モデルの「設定値」

例：
  num_leaves=127    ← 木の葉の最大数（モデルの複雑さ）
  learning_rate=0.05 ← 1本の木をどれだけ信頼するか
  lambda_l1=0.1     ← 正則化の強さ（過学習を抑える）

これらの最適な値はデータによって異なるため、
試行錯誤で探す必要がある。
```

### なぜ手動で探さないのか：GridSearch の限界

```
5つのパラメータを各5通り試すと：
  5^5 = 3,125通り × 5-Fold CV = 15,625回の学習

→ 現実的な時間では終わらない
```

### Optuna の仕組み

Optuna は「**ベイズ最適化**」を使って効率的にパラメータを探索する。

```
ランダム探索（GridSearch の改良版）:
  試行1: num_leaves=200 → score=0.960
  試行2: num_leaves= 80 → score=0.963
  試行3: 80付近が良さそう → num_leaves= 95 → score=0.964
         ↑ 良かった領域を優先的に探索

完全にランダムではなく、「これまでの結果から良さそうな場所」を重点的に試す
```

### 2段階の CV 設計：なぜ Optuna 中は 3-Fold にするか

```
Optuna 探索中（3-Fold）:
  50試行 × 3 Fold = 150回の学習
  → 速度優先（1試行あたり約3分 × 50 = 約2.5時間）

最終評価（5-Fold）:
  ベストパラメータが確定してから精度高く評価
  → 信頼性優先
```

```python
N_TRIALS   = 50   # 試行回数
N_CV_FOLDS = 3    # Optuna 中は 3-Fold（速度優先）

# 最終評価だけ 5-Fold
skf5 = StratifiedKFold(n_splits=5, ...)
```

### 探索したパラメータと意味

| パラメータ | 探索範囲 | 効果 |
|-----------|---------|------|
| `learning_rate` | 0.005 〜 0.1（対数スケール） | 小さいほど丁寧に学習するが時間がかかる |
| `num_leaves` | 31 〜 511 | 大きいほど複雑なモデル（過学習リスクあり）|
| `min_child_samples` | 5 〜 100 | 大きいほど過学習を抑制 |
| `feature_fraction` | 0.5 〜 1.0 | 各木でランダムに使う特徴量の割合 |
| `bagging_fraction` | 0.5 〜 1.0 | 各木でランダムに使うデータの割合 |
| `lambda_l1 / l2` | 0.001 〜 10（対数スケール） | 正則化の強さ（大きいほど過学習を抑制）|

### 対数スケールで探索する理由

```python
"learning_rate": trial.suggest_float("learning_rate", 0.005, 0.1, log=True)
```

```
線形スケール: 0.005, 0.010, 0.015, ..., 0.100  （均等な間隔）
対数スケール: 0.005, 0.010, 0.020, 0.040, 0.080 （比率が均等）

learning_rate の場合：
  0.005 → 0.010 の変化（×2倍）と
  0.050 → 0.100 の変化（×2倍）は同じ「大きさの変化」
  → 対数スケールの方が自然な探索ができる
```

### 進捗コールバックの実装

学習に時間がかかるため、途中経過を確認できる仕組みを追加した。

```python
def progress_callback(study, trial):
    best_mark = " ★ best" if trial.value == study.best_value else ""
    print(
        f"  [{trial.number + 1:>3}/{N_TRIALS}]"
        f"  score={trial.value:.5f}"
        f"  best={study.best_value:.5f}"
        f"{best_mark}"
    )
```

```
出力例：
  [  1/ 50]  score=0.96142  best=0.96142  ★ best
  [  2/ 50]  score=0.95834  best=0.96142
  [  3/ 50]  score=0.96201  best=0.96201  ★ best
  ...
```

**重要**：コールバックは各試行が終わった後に呼ばれるだけなので、  
**学習処理の速度には一切影響しない**。

## 精度向上プロセス全体の振り返り

### 時系列まとめ

```
ステップ1: クラス不均衡を理解し、対策方法を整理
  → class_weight='balanced' + RandomForest でベースライン作成
  → スコア: 0.95865
    ↓
  [問題発見] Train=1.0、CV=0.958 → 過学習が起きている
    ↓
ステップ2: 過学習を抑えられる LightGBM に切り替え
  → early_stopping で最適な木の本数を自動決定
  → スコア: 0.96179（+0.00314）
    ↓
ステップ3: ドメイン知識を活かした特徴量エンジニアリング
  → 「気温×風速」などの農業的に意味のある交互作用を追加
  → スコア: 0.96217（+0.00038）
    ↓
ステップ4: Optuna でハイパーパラメータを自動探索
  → 手動設定のデフォルト値より良いパラメータを発見
  → スコア: 0.96272（+0.00055）
```

### 各ステップで使った技術の整理

| ステップ | 主な技術 | 解決した問題 |
|---------|---------|-----------|
| 1 | `class_weight='balanced'`、StratifiedKFold | クラス不均衡、公正な評価 |
| 2 | LightGBM、Early Stopping、OOF 予測 | 過学習の抑制、精度向上 |
| 3 | 交互作用特徴量、ファイル分離設計 | モデルに与える情報の質向上 |
| 4 | Optuna（ベイズ最適化）、2段階 CV | 最適なハイパーパラメータの発見 |

### 改善量から学ぶ優先順位

```
モデルの切り替え（RF → LightGBM）: +0.00314  ← 最大の改善
Optuna チューニング               : +0.00055
特徴量エンジニアリング              : +0.00038
```

> **重要な教訓**  
> モデルの選択（アルゴリズムレベルの改善）が最も大きな効果をもたらした。  
> 複雑な特徴量を作るより先に、「適切なモデルを使えているか？」を確認することが重要。

## 機械学習の精度向上：一般的な進め方（まとめ）

精度向上は以下のサイクルを繰り返すことで行う。

```
①  問題を理解する（EDA）
   → データの分布、クラス不均衡、欠損値を確認
    ↓
②  シンプルなベースラインを作る
   → 評価の基準（ベースライン）を確立する
    ↓
③  問題点を発見する
   → 過学習？ クラス不均衡？ 特徴量が足りない？
    ↓
④  1つずつ改善して CV スコアを測定
   → 改善した → 採用、改善しなかった → 却下
    ↓
⑤  Kaggle に提出して実際のスコアを確認
   → CV スコアと大きく乖離 → データリーク・過学習を疑う
    ↓
⑥  ①に戻る
```

> **最も大切なこと**  
> 「どの技術を使うか」ではなく、「何の問題を解決しようとしているのか」を  
> 常に意識しながら改善を進めること。  
> 技術は目的ではなく、**「精度を上げるための手段」として使うことが重要**。
