## はじめに：このコンペティションで学べること

| 観点 | 内容 |
|---|---|
| 問題の種類 | 二値分類（Binary Classification） |
| 目的変数 | PitNextLap（1=次のラップでピットイン、0=しない） |
| 評価指標 | ROC-AUC（受信者動作特性曲線下面積） |
| 特徴 | **表形式データ**・**クラス不均衡**（PitNextLap=1 が約 20%）・**外部データ活用可能** |

### ROC-AUC とは

```
ROC-AUC = 0 と 1 のサンプルをランダムに1件ずつ取り出したとき、
           モデルが正しく「1のほうが高い確率」と予測できる確率

AUC = 0.5: ランダム予測と同じ（全く意味がない）
AUC = 1.0: 完璧な予測
AUC = 0.95: 実用的に優秀なモデル
```

NLP コンテストの F1 スコアと違い、ROC-AUC は**閾値に依存しない**指標です。
確率値（0〜1 の実数）を提出するため、「何%以上をピットありと判定するか」を
決めなくても評価できます。

> **精度改善の基本原則**（このコンペ全体を通じて）
> - まずシンプルなモデルでベースラインを確立する
> - 変更は1つずつ行い、各変更の効果を OOF スコアと Kaggle LB 両方で測定する
> - OOF と LB の差（ギャップ）を常に意識する

## ステップ 0：ドメイン知識の収集（モデル作成前の準備）

### なぜドメイン知識が必要なのか

表形式データのコンテストでは、**データの背景にある現実を理解している人が有利**です。

```
モデルは「数値のパターン」しか見えない
ドメイン知識があると「この数値は何を意味するか」が分かる
→ 効果的な特徴量エンジニアリングのアイデアが浮かぶ
→ おかしな予測の原因に気づける
```

### 今回のデータで調べたこと：F1 のピット戦略

F1 のピットストップとは何かを理解するために、各特徴量がピット判断にどう影響するかを調査しました。

#### データに含まれる特徴量と F1 ドメイン知識

| 特徴量 | F1 での意味 | ピット予測への影響 |
|---|---|---|
| `TyreLife` | タイヤを装着してから何周走ったか | **最重要**：長いほどピット近し |
| `Compound` | タイヤの種類（SOFT/MEDIUM/HARD/雨用） | SOFT は早期交換、HARD は長持ち |
| `Cumulative_Degradation` | 累積劣化量 | 大きいほどタイヤが消耗している |
| `LapTime_Delta` | 前周からのラップタイム変化 | 正（遅くなっている）→ 劣化進行 |
| `Stint` | 何回目のスティント（タイヤセット）か | スティント数が増えるほど次ピットが近い |
| `Year` | シーズン年 | タイヤ規定がシーズンごとに異なる |
| `RaceProgress` | レースの進行度（0〜1） | 典型的なピット窓のタイミングを示す |
| `Position` | 現在の順位 | 下位ほどアンダーカット戦略の動機が強い |
| `Race` | グランプリ名 | サーキット特性でタイヤ消耗速度が異なる |
| `Driver` | ドライバー ID | タイヤ管理スタイルに個人差がある |

#### F1 ピット戦略の重要概念

**アンダーカット戦略**
```
前方の車より先にピットインして、フレッシュタイヤの速さで
前に出る戦略。順位が悪い車ほど試みる動機が強い。
```

**タイヤコンパウンドと標準スティント長（実データから調査）**
```
SOFT       : 中央値 12 周でピット（最も消耗が速い）
MEDIUM     : 中央値 16 周でピット
HARD       : 中央値 20 周でピット（最も長持ち）
INTERMEDIATE: 中央値 17 周（雨天用）
WET        : 中央値 11 周（豪雨用）
```

**コースによる差（調査で発見した事実）**
```
モナコ  × HARD : 中央値 28 周 → タイヤに優しいコース
アゼルバイジャン × HARD: 中央値 20 周 → 標準的なコース
```

#### ドメイン知識をどのようにモデルに活かしたか

調査で得た知識は2つの形でモデルに活用しました。

1. **特徴量エンジニアリングのアイデア**
   - `TyreLife_Ratio`（タイヤ寿命の進捗率）: `TyreLife / 標準スティント長`
   - `Compound_Dur`（耐久性の数値化）: SOFT=1, MEDIUM=2, HARD=3 に変換
   - `TyreLife_sq`（二乗項）: タイヤは後半ほど急速に劣化するため非線形を表現

2. **特徴量重要度の解釈**
   - `Year` と `Stint` が最重要 → タイヤ規定とスティント文脈がピットを支配
   - ドメイン知識と一致 → モデルが妥当な学習をしている証拠

> **ドメイン知識収集の汎用的な進め方**
> 1. データの各カラムが「現実の何を意味するか」を調べる
> 2. 目的変数との関係を「常識」から予想する
> 3. 実際にデータで確認する（`groupby` での集計など）
> 4. 予想と一致する特徴量 → 信頼できる特徴量
> 5. 予想と外れた特徴量 → なぜ違うか考えることで深い理解が生まれる

## ステップ 1：ベースラインモデルの作成

### 何をしたか

LightGBM + StratifiedKFold（5-Fold CV）で最初のモデルを作成しました。

### なぜ LightGBM を選んだか

表形式データのコンペティションではほぼ必ず LightGBM・XGBoost・CatBoost などの
**勾配ブースティング**系モデルが上位に来ます。

```
勾配ブースティングの仕組み:
  学習データ → [木1] → 誤差 → [木2（誤差を修正）] → 誤差 → [木3] → ...

RandomForest: 複数の木が「独立して」学習し、多数決で予測
LightGBM   : 複数の木が「前の木の失敗を引き継いで」順番に学習
→ LightGBM の方が同じ木の数でより精度が高い傾向がある
```

特に LightGBM は以下の理由で表形式データに強いです。
- 大規模データ（439K行）でも高速
- カテゴリ変数を扱いやすい
- `is_unbalance=True` でクラス不均衡を自動補正できる

### クラス不均衡への対処

```
PitNextLap=0（ピットしない）: 80.1%
PitNextLap=1（ピットする）  : 19.9%

→ 何も対策しないと、モデルは「常にピットしない」と予測しても
  Accuracy=80% になってしまう（ROC-AUC は低いままだが）
→ is_unbalance=True でモデルが少数クラスを重視するよう自動調整
```

### StratifiedKFold とは

```
通常の KFold:
  fold1: 訓練80% / 検証20% ← ランダムに分割するとクラス比率が偏ることがある

StratifiedKFold:
  fold1: 訓練80% / 検証20%  ← 各フォールドで PitNextLap=1 が約 20% を保証
  fold2: 訓練80% / 検証20%  ← 同様
  ...
```

クラス不均衡がある場合、`StratifiedKFold` が必須です。
通常の KFold では検証データにたまたま少数クラスが少なくなり、
スコアが不安定になります。

### OOF（Out-of-Fold）予測とは

```
OOF: 各サンプルが「自分を含まないフォールドで学習したモデル」から予測を受ける

Fold1 のモデル: Fold2〜5 で学習 → Fold1 の 20% を予測
Fold2 のモデル: Fold1,3〜5 で学習 → Fold2 の 20% を予測
...

→ 全 439,140 行の予測が揃う
→ これが「データリークのない正直な精度推定値」
```

テスト予測は 5 フォールドの平均を使います。
単一モデルより安定した予測になります。

### 追加した特徴量（ドメイン知識に基づく）

```python
df["TyreLife_sq"]         = df["TyreLife"] ** 2          # 劣化の非線形性
df["TyreLife_sqrt"]       = np.sqrt(df["TyreLife"])       # 逆方向の非線形性
df["Degradation_Rate"]    = df["Cumulative_Degradation"] / (df["TyreLife"] + 1)
df["Compound_Dur"]        = df["Compound"].map({"SOFT":1, "MEDIUM":2, "HARD":3, ...})
df["TyreLife_x_Dur"]      = df["TyreLife"] / df["Compound_Dur"]  # コンパウンド考慮済み消耗度
df["Progress_x_TyreLife"] = df["RaceProgress"] * df["TyreLife"]  # 戦略タイミング
```

### 結果

```
=== 5-Fold Cross Validation ===
  Fold 1  AUC=0.94974
  Fold 2  AUC=0.94751
  Fold 3  AUC=0.94844
  Fold 4  AUC=0.94783
  Fold 5  AUC=0.94852

OOF AUC: 0.94840
```

**Kaggle スコア: 0.94821**

特徴量重要度では `Year`（1位）と `Stint`（2位）が突出していました。
これはドメイン知識と一致します。
- `Year`：シーズンごとのタイヤ規定の違い
- `Stint`：何回目のスティントかがピット回数に直結

## ステップ 2：特徴量エンジニアリングの試み（失敗から学ぶ）

### 何をしたか

「グループ集計統計」と「ラグ特徴量（時系列的な前周のデータ）」を追加しました。

#### グループ集計特徴量のアイデア

```
例: HARD タイヤ × モナコ GP → 平均 28 周でピット
    SOFT タイヤ × 同じ GP  → 平均 12 周でピット

→ 「このタイヤ・このレースで何周が標準か」を特徴量として与えると、
   現在の TyreLife が標準の何%にあたるかが計算できる
→ TyreLife_Ratio = TyreLife / Expected_Stint_Len
```

#### ラグ特徴量のアイデア

```
現在の周のラップタイムだけでなく、
「直前2周のラップタイムの変化（劣化トレンド）」も予測に使える
```

### 結果と失敗の分析

```
特徴量エンジニアリング版  OOF AUC: 0.94773（ベースライン比 -0.00067）
Kaggle スコア: 0.94757（ベースライン比 -0.00064）
```

**なぜ改善しなかったか**

理由1：`Year` と `Stint` が既に「標準スティント長」の情報を内包していた
```
Year  → タイヤ規定の年代（どんなコンパウンドが多いか）
Stint → 何回目のピットか → 残りスティント数が分かる

→ Expected_Stint_Len を追加しても、モデルにとって新情報が少ない
```

理由2：ラグ特徴量のデータリーク問題
```
データはランダムに訓練/テスト分割されている可能性がある
→ ラップ N の「前周データ」が訓練に、ラップ N 自体がテストに入ることがある
→ CVでは一部のラグ値が不正確になり、スコアが不安定に
```

> **学べること**
> - ドメイン知識から「良さそうな特徴量」を思いついても、データが証明するまでは採用しない
> - 特徴量追加は1つずつ検証し、OOF スコアが上がる場合のみ採用する
> - 時系列的なラグ特徴量はランダム分割データには注意が必要

## ステップ 3：Optuna によるハイパーパラメータ最適化

### ハイパーパラメータとは

```
ハイパーパラメータ = モデルの「設定値」

例:
  num_leaves=127    → 木の葉の最大数（モデルの複雑さ）
  learning_rate=0.05 → 1本の木をどのくらい信頼するか
  lambda_l1=0.1     → 正則化の強さ（過学習を防ぐ）

これらの最適な値はデータによって異なるため、
試行錯誤で探す必要がある
```

### なぜ Optuna を使うか

```
総当たり（GridSearch）の問題:
  5つのパラメータ × 各5通り = 5^5 = 3,125通り × 5-Fold = 15,625 回学習
  → 現実的な時間では終わらない

Optuna の解決策（ベイズ最適化）:
  試行1: num_leaves=200 → AUC=0.960
  試行2: num_leaves=80  → AUC=0.963
  試行3: 80付近が良さそう → num_leaves=95 → AUC=0.964
         → 良かった領域を優先的に探索

完全にランダムではなく、「これまでの結果から賢く絞り込む」
```

### 2段階 CV 設計

```
Optuna 探索フェーズ（3-Fold、高速化）:
  50試行 × 3 Fold = 150回の学習
  → 速度優先で大まかな最適パラメータを発見

最終評価フェーズ（5-Fold、信頼性重視）:
  ベストパラメータで 5-Fold CV
  → ベースラインと同条件で公平な比較
```

### 結果

```
=== Optuna 探索結果 ===
Best 3-Fold AUC: 0.94883

Best params:
  learning_rate:  0.01124（ベースラインの 0.05 より大幅に低い）
  num_leaves:     206（ベースラインの 127 より多い）
  lambda_l1:      5.05（ベースラインの 0.1 より大幅に強い）
  min_split_gain: 0.644（意味のある分岐のみ行う）

=== 最終 5-Fold CV ===
OOF AUC: 0.94937（ベースライン比 +0.00097）
```

**Kaggle スコア: 0.94873**

### ベストパラメータから学べること

| パラメータ | ベースライン | 最適値 | 意味 |
|---|---|---|---|
| `learning_rate` | 0.05 | **0.0112** | 低い→丁寧に学習、木の本数が増える |
| `num_leaves` | 127 | **206** | 多い→複雑なパターンを捉えられる |
| `lambda_l1` | 0.1 | **5.05** | 強い正則化→過学習を大きく抑制 |
| `best_iter`（平均） | ~650 | **~1,885** | 学習率が低いため約3倍の反復が必要 |

**「学習率を下げて木を増やし、強い正則化で過学習を防ぐ」**
これが最も効果的な組み合わせでした。

## ステップ 4：LightGBM + CatBoost アンサンブル

### アンサンブルとは

```
複数のモデルの予測を組み合わせて最終予測を作る方法

例:
  LightGBM → 確率 0.65（ピットあり）
  CatBoost → 確率 0.72（ピットあり）
  平均     → 0.685（最終予測）

→ 単体モデルより安定した予測になる
  「一方のモデルが間違えても、もう一方が補正する」
```

### なぜ CatBoost を選んだか

このデータには `Driver`（887 種類）・`Race`・`Compound` という
**カーディナリティ（種類数）の高いカテゴリ変数**があります。

```
LightGBM の処理:
  "Driver" → Label Encoding → 数値に変換
  例: D109=45, D086=22 ...
  問題: 数値に順序関係はないのに、モデルがそう解釈してしまうことがある

CatBoost の処理:
  カテゴリ変数をそのまま受け取る
  内部で「このドライバーは PitNextLap=1 が何%か」という
  ターゲット統計を計算してエンコード
  → ドライバーごとの傾向をより正確に学習できる
```

### アンサンブル重みの最適化

```python
# OOF 予測を使って最適な混合比率を探索
for w in np.linspace(0, 1, 101):
    oof_blend = w * oof_lgbm + (1 - w) * oof_cb
    auc = roc_auc_score(y, oof_blend)
    if auc > best_auc:
        best_w = w
```

OOF データは「訓練データの正解ラベルが分かる」ため、
混合比率を OOF スコアで評価することができます。

### 結果

```
=== 単体モデル OOF AUC ===
  LightGBM : 0.94937
  CatBoost : 0.94890

=== アンサンブル ===
  最適重み: LightGBM=0.57  CatBoost=0.43
  OOF AUC（最適重み）: 0.94992

LightGBM vs CatBoost の OOF 予測相関: 0.9906
```

**Kaggle スコア: 0.94915**

### 重要な観察：モデル間の相関

```
OOF 予測の相関 = 0.9906（非常に高い）

→ 2つのモデルはほぼ同じ予測をしている
→ 「互いの弱点を補う」効果が限定的
→ アンサンブルの改善幅が +0.00042 に留まった

アンサンブル効果を最大化するには:
  相関が低い（異なるタイプの）モデルを組み合わせるほど効果的
```

## ステップ 6：CV 戦略の修正（外部データリーク問題の解決）

### なぜ OOF スコアが過大評価されたか

```
旧 CV 方式:
  [コンペデータ + 外部データ] を 5-Fold で分割
                           ↑
              バリデーションフォールドに外部データが混入

問題:
  外部データは「実際の F1 データ」→ 内部的に一貫性が高い → OOF が簡単
  Kaggle テストは「合成データ」→ 外部データほど一貫していない
  → OOF スコアがテストデータの難しさを反映していない
```

### データリーク（Data Leakage）の概念

```
データリーク = 本来知ってはいけない情報が学習に混入すること

今回のケース:
  外部データがバリデーションフォールドに含まれる
  → バリデーションで外部データを評価 → 簡単すぎるスコアになる
  → 「テストデータ（合成）での性能」を正しく推定できない
```

### 修正後の CV 戦略

```
修正後:
  コンペデータのみを 5-Fold で分割
  ┌─────────────────────────────────────────────────────┐
  │ 訓練  = コンペ訓練折（351K行）+ 全外部データ（101K行） │
  │ 検証  = コンペ検証折（87K行）のみ                      │
  └─────────────────────────────────────────────────────┘

→ 検証は常に「合成データのみ」= Kaggle テストと同じ分布
→ OOF スコアが正直な推定値になる
```

### num_boost_round の増加

前回（旧 CV）の学習ログを確認すると：

```
Fold 1: LightGBM best_iter=3000（上限到達）
Fold 2: LightGBM best_iter=2999（上限到達）
...（全フォールドで上限到達）

→ Early Stopping が発動していない = モデルはまだ改善途中で強制停止
→ num_boost_round を 3000 → 8000 に増やすだけで改善できる
```

## 失敗から学んだこと

### 失敗1：特徴量エンジニアリングが逆効果

| 失敗 | 原因 | 対策 |
|---|---|---|
| グループ集計特徴量が効かなかった | `Year` と `Stint` が既に同じ情報を持っていた | 特徴量重要度を見て重複を確認する |
| ラグ特徴量が不安定 | ランダム分割でラグの参照先が不正確になる | データの分割方式を理解してから実装する |

### 失敗2：外部データで OOF が過大評価された

| 失敗 | 原因 | 対策 |
|---|---|---|
| OOF 0.95933 なのに LB 0.95048 | 外部データがバリデーションに混入してスコアが簡単になった | 外部データは常に訓練フォールドのみに使う |

> **重要な教訓**
> OOF スコアと Kaggle LB スコアの差（ギャップ）を常に監視する。
> ギャップが突然拡大したら、データリークや分布のズレを疑う。

### 失敗3：num_boost_round の設定ミス

| 失敗 | 原因 | 対策 |
|---|---|---|
| 全フォールドで best_iter=3000（上限到達） | モデルが学習途中で強制停止していた | 学習ログを確認し、上限に達していたら増やす |

## OOF スコアと Kaggle LB スコアの読み方

このコンペを通じて分かった「2つのスコアの関係」をまとめます。

```
正常なギャップ（~0.001以下）:
  モデルが汎化できている証拠
  → 改善方向が正しければ、LB も同様に動く

ギャップが急拡大（>0.005）:
  以下のいずれかを疑う:
    1. データリーク（バリデーションに本来知ってはいけない情報が混入）
    2. 過学習（訓練データに特化しすぎている）
    3. 訓練・テストの分布ズレ（外部データの性質がテストと違う）
```

## 機械学習の精度向上：一般的な進め方（まとめ）

このコンペで実践した手法を、汎用的なサイクルとして整理します。

```
①  問題を理解する（EDA + ドメイン知識）
    ↓ データの各カラムの意味・目的変数との関係を把握
②  シンプルなベースラインを作る
    ↓ LightGBM + StratifiedKFold + OOF 評価
③  ハイパーパラメータを最適化する（Optuna）
    ↓ 確実な改善を得てから次のステップへ
④  モデルの多様性を増やす（アンサンブル）
    ↓ 異なる種類のモデルを組み合わせる
⑤  データの質・量を増やす（外部データ）
    ↓ CV 方式が適切かを常に確認する
⑥  OOF と LB のギャップを確認する
    ↓ ギャップが大きければ原因を調査
⑦  ①に戻る
```

> **最も大切なこと**
> どの手法を使うかではなく、「なぜこの手法を使うのか」「何の問題を解決しようとしているのか」
> を常に意識しながら改善を進めること。
> 手法は目的のための手段であって、手法を使うことが目的ではない。
