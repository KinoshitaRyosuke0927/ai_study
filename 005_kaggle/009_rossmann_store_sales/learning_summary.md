## 1. コンペティション概要

**Rossmann Store Sales**（Kaggle）  
ドイツ全土に展開する薬局チェーン Rossmann の **1115 店舗・最大 6 週間先の日次売上を予測** するコンペティション。

### 評価指標: RMSPE（Root Mean Square Percentage Error）

$$\text{RMSPE} = \sqrt{\frac{1}{n} \sum_{i=1}^{n} \left(\frac{y_i - \hat{y}_i}{y_i}\right)^2}$$

- 売上金額の**絶対誤差**ではなく**割合誤差**で評価される
- 売上が少ない店舗の予測精度も同等に重視される
- `log1p(Sales)` を目的変数にすることで RMSPE に近似した損失関数を使える

### データ構成

| ファイル | 内容 |
|---|---|
| `train.csv` | 2013〜2015年の日次売上実績（約 100 万行）|
| `test.csv` | 予測対象（2015年8〜9月の約6週間）|
| `store.csv` | 店舗属性（StoreType, 競合距離, Promo2 設定など）|

### v1 → v2: 店舗別統計量の追加（大きな改善）

#### 何をしたか

店舗 ID は元々「ただの番号」として LightGBM に渡されていた。  
代わりに **各店舗の過去の売上パターンを数値化**して特徴量に追加した。

```python
# 追加した6つの統計量
store_mean       : 店舗の全期間平均売上
store_median     : 店舗の中央値
store_std        : 店舗の売上の標準偏差（ばらつき）
store_dow_mean   : 店舗 × 曜日の平均売上（月曜の売上は？日曜は？）
store_month_mean : 店舗 × 月の平均売上（季節性）
store_promo_mean : 店舗 × プロモ有無の平均売上（プロモ感応度）
```

#### なぜ効いたか

LightGBM は「Store 562 はどんな店か」を学習データから学べるが、  
明示的に「Store 562 の平均売上は 8,500 円」と教えると決定木の分割が格段に効率的になる。

特徴量重要度でも `store_promo_mean`（重要度 1 位）と `store_dow_mean`（重要度 2 位）が最上位になった。

#### 重要: 時系列リークの防止

```
× 間違い: val_fold の Sales も含めて統計を計算してしまう（未来の情報を使ってしまう）
○ 正しい: tr_fold（学習期間）の Sales だけで統計を計算し、val_fold に適用する
```

```python
# CV-safe な計算方法
tr_fold  = add_store_stats(tr_fold,  ref=tr_fold)   # 学習データから計算
val_fold = add_store_stats(val_fold, ref=tr_fold)   # 同じ統計量をバリデーションに適用
test     = add_store_stats(test,     ref=train_open) # テストには全学習データを使用
```

### v2 → v3: ラグ特徴量（失敗から学ぶ）

#### 何をしたか

「1年前の同じ日の売上」を特徴量として追加しようとした（364/365日ラグ）。

#### なぜ失敗したか

```
学習データ開始: 2013-01-01
ラグ364日の最初の有効日: 2014-01-01

→ 2013年のデータ（全体の約42%）はラグ値が NaN になる
→ 学習 / バリデーション / テストで NaN の割合が大きく異なる
  学習期間: NaN 41.9%
  バリデーション: NaN 12.5%
  テスト期間: NaN 21.0%

→ NaN を store_mean で補完しても、補完の意味が場所によって異なる
→ モデルが誤ったパターンを学習してしまう
```

**教訓**: ラグ特徴量は、**全ての期間で同様の欠損率になる**ことを確認してから使う。

### v3 → v4: Optuna によるハイパーパラメータ最適化

#### 何をしたか

LightGBM のパラメータ（学習率・葉の数・正則化など）を **Optuna（ベイズ最適化）** で自動探索した。

```python
# 探索したパラメータ例
learning_rate    : 0.01 〜 0.1   （対数スケール）
num_leaves       : 63  〜 511
min_child_samples: 10  〜 200
lambda_l2        : 0.001 〜 10   （過学習防止の正則化）
max_depth        : 4   〜 12
```

#### Optuna の仕組み（ベイズ最適化）

```
グリッドサーチ（従来）: 全組み合わせを試す → 指数的に時間がかかる
ランダムサーチ: ランダムに試す → 効率が悪い

Optuna（ベイズ最適化）:
  1. 最初の数 trial はランダムに試す
  2. 「このパラメータで良かった」という結果を学習
  3. 良さそうな領域を重点的に探索
  → 限られた trial 数で効率よく最適解に近づける
```

#### 重要な問題と解決

Optuna 実行時に発生したエラー:

```
LightGBMError: Reducing min_data_in_leaf with feature_pre_filter=true may cause unexpected behaviour
```

**原因**: lgb.Dataset をキャッシュしている状態で `min_child_samples` が変わると内部で矛盾が生じる。  
**解決**: パラメータに `"feature_pre_filter": False` を追加する。

### v4 → v6: Entity Embedding Neural Network（詳細は第4章）

ハイスコアノートブックの最大の差別化要素を参考に実装。  
カテゴリ変数（Store ID など）を **低次元の意味ある数値ベクトル** に変換し、LightGBM の特徴量として注入した。

#### 実装で学んだ教訓: CV/LB 乖離の問題

| バージョン | NN の学習方法 | valid RMSPE | Kaggle LB | CV/LB 乖離 |
|---|---|---|---|---|
| v6 旧（2ステップ）| CV 用と最終用で別々に学習 | 0.13241 | 0.11411 | 0.0183 |
| v6 案A | train_open 全体で1回だけ学習 | 0.11786 | 0.11575 | 0.0021 |
| v6 案A + Store50 | Store 埋め込み 10→50 次元 | 0.11778 | 0.11490 | 0.0029 |

**v6 旧の問題**: 時系列分割を使ったため、CV 用 NN が Epoch 1 で早期停止（ほぼランダムな埋め込み）。  
最終提出用の NN は 30 epoch フル学習 → CV と最終提出で埋め込みの品質が全く異なった。

**案A の改善**: train_open 全データで NN を 1 回学習 → 同じ高品質な埋め込みを全データに適用。

### v6 → v7: XGBoost アンサンブル

LightGBM と XGBoost を 0.5:0.5 でブレンドした。

#### アンサンブルの原理

```
なぜアンサンブルでスコアが上がるか？

LightGBM と XGBoost は:
  - 異なるアルゴリズムの実装（ヒストグラム法 vs 厳密な分割探索）
  - 異なる正則化の方法
  → 異なる誤りを犯す

0.5 × LGB予測 + 0.5 × XGB予測
→ 一方が大きく外れてももう一方が補正する
→ 単体より安定した予測になる
```

#### v7 の結果と考察

- valid RMSPE: 0.11474（改善）
- Kaggle LB: 0.11535（v6 より悪化）

**原因**: XGBoost のパラメータが未調整（LightGBM は Optuna 最適化済み）。  
パラメータ差がある 2 モデルを均等ブレンドすると、弱い側がノイズになる可能性がある。  
→ **アンサンブルの効果を最大化するには、各モデルを同等の精度まで調整することが重要**。

### ハイスコアノートブック（Kaggle LB: 0.10021）の手法一覧

#### アーキテクチャ全体

```
ハイスコアノートブック:

      ↓

      ↓

我々のモデル（v7）:
  Neural Network（Entity Embedding 学習用）
      ↓ 埋め込みベクトルを抽出
  LightGBM（埋め込み + 特徴量で学習）
      +
  XGBoost（埋め込み + 特徴量で学習）
      ↓
  0.5:0.5 アンサンブル → 提出
```

### ハイスコアが出る理由1: 外部データの活用

#### Google Trends データ

```python
state_trend : 各州で「Rossmann」が検索された頻度（週次）
DE_trend    : ドイツ全国の「Rossmann」検索頻度（週次）
```

**なぜ有効か？**  
Rossmann のブランド認知が高まる週（新聞広告・TV CM など）は来店者が増える。  
この「プロモーション効果の波及」を Google 検索数が間接的に表している。

#### 気象データ（州別・日次）

```python
Max/Mean/Min_TemperatureC  : 気温
Max/Mean/Min_Humidity      : 湿度
Max_Wind_SpeedKm_h         : 最高風速
CloudCover                 : 雲量
Events                     : 天気イベント（雨・霧・雷など）
```

**なぜ有効か？**  
天気は来店動機に直接影響する。  
特に薬局（Rossmann）は「急に雨が降った→帰宅ついでに立ち寄る」などの行動変化がある。

#### 州マッピング

ドイツは州によって **祝日の日程が異なる**（バイエルン州の祝日 ≠ ベルリンの祝日）。  
店舗が属する州を特定することで、祝日の影響を正確にモデリングできる。

### ハイスコアが出る理由2: 精密な特徴量設計

#### `latest_promo2_months`（累積ではなくサイクル位置）

```python
# 我々のアプローチ（累積経過週数）
Promo2OpenWeeks = 52 * (Year - Promo2SinceYear) + (WeekOfYear - Promo2SinceWeek)
# 例: Promo2 開始から 300 週目  → 300（単調増加）

# ハイスコアのアプローチ（現サイクルの何ヶ月目か）
latest_promo2_months = (今月 - 今のサイクル開始月) % サイクル長
# 例: Promo2 が「Jan, Apr, Jul, Oct」なら 3ヶ月サイクル
#     4月（新サイクル開始）→ 0、5月 → 1、6月 → 2、7月（新サイクル）→ 0
```

**なぜ有効か？**  
Promo2 は毎年繰り返すサイクルイベント。  
「開始から何週経ったか」は際限なく増加するため、モデルが季節性を学びにくい。  
「今のサイクルで何ヶ月目か」は毎年同じパターンを繰り返すため、汎化しやすい。

#### `hasCompetitionmonths`（競合影響の飽和）

```python
# 我々のアプローチ（上限なし）
CompetitionOpen = 12 * (Year - CompetitionOpenSinceYear) + (Month - CompetitionOpenSinceMonth)
# 例: 100ヶ月前に競合がオープン → 100（無制限）

# ハイスコアのアプローチ（24ヶ月で飽和）
hasCompetitionmonths = min(24, CompetitionOpen)
# 例: 100ヶ月前に競合がオープン → 24（頭打ち）
```

**なぜ有効か？**  
競合店の影響は最初は大きいが、やがて市場が安定する（飽和する）。  
24ヶ月以上経過した競合店は「すでに安定した脅威」として同等に扱うべき。  
これはビジネス知識をモデルに組み込む良い例。

---

### ハイスコアが出る理由3: バリデーション戦略

ハイスコアノートブックは **バリデーションを使わず** に提出している。

```python
# ハイスコアノートブックのアプローチ
num_round = 2528   # XGBoost（事前に early stopping で決定済み）
num_iterations = 15148  # LightGBM（事前に early stopping で決定済み）

# 全学習データを使って最終モデルを学習 → ラウンド数はハードコーディング
```

**なぜこれで機能するか？**  
1. 事前に別の実験でバリデーションによって最適ラウンド数を特定済み
2. 最終提出時は全データで学習することでモデルの精度が向上する

**リスクと注意点**:  
バリデーションがないため過学習の検出が難しい。  
我々の時系列 Hold-out CV は理論的に正しいアプローチで、信頼できる評価が可能。

## 4. Entity Embedding Neural Network 詳解

### 4-1. そもそも Neural Network（ニューラルネットワーク）とは

#### 生物の脳を模倣した計算モデル

人間の脳には約 860 億個のニューロン（神経細胞）がある。  
各ニューロンは複数の信号を受け取り、処理して次のニューロンに伝える。  
Neural Network はこの仕組みを数式で表現したもの。

```
生物のニューロン:
  樹状突起（入力）→ 細胞体（処理）→ 軸索（出力）→ 次のニューロンへ

数式のニューロン（パーセプトロン）:
  入力 x1, x2, x3
      ↓ 重み w1, w2, w3 をかける
  合計 z = w1*x1 + w2*x2 + w3*x3 + b（バイアス）
      ↓ 活性化関数（例: ReLU）を通す
  出力 y = max(0, z)
```

#### 層を重ねることで複雑なパターンを学習

```
入力層     隠れ層1    隠れ層2    出力層
x1 ─┐                          ┌─ 売上予測
x2 ─┼→ [ニューロン群] → [ニューロン群] ─┤
x3 ─┘                          └─（単一値）
```

- **入力層**: 特徴量（気温・曜日・プロモフラグなど）
- **隠れ層**: 中間的な特徴を自動的に学習
- **出力層**: 予測値

「学習」とは、予測値と正解の差（損失）が小さくなるように **重み w を調整していく**プロセス。  
これを **誤差逆伝播法（バックプロパゲーション）** で行う。

---

### 4-2. Embedding（埋め込み）の概念

#### カテゴリ変数の問題

機械学習では数値を扱う。「店舗タイプ: A, B, C, D」のようなカテゴリ変数は数値に変換が必要。

```
通常の方法1: One-Hot Encoding
  A → [1, 0, 0, 0]
  B → [0, 1, 0, 0]
  C → [0, 0, 1, 0]
  D → [0, 0, 0, 1]
  問題: 次元数が増大（1115 店舗 → 1115 次元）

通常の方法2: Label Encoding（ラベル番号）
  A → 0, B → 1, C → 2, D → 3
  問題: 「A と B は数値が近い」という誤った意味が生まれる
```

#### Embedding の解決策

カテゴリ変数を **低次元の連続値ベクトル** に変換する。

```
Store 1   → [0.12, -0.34, 0.87, 0.55, ...]  ← 10次元ベクトル
Store 2   → [0.44,  0.21, 0.12, -0.33, ...]
Store 817 → [0.11, -0.38, 0.91,  0.52, ...]  ← Store 1 と似ている！
```

このベクトルの **距離・方向が意味を持つ**。  
ベクトルが近い店舗 = 売上パターンが似ている店舗、という構造を NN が自動的に学習する。

---

### 4-3. Entity Embedding Neural Network の仕組み

#### アーキテクチャ

```
入力カテゴリ変数:
  Store ID（1115 種）  → [Embedding 層 10次元] → 10次元ベクトル ┐
  DayOfWeek（7 種）    → [Embedding 層  4次元] →  4次元ベクトル │
  Month（12 種）       → [Embedding 層  6次元] →  6次元ベクトル ├─ 結合
  StoreType（4 種）    → [Embedding 層  2次元] →  2次元ベクトル │
  ...（合計 13 カテゴリ）                                        ┘
                                                                  ↓
連続変数:                                                  [Dense 512]
  CompetitionDistance ─────────────────────────────────────     ↓
  store_mean           ─────────────────────────────────────[Dense 256]
  ...（合計 12 変数）                                             ↓
                                                           [Dense 128]
                                                                  ↓
                                                         予測: log(Sales)
```

#### 学習フェーズ

```
1. ランダムに初期化された埋め込みベクトル
2. log(Sales) を予測する
3. 予測誤差（損失）を計算
4. バックプロパゲーションで誤差を逆伝播
5. 埋め込みベクトルの値を更新
    → 「Store 1 は Store 817 に似ている」という情報が埋め込みに刻まれる
6. 1000 万件のデータを何度も繰り返し学習
```

#### 埋め込みの抽出と再利用

```python
# NN が学習した埋め込み重みを取り出す
store_weights = model.get_layer("emb_Store").get_weights()[0]
# shape: (1115, 50) ← 1115店舗 × 50次元

# これを LightGBM の特徴量として追加
# Store 1 → 50次元の特徴量が50列追加される
train = train.merge(store_embedding_df, on="Store", how="left")
```

### 4-4. なぜ Entity Embedding でスコアが上がるのか

#### 理由1: 類似店舗からの情報補完

```
例: Store 562（学習データが少ない店舗）

通常の LightGBM:
  Store 562 のデータが少ない
  → この店舗の予測精度が低い

Entity Embedding あり:
  NN が「Store 562 は Store 88 と Store 341 に似ている」と学習
  → Store 562 の埋め込みベクトル ≈ Store 88 の埋め込みベクトル
  → LightGBM は類似店舗の知識を使って Store 562 を予測できる
```

#### 理由2: カテゴリ間の複雑な関係を表現

```
通常: Store ID = 562（ただの番号）

Embedding: [0.34, -0.21, 0.87, ...]（意味のある方向を持つベクトル）
  次元0: 売上規模（大 → 正方向）
  次元1: 都市/郊外（都市 → 負方向）
  次元2: プロモ感応度（高感応 → 正方向）
  ...
```

NN が自動的に「どの方向に意味があるか」を発見する。  
人間が手動で設計できない複雑な関係を捉えられる。

#### 理由3: 次元削減と情報圧縮

```
1115 店舗の One-Hot: 1115次元（スパース・ノイズが多い）
1115 店舗の Embedding: 50次元（密・意味が圧縮されている）
```

次元が小さい方が LightGBM は効率よく学習できる。

---

### 4-5. 今回の実装で学んだこと

#### 問題1: CV 用 NN が Epoch 1 で停止した（v6 旧の失敗）

```
原因:
  NN を「tr_fold（過去）→ val_fold（未来6週）」で検証
  → 時系列データで未来を予測するのは難しい
  → val_loss が Epoch 1 から悪化 → 即座に早期停止

結果:
  CV 用 NN の埋め込み = ほぼランダム
  最終提出用 NN の埋め込み = フル学習済み
  → CV スコアと LB スコアが全く一致しない（乖離 0.018）
```

#### 解決策（案A）: 全データで1回学習

```
train_open 全データで NN を学習（検証データなし、train loss を監視）
    ↓
同じ埋め込みを tr_fold / val_fold / test 全てに適用
    ↓
LightGBM の CV が実態を反映するようになる（乖離 0.002 に縮小）
```

#### 問題2: Store 埋め込みが特徴量重要度に現れない

```
原因:
  store_promo_mean / store_dow_mean / store_mean が
  すでに Store の個性を「売上の単位」で直接表現している
  → Store 埋め込み（抽象ベクトル）の追加価値が薄い

教訓:
  Entity Embedding が最も効果的なのは、
  「明示的な統計量がなく、Store ID だけが頼り」の状況
  我々のモデルは統計量が強力すぎて Embedding の出番が少なかった
```

## 5. 次のコンペティションへの活かし方

### 初期段階でやること

```
1. データを理解する（EDA）
   - 目的変数の分布を確認（log 変換が必要か？）
   - 欠損値の分布を確認
   - 時系列データかどうかを確認（→ CV 戦略が変わる）

2. バリデーション戦略を最初に決める
   - 時系列: Hold-out（テスト期間と同じ長さで直近を使用）
   - 非時系列: Stratified K-Fold など

3. ベースラインを素早く作る
   - 最小限の特徴量で動かす
   - CV スコアと LB スコアの乖離を確認する
```

### ハイスコアノートブックの読み方

Kaggle では他の参加者のノートブックを参照できる。  
**ハイスコアノートブックを読む際のチェックポイント**:

```
□ 使用しているモデルは何か（LightGBM / XGBoost / NN / アンサンブル）
□ 外部データを使っているか（どんなデータか・なぜ有効か）
□ 特徴量設計に独自の工夫があるか（ビジネス知識を活かしているか）
□ バリデーション戦略はどうなっているか
□ 目的変数や損失関数に工夫があるか
□ アンサンブルの方法と重みはどうなっているか
```

### 特徴量エンジニアリングの鉄則

| 鉄則 | 説明 |
|---|---|
| リークを防ぐ | バリデーション・テストの情報を学習に使わない |
| ビジネス知識を使う | 「なぜこの変数が有効か」を考える |
| 飽和・上限を考える | 影響が無限に続くとは限らない（例: 競合24ヶ月上限） |
| サイクルを考える | 累積量より「周期の何番目か」が重要な場合がある |
| 外部データを探す | 公式データ以外の関連データがないか検討する |

### Entity Embedding を使うべき状況

```
✅ 使うと効果的な状況:
  - カテゴリの種類が多い（100種以上）
  - カテゴリ間の類似度を学習させたい
  - 明示的な統計量が作りにくい（データが少ない）
  - NN 自体も予測に使う（NN + GBDT のアンサンブル）

⚠️ 効果が限定的な状況:
  - 強力な統計量が既にある（我々の場合）
  - カテゴリの種類が少ない（数種類程度）
  - データ量が非常に少ない（NN の学習が収束しない）
```

### モデル改善のチェックリスト

```
□ EDA で有効な特徴量の仮説を立てた
□ ベースラインを作り、CV と LB の乖離を確認した
□ 店舗・ユーザーなどのエンティティ統計量を追加した
□ 時系列リークがないか確認した
□ Optuna などでハイパーパラメータを最適化した
□ 特徴量重要度を確認し、不要な特徴量を削除した
□ ハイスコアノートブックを参照して手法の差異を分析した
□ 外部データの追加を検討した
□ アンサンブルを試みた（各モデルを十分に調整した上で）
□ CV スコアと LB スコアの傾向が一致しているか確認した
```
