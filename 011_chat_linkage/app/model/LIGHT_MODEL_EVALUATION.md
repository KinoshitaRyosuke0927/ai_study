# アジェンダ作成ツールのモデル検証

アジェンダ作成ツールでは、チャット投稿が「リマインドが必要そうな内容か」をファインチューニングした日本語BERTで判定している。

BERTは精度が期待できる一方で、実際にツールをexe化し、zip形式で配布して使用することを考えると以下のような負担がある。

- モデルのサイズが大きい(約425MB)
- 推論に `torch`・`transformers` といった大きなライブラリが必要
- GPUのない環境では推論に時間がかかる

そこで現在使用しているBERT以外の**より軽量なモデル**(ナイーブベイズ、ロジスティック回帰、線形SVMなどの古典的な機械学習手法)について、判定タスクにおける精度とツールへの組み込みやすさの観点から、適したモデルはないのか比較検討した。

あわせて付録として、「リマインド対象の投稿に含まれている単語の特徴」についても調べた。

---

## 結論

- **軽量モデルでもBERTに近い精度が得られる見込みが高い。**
  - 最も良かったのはTF-IDF(文字n-gram)+ ロジスティック回帰で、BERTとの間に統計的に有意な差は見られなかった(PR-AUC 0.89 vs 0.88)。ただし同等であることの証明ではない(2.6.1参照)
  - モデルのサイズは425MB→0.3MB、推論時間はBERTの約1/100〜1/450(1件ずつ〜100件まとめて)になる
- **ナイーブベイズは軽量だが、精度は一段低い**(PR-AUC 0.83〜0.84)
- **軽量モデルに切り替える場合は、しきい値の見直しが必要**(現行の0.9から0.5前後へ。2.8参照)
- **発展研究(4章)**: リマインド対象の投稿に偏って出現する語はある。ただし中心は「締切」「提出」より、`@channel`・`【】`・`ください` など**全体向けのお知らせの書き方**。どれか1語で判定が決まる語はなく、キーワード一致だけのルールでは精度が大きく下がる(PR-AUC 0.53〜0.81)

---

## 1. 前提条件

### 1.1 判定タスク

- **入力**: Mattermostの投稿本文1件
- **出力**: リマインドが必要な内容(締め切り・提出物・注意喚起など)である確率(0〜1)
- アプリでは、この確率が**しきい値以上**の投稿だけを、リマインド・アジェンダ作成の対象にしています

### 1.2 データ

| 項目 | 内容 |
|---|---|
| 取得元 | リマインド対象になりうる、社内Mattermostの実際の投稿を人手で 0(不要)/ 1(必要)にラベル付けしたもの |
| 件数 | 1,369件 |
| 内訳 | 1(必要)が312件、0(不要)が1,057件 |
| 投稿の長さ | 平均 約440文字 |

> **注**: 実際に取得したデータはリマインド対象の投稿が全体の約2割という**不均衡なデータ**であった。そのため、単純な正解率ではなく重みづけした指標で評価している。

### 1.3 比較対象の現行モデル(BERT)の学習方法

今回の比較元は、現在ツールで使っている判定モデルとした。

#### ベースモデルと構造

- **ベースモデル**: [`cl-tohoku/bert-base-japanese-v3`](https://huggingface.co/cl-tohoku/bert-base-japanese-v3)
  東北大学が公開している、日本語Wikipediaなどで事前学習済みの日本語BERT。12層、隠れ層768次元
- 事前学習済みのBERTは、文章を意味のベクトルに変換する能力しか持たない。そこで、文全体を表すベクトル(`[CLS]`トークンの出力、768次元)の後ろに**2クラス分類用の層(Dropout → 全結合層 768→2)** を追加した。この層だけはランダムな初期値から、本タスク用に学習する
- 出力された2つのスコアをsoftmax関数で確率に変換し、「必要(クラス1)」側の確率をアプリでの判定に使用する

```
投稿テキスト → トークン分割(最大256トークン) → BERT本体(12層、事前学習済み)
  → [CLS]ベクトル(768次元) → Dropout → 全結合層(768→2、新規追加) → softmax → 「必要」の確率
```

#### 学習データ

- 1.2のデータ(1,369件)を使用する
- 「必要」の比率を保ったまま、**学習用85%(1,163件、うち必要265件)/ 検証用15%(206件、うち必要47件)** に分割する
- 今回のデータでは投稿の中央値が67トークンで、256トークンを超える投稿が全体の約13%であった
- 投稿はBERT用のトークナイザで分割し、学習にかける時間の観点から**256トークンを超える部分は切り捨てた**

#### 学習方法と条件

- **フルファインチューニング**: 追加した分類層だけでなく、BERT本体を含むすべての重みを更新した
- **不均衡への対応**: 誤差の計算(交差エントロピー損失)で「必要」クラスの重みを **不要の件数 ÷ 必要の件数 ≒ 3.39倍** にした

| 項目 | 値 |
|---|---|
| 学習の繰り返し回数(エポック数) | 5 |
| バッチサイズ | 8 |
| 学習率 | 2e-5(事前学習済みの重みを壊さないよう小さめ) |
| 最適化手法 | AdamW(Hugging Face `Trainer` の既定。学習率は線形に減衰) |
| モデルの選び方 | 各エポック終了時に検証用206件でF1(確率0.5を境に判定)を計算し、**F1が最も高かったエポックのモデルを採用** |
| 乱数シード | 42 |

#### その他

- 学習済みモデルのサイズは約425MB。推論には `torch` と `transformers` が必要
- 今回の確認では、このモデルの学習用1,163件でのPR-AUCは0.997、検証用206件では0.881であった

### 1.4 実行環境

- Windows 10 / Python 3.12 / scikit-learn 1.8 / CPUのみ(GPUなし)
- 推論時間などの動作面の計測値はすべてこの環境でのものです

### 1.5 評価指標

| 指標 | 意味 | 使う理由 |
|---|---|---|
| **PR-AUC** | しきい値を0〜1で動かしたときの、適合率と再現率のバランスを1つの値にまとめたもの(1.0が最良) | 不均衡データで「必要」な投稿をどれだけ上位に並べられるかを、しきい値によらず比べられる。**今回の主指標** |
| 最良F1 | しきい値を最適に選んだときのF1(適合率と再現率の調和平均) | しきい値を調整した場合に到達できる性能の目安 |
| 適合率80%時の再現率 | 「拾った投稿の8割以上が本当に必要」を保ったまま、必要な投稿を何割拾えるか | 実運用(誤検知を抑えたい)に近い観点 |
| Brierスコア | 出力確率と実際のラベルのずれ(小さいほど良い) | 確率の値そのものが信用できるか(しきい値の意味が保たれるか)を見る |

## 2. 軽量モデルの比較

### 2.1 比較したモデル

テキストをTF-IDFで数値ベクトルにしてから分類器にかける、古典的な機械学習の手法と比較した。

**特徴量(日本語テキストの区切り方)**

| 名前 | 内容 |
|---|---|
| 文字n-gram | 連続する数文字ずつ(例: 「お願い」→「お願」「願い」)を1単位とする。形態素解析が不要 |
| 単語n-gram | 形態素解析器 fugashi(MeCab)で単語に分割し、1〜数単語ずつを1単位とする |

**分類器**

| 名前 | 特徴 |
|---|---|
| MultinomialNB | ナイーブベイズ。最も軽量 |
| ComplementNB | 不均衡データ向けに改良されたナイーブベイズ |
| ロジスティック回帰 | 単語ごとの重みを足し合わせて確率を出す線形モデル |
| 線形SVM | テキスト分類で精度が高いことの多い線形モデル。確率はシグモイド関数で補正して出力 |

> **注**: クラスの不均衡への対応として、ロジスティック回帰と線形SVMでは少数派(必要)の重みを大きくした。

### 2.2 前処理: メンションの正規化

実際に学習を行うと、モデルが**特定の個人へのメンション**(`@個人名`)を判定の強い手がかりにしていることがわかった。
これは人が入れ替わると通用しない情報であるため、投稿に対して以下の置き換えを適用した条件でも比較した。

| 置き換え前 | 置き換え後 | 理由 |
|---|---|---|
| `@個人名` | `@USER` | 特定の人物に依存させない |
| `@channel` / `@here` / `@all` | そのまま | 「全員宛て」は内容の性質を表すため残す |
| URL | `URL` | URL中の英数字を特徴として拾わせない |

### 2.3 パラメータ調整

各モデルについて以下の候補値を総当たりで試し、最も良い組み合わせを選択した。

| 対象 | 候補 |
|---|---|
| n-gramの範囲 | 文字: 1〜3 / 2〜3 / 2〜4文字、単語: 1 / 1〜2 / 1〜3単語 |
| 何件以上の投稿に出る語を使うか | 1 / 2 / 3件以上 |
| ナイーブベイズの平滑化の強さ | 0.01 〜 1.0 |
| ロジスティック回帰・SVMの正則化の強さ(C) | 0.03 〜 100 |

### 2.4 評価のしかた

評価は以下の2通りで行った。

**(a) 層化5分割交差検証(今回検証する軽量モデルのみを対象)**

```
全1,369件を、「必要」の比率を保って5つに分割
 ├─ 1つを評価用、残り4つを学習用にして学習 → 評価用を予測
 └─ これを5回繰り返し、全件について「自分を学習に使っていないモデルの予測」を得て指標を算出
```

- パラメータ調整は、各回の学習用データの中だけでさらに3分割して**入れ子交差検証**により行った
- 次の3条件で比較を行った: 「前処理なし・固定パラメータ」「正規化あり・固定パラメータ」「正規化あり・パラメータ調整あり」

**(b) ホールドアウト評価(軽量モデルとBERTとの直接比較)**

- 現在のツールとの比較であるという点から、BERTについては**既存のBERTモデルをそのまま使って比較**した
- 軽量モデルについても、BERTの学習時と同じ分割(検証用15% = 206件、うち「必要」47件)で学習・評価した
- 差が偶然の範囲かどうかは、ブートストラップ法で「PR-AUCの差」の95%信頼区間を求めて確認した

> **注**: この検証用の206件はBERTの学習時に「最も良いエポックを選ぶ」ために使用したデータであるため、BERTの値はやや有利に出ている可能性がある

### 2.5 結果: 交差検証(PR-AUC)

| モデル | 前処理なし | 正規化あり | 正規化 + 調整 | 適合率80%時の再現率 ※ | 最良F1 ※ |
|---|---|---|---|---|---|
| **文字 + ロジスティック回帰** | 0.877 | 0.886 | **0.894** | **0.833** | **0.825** |
| 文字 + 線形SVM | 0.873 | 0.883 | 0.893 | 0.833 | 0.821 |
| 単語 + ロジスティック回帰 | 0.881 | 0.893 | 0.877 | 0.798 | 0.818 |
| 単語 + 線形SVM | 0.881 | 0.893 | 0.890 | 0.817 | 0.812 |
| 文字 + MultinomialNB | 0.821 | 0.833 | 0.839 | 0.737 | 0.771 |
| 文字 + ComplementNB | 0.786 | 0.807 | 0.839 | 0.737 | 0.771 |
| 単語 + MultinomialNB | 0.827 | 0.839 | 0.834 | 0.705 | 0.772 |
| 単語 + ComplementNB | 0.801 | 0.824 | 0.834 | 0.705 | 0.772 |

※ 「正規化 + 調整」条件での値

**読み取れること**

- **メンションの正規化は、全モデルで +0.01〜0.02 の効果があった。** 個人に依存しない形にしても精度は落ちず、むしろ上がっている
- **パラメータ調整の効果が表れたのは文字n-gram系。** 文字系では「1〜3文字、3件以上の投稿に出る語」という設定が5回中ほぼ毎回選ばれ、安定していた。単語系は選ばれる設定が回ごとにばらつき、調整しない方がむしろ良い結果となった。データ量が少ないため、調整が偶然のばらつきに引っ張られたと考えられる
- **ナイーブベイズは、調整してもロジスティック回帰・SVMより約0.05低い**結果であった。また出力確率が0か1に偏りやすく、Brierスコアも悪化した(0.09〜0.14、ロジスティック回帰は約0.07)

### 2.6 結果: BERTとの比較(ホールドアウト206件)

| モデル | PR-AUC | 最良F1 | 適合率80%時の再現率 | BERTとのPR-AUC差の95%信頼区間 |
|---|---|---|---|---|
| BERT(既存) | 0.881 | 0.843 | 0.830 | — |
| 文字 + ロジスティック回帰 | 0.876 | 0.804 | 0.766 | [−0.071, +0.060] |
| 文字 + MultinomialNB | 0.867 | 0.826 | 0.809 | [−0.086, +0.056] |
| 文字 + 線形SVM | 0.866 | 0.800 | 0.766 | [−0.080, +0.045] |
| 単語 + ロジスティック回帰 | 0.856 | 0.784 | 0.681 | [−0.085, +0.034] |

- **すべての軽量モデルで信頼区間が0をまたいでおり、BERTとの差は統計的に確認できなかった**
- 検証用の「必要」な投稿が47件と少なく、結果のブレが大きいと考えられる。そのため、**モデル同士の比較は(a)の交差検証の結果を主な根拠**としている

**BERTとのPR-AUC差の95%信頼区間からわかること**

- 区間が0を含むため、この206件のデータからは「BERTの方が良い」とも「軽量モデルの方が良い」とも言えない
- 実際の精度の差が区間の幅より小さい可能性は否定できないため、「両者の精度が同等である」ことも言えない

### 2.7 結果: 動作面(同じ206件の検証データで計測)

| 項目 | BERT(既存) | 文字 + ロジスティック回帰 |
|---|---|---|
| モデルのファイルサイズ | 約425MB | **約0.3MB** |
| 100件まとめて推論 | 約13.6秒 | **約0.03秒** |
| 1件の推論 | 約81ms | **約0.7ms** |
| 学習時間 | (GPUなしでは長時間) | 1秒未満 |
| 必要なライブラリ | torch, transformers(数GB規模) | scikit-learn(既に利用中) |

上記結果から、ツールに組み込むことで以下の改善が見込めそうである

- exe配布版のサイズが大幅に小さくなる
- 起動直後の待ち時間とメモリ使用量が減る

### 2.8 しきい値について

BERTは確率を0か1の極端な値で出す傾向があることがわかった。そのため、しきい値0.9でも「必要」な投稿の87%を拾えている。一方、ロジスティック回帰はBERTと比べて確率を控えめに出していたため、しきい値0.9のままだと再現率が30〜40%程度まで下がってしまう。
そのため、軽量モデルに切り替える場合は、しきい値を0.5前後に設定し直す必要がある。

## 3. 課題

- **データ量が少ない**: 学習データの「必要」な投稿は312件であるため、モデルの性能に差があるかは判断できない
- **BERTは交差検証で評価していない**: BERTはホールドアウト1回分のみの結果で比較しているため、厳密に比べるには再学習が必要

## 4. 付録: リマインド対象の投稿に特定の単語は含まれているか

本章はモデル比較とは別に、リマインド対象の投稿に含まれる語句に関する調査として調べた。

### 4.1 調査方法

次の3段階で調べた。いずれもメンションを正規化した後のテキストを使用している。

1. **単語ごとの偏りの集計**: 各単語について次の値を算出した
   - 「必要」な投稿のうち何割に含まれるか(カバー率)
   - 「不要」な投稿のうち何割に含まれるか
   - その語を含む投稿のうち何割が「必要」か(適合率)

   偏りの強さは、2×2の分割表(含む/含まない × 必要/不要)から計算したオッズ比のz値で順位付けした。偶然の偏りを避けるため、10件以上の投稿に出る語に限っている
2. **人手のキーワード辞書による判定**: データを見る前に、直感的に選んだ21語(締切・期限・期日・までに・提出・回答・申請・お願いします・各自・必ず・忘れず・ご確認・注意 など)を用意した。「1語でも含めば必要」と判定した場合の精度を測定した
3. **データから選んだキーワードによる判定**: 学習用データで「必要」側に最も偏っている上位K語(K = 5〜100)を選び、評価用データでは含まれるキーワードの数をスコアにして判定した。キーワードを選ぶのに評価用データを使わないよう、2.4(a)と同じ層化5分割交差検証で、分割ごとに選び直している

### 4.2 結果: 「必要」側・「不要」側に偏っている語

| 語 | 必要な投稿での出現率 | 不要な投稿での出現率 | その語を含む投稿が「必要」である割合 |
|---|---|---|---|
| `@channel` | **81%** | 24% | 50% |
| お願い | 66% | 25% | 43% |
| 見出し記号 `##` | 54% | 16% | 50% |
| ください | 49% | 12% | 56% |
| `【` `】` | 31% | 1% | **88%** |
| までに | 14% | 2% | 69% |
| 各自 | 11% | 0.3% | **92%** |
| 期限 | 9% | 0.6% | 83% |
| 提出 | 6% | 0.9% | 67% |
| 締切 | 1.6%(5件) | 0.1% | 83% |
| 個人宛てメンション `@USER` | 14% | **46%** | 8%(「不要」側の手がかり) |

**読み取れること**

- 最も強い手がかりは、`@channel`・`【】`・見出しの `##`・`ください`・`お願い` といった**全体向けのお知らせの書き方**であった
- 「各自」「期限」「締切」などの語は、**含まれていればかなり高い確率で「必要」だが、使われる投稿自体が少ない**語だった。例えば「締切」は1,369件中わずか6件
- 逆に、個人宛てのメンションがある投稿(個別のやり取り)は「不要」側に強く偏っていた

### 4.3 結果: キーワード一致だけで判定した場合の精度

| 判定方法 | PR-AUC | 適合率80%時の再現率 | 備考 |
|---|---|---|---|
| 人手辞書(21語)に1語でも該当 | 0.53 | 0.20 | 「必要」の89%を拾えるが、該当した投稿の63%は「不要」 |
| データから選んだ上位10語の該当数 | 0.71 | 0.53 | 交差検証 |
| データから選んだ上位50語の該当数 | **0.81** | **0.60** | 交差検証。キーワード方式で最良 |
| (参考)文字 + ロジスティック回帰 | 0.89 | 0.83 | 交差検証 |

- 人手辞書の判定で誤検知が多いのは、「お願いします」「実施」「対応」などが普段の業務連絡でも頻繁に使われるためと考えられる

### 4.4 まとめ: リマインド対象かどうかに強く影響している語

4.2の集計結果(`keyword_stats_*.csv`)をもとに、判定に強く影響している語を性質ごとに整理すると以下のようになった。
表の数値は「必要な投稿での出現率 / 不要な投稿での出現率 / その語を含む投稿が必要である割合」を表している。

#### 「必要」側に強く影響している語

| 分類 | 代表的な語 | 傾向 |
|---|---|---|
| **全体宛て・告知の形式** | `@channel`(81% / 24% / 50%)、`【` `】`(31% / 1% / 88%)、見出し `##`(54% / 16% / 50%) | 最も影響が大きいグループ。全員に向けて、見出しや隅付き括弧で整えて書かれた「お知らせ」の形式そのものが手がかりになっている |
| **依頼・丁寧な表現** | `ください`(49% / 12% / 56%)、`お願い`(66% / 25% / 43%)、`ご`(52% / 16% / 50%)、`様`(31% / 9% / 50%) | 「必要」な投稿の半数以上に含まれ、カバー範囲が広い。ただし普段の業務連絡にも出るため、単独では決め手にならない |
| **対象者への呼びかけ** | `各位`(10% / 0.1% / 97%)、`各自`(11% / 0.3% / 92%)、`皆`(14% / 1% / 76%)、`メンバー`(11% / 1% / 69%)、`社員`(14% / 3% / 63%) | 含まれていれば、ほぼ確実に「必要」。出現は1〜2割程度 |
| **案内・説明の定型表現** | `案内`(10% / 1% / 78%)、`メール`(11% / 1% / 79%)、`協力`(12% / 2% / 67%)、`内容`(13% / 2% / 66%)、`以下`(34% / 10% / 52%) | 「以下のとおりご案内します」「ご協力をお願いします」といった、告知文の定型的な言い回し |
| **期限・提出** | `期限`(9% / 0.6% / 83%)、`期日`(5% / 0.4% / 81%)、`締切`(2% / 0.1% / 83%)、`までに`(14% / 2% / 69%)、`提出`(6% / 1% / 67%) | 含まれていれば高い確率で「必要」。ただし**使われる投稿自体が少なく**、「必要」な投稿の大半はこれらの語を含まない |
| **日付表現** | `月`(36% / 12% / 46%)、`木`(13% / 2% / 64%)、`金`(14% / 3% / 58%) | 「10月15日(木)」のような日付・曜日の表記と考えられる。期日を示す投稿に現れやすい |

#### 「不要」側に強く影響している語

| 分類 | 代表的な語 | 傾向 |
|---|---|---|
| **個人宛てのメンション** | `@USER`(14% / 46% / 8%) | 最も影響が大きい。特定の個人に向けたやり取りは、リマインド対象になりにくい |
| **質問・会話** | `？`(4% / 9% / 12%) | 疑問形の投稿は、問い合わせや会話であることが多い |
| **状況報告** | `更新`(4% / 11% / 9%)、`状況`(6% / 13% / 12%) | 作業や状況の報告は「不要」側に偏る |
| **一部の全体宛てメンション** | `@here`(2% / 5% / 9%) | 同じ全体宛てでも `@channel` とは逆の傾向。その場にいる人への一時的な連絡に使われやすいためと考えられる |

#### 全体として言えること

1. **最も強い手がかりは個々の単語より「書き方」**
   `@channel`・`【】`・見出し・`各位` のような**全体向けのお知らせの形式**か、`@USER`・`？` のような**個人間のやり取り**か。この違いが、リマインド対象かどうかに最も強く影響していた。
2. **「締切」「提出」などの語は、強いが限定的**
   含まれていればかなりの確率でリマインド対象となる。ただし実際の告知では、「〜をお願いします」「以下のとおりご案内します」など、締め切りを直接表す語を使わない書き方が多く、これらの語だけでは大半を拾うことは難しい。
3. **影響の強い語には2つのタイプがある**
   - 「各位」「期限」のように、**含まれれば確実性は高いが、出現が少ない語**
   - 「ください」「お願い」のように、**出現は多いが、それだけでは確実性が中程度の語**

   どちらか一方だけでは十分に判定できず、「この語があればリマインド対象」と言い切れる単独の語は確認できなかった。
