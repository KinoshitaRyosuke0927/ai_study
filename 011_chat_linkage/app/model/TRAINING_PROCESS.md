# 日本語BERTの学習プロセス(`train_model.py` 解説)

[`train_model.py`](train_model.py) が、リマインド判定モデル(日本語BERT)をどのような手順で学習しているかを、
コードに沿って説明する。モデル全体の概要・アプリへの組み込み方は [`MODEL.md`](MODEL.md) を参照。

実行方法(`011_chat_linkage` ディレクトリで):

```bash
python -m app.model.train_model
```

## 全体の流れ

学習処理は `main()`([L130](train_model.py#L130))が次の7ステップを順に実行する。

```
① ラベル付きCSVを読み込む
② 学習用85% / 検証用15%に分割
③ テキストをトークン(BERTが扱える数値列)に変換
④ BERTに分類用の層を付けて読み込む
⑤ クラスの重みを計算(不均衡への対応)
⑥ 学習条件を設定し、学習を実行(エポックごとに検証して最良を選ぶ)
⑦ 最終評価を表示し、モデルを保存
```

  - `pickup_flag` が `"0"` か `"1"`
  - `text` が空でない
- 戻り値は、テキストのリストとラベル(0/1)のリスト

2026年10月時点のデータは `collected_posts.csv` の1,369件(1が312件、0が1,057件)。

## ② 学習用・検証用への分割([L141](train_model.py#L141))

```python
train_test_split(texts, labels, test_size=VAL_RATIO, random_state=RANDOM_SEED, stratify=labels)
```

- `RANDOM_SEED = 42` で乱数を固定しているため、何度実行しても同じ分け方になる

## ③ トークナイズ([L146](train_model.py#L146))

```python
tokenizer = AutoTokenizer.from_pretrained(MODEL_NAME)
train_encodings = tokenizer(train_texts, truncation=True, padding=True, max_length=MAX_LENGTH, return_tensors="pt")
```

### トークナイズとは

BERTは文字列をそのまま扱えず、**数値(ID)の列**しか入力できない。そこで、テキストを次のように変換する。

1. 「トークン」と呼ぶ単位(単語や単語の一部)に区切る
2. 各トークンを、あらかじめ決められた**語彙表(vocabulary)**の番号(ID)に置き換える

この変換を**トークナイズ**、変換を行う部品を**トークナイザ**と呼ぶ。

BERTの最初の層(埋め込み層)は、IDごとに768次元のベクトルを持つ表になっている。
IDを受け取ると対応するベクトルを取り出し、以降の12層で文脈を加味したベクトルに変換していく。
語彙表とベクトル表は1対1で対応しているので、**事前学習時と同じトークナイザを使うことが必須**になる。
`AutoTokenizer.from_pretrained(MODEL_NAME)` は、ベースモデルの公開元からそのトークナイザ(語彙表 `vocab.txt` と設定)を取得する。

### このモデルのトークナイザ(`BertJapaneseTokenizer`)

`cl-tohoku/bert-base-japanese-v3` のトークナイザは、次の2段階で分割する。

| 段階 | 処理 | 使っている部品 |
|---|---|---|
| 1. 単語分割 | 日本語の文を形態素(単語)に区切る。英語と違ってスペースで単語が区切られていないため必要 | MeCab(Pythonからは `fugashi` 経由)+ 辞書 `unidic-lite` |
| 2. サブワード分割 | 語彙表にない単語を、語彙表にある**より小さな断片**に分ける。断片のうち2つ目以降には `##` が付く | WordPiece |

- 語彙表の大きさは **32,768語**(`config.json` の `vocab_size`)
- 大文字・小文字は区別する(`do_lower_case: false`)
- サブワード分割があるため、未知の単語でも文字単位まで分ければ、ほとんどの場合は語彙表の語で表現できる。どうしても表現できない文字は `[UNK]`(未知語)になる

**実際の分割例**(保存済みトークナイザで確認)

| 入力 | トークン |
|---|---|
| `@channel 明日までに経費精算をお願いします` | `[CLS]` `@` `ch` `##ann` `##el` `明日` `まで` `に` `経費` `精` `##算` `を` `お` `願い` `し` `ます` `[SEP]` |
| `【重要】年末調整書類の提出期限について` | `[CLS]` `【` `重要` `】` `年末` `調整` `書類` `の` `提出` `期限` `に` `つい` `て` `[SEP]` |

`channel` は語彙表に1語として無いため `ch` + `##ann` + `##el` に、`精算` は `精` + `##算` に分かれている。

### 特殊トークン

トークナイザは、文の前後などに次の特殊トークンを自動で付ける。

| トークン | ID | 役割 |
|---|---|---|
| `[CLS]` | 2 | 文の先頭に付く。BERTの最終層でこの位置のベクトルが「文全体の要約」となり、分類層への入力に使われる |
| `[SEP]` | 3 | 文の末尾に付く区切り |
| `[PAD]` | 0 | 長さを揃えるための埋め文字(後述) |
| `[UNK]` | 1 | 語彙表で表現できない文字 |
| `[MASK]` | 4 | 事前学習(穴埋め問題)で使うもの。本タスクでは使わない |

### トークナイズの設定

| 引数 | 意味 |
|---|---|
| `truncation=True, max_length=256` | `[CLS]`・`[SEP]` を含めて256トークンを超える場合は、**後ろを切り捨てる**(末尾の `[SEP]` は残る)。BERT自体は512トークンまで扱えるが、計算量はトークン数の2乗に比例して増えるため、256に抑えている。2026年10月時点のデータでは、投稿の中央値は67トークンで、約13%の投稿で切り捨てが発生する |
| `padding=True` | 複数の投稿をまとめて計算するには、長さを揃えた表(行列)にする必要がある。短い投稿の後ろに `[PAD]` を足して、**一緒にトークナイズした中で最も長い投稿**に揃える |
| `return_tensors="pt"` | 結果をPyTorchのテンソル形式で返す |

### トークナイズの結果

結果は、投稿ごとに次の2つの列を持つ。

- `input_ids`: トークンIDの列
- `attention_mask`: 各位置が本物のトークンなら `1`、`[PAD]` なら `0`。BERTは、`0` の位置を文脈の計算で無視する

```
入力: ["短い文", "@channel 明日までに経費精算をお願いします"]

トークン:       [CLS] 短い 文 [SEP] [PAD] [PAD] ... [PAD]     ← 17トークンに揃えられる
attention_mask:   1    1   1    1     0     0   ...   0
```

### 注意点

- `train_model.py` では、学習用の全1,163件を**1回でまとめて**トークナイズしている。そのため、全投稿がデータ中で最長の長さ(最大256)まで `[PAD]` で埋められる。多くの投稿は数十トークンなので、計算の大部分が `[PAD]` に費やされることになる。結果の正しさには影響しないが、学習時間が長くなる要因になっている(バッチごとに揃える「動的パディング」にすれば短縮できる)
- 推論時([`predict.py`](predict.py))も、学習時と同じ `max_length=256` と、`reminder_classifier/` に保存したトークナイザを使う。トークナイザの単語分割にはMeCabを使うため、実行環境に `fugashi` と `unidic-lite` が必要

### Datasetへの格納

トークナイズ結果は、`ReminderDataset`([L70](train_model.py#L70))に包む。
`__getitem__` は、i番目の投稿について `{"input_ids": ..., "attention_mask": ..., "labels": ...}` の辞書を返す。
この辞書のキー名はモデルの入力引数名と一致しているので、後述の `Trainer` がそのまま取り出してモデルに渡せる。

## ④ モデルの読み込み([L159](train_model.py#L159))

```python
AutoModelForSequenceClassification.from_pretrained(MODEL_NAME, num_labels=2)
```

- 事前学習済みのBERT本体(12層)を読み込み、その上に**2クラス分類用の層(Dropout → 全結合層 768→2)**を自動で追加する
- BERT本体は事前学習済みの重みを使う。追加した分類層だけは、ランダムな初期値から始まる

## ⑤ クラス重みの計算([L164](train_model.py#L164))

```python
class_weights = torch.tensor([1.0, num_neg / num_pos])
```

- **学習用データだけ**から「0の件数 ÷ 1の件数」を計算する(2026年10月時点のデータでは 898 ÷ 265 ≒ 3.39)
- この重みは `WeightedTrainer`([L88](train_model.py#L88))の `compute_loss()` で使われる。
  損失関数 `CrossEntropyLoss(weight=...)`([L102](train_model.py#L102))に渡すことで、
  「1」の投稿を間違えたときの損失が約3.39倍になる
- 重みを付けないと、件数の多い「0」ばかり当てていても損失が小さくなり、少数派の「1」を軽視したモデルになりがち。そのための対策

## ⑥ 学習条件の設定と学習の実行([L167](train_model.py#L167)〜[L193](train_model.py#L193))

### Hugging Face の `Trainer` とは

`Trainer` は、Hugging Face の `transformers` ライブラリが提供する**汎用の学習ループ**のクラス。
PyTorchでモデルを学習するには、本来は次のような処理をすべて自分で書く必要がある。

```python
# Trainer を使わない場合に自分で書く処理(概略)
loader = DataLoader(train_dataset, batch_size=8, shuffle=True)
optimizer = AdamW(model.parameters(), lr=2e-5)
scheduler = get_linear_schedule_with_warmup(optimizer, 0, total_steps)
for epoch in range(5):
    model.train()
    for batch in loader:
        loss = compute_loss(model, batch)      # 順伝播と損失の計算
        loss.backward()                        # 誤差逆伝播(勾配の計算)
        clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()                       # 重みの更新
        scheduler.step()                       # 学習率の更新
        optimizer.zero_grad()
    model.eval()
    metrics = evaluate(model, val_dataset)     # 検証(勾配計算なし)
    save_checkpoint_if_needed(model, metrics)  # チェックポイント保存・最良モデルの記録
```

`Trainer` は、このループと周辺処理(GPU/CPUへの配置、ログ出力、チェックポイント管理、最良モデルの復元など)をまとめて引き受ける。
利用者は、「何を」「どの条件で」学習するかを渡すだけで済む。

**このコードで `Trainer` に渡しているもの**([L183](train_model.py#L183))

| 引数 | 渡しているもの | 役割 |
|---|---|---|
| `model` | ④で読み込んだBERT + 分類層 | 学習対象 |
| `args` | `TrainingArguments`(下表) | エポック数・学習率などの学習条件 |
| `train_dataset` / `eval_dataset` | ③の `ReminderDataset` | 学習用・検証用のデータ |
| `compute_metrics` | `compute_metrics()` 関数 | 検証時に評価指標を計算する関数 |
| `class_weights` | ⑤のクラス重み | `WeightedTrainer` 独自の追加引数 |

**`Trainer` が内部で行っていること**

- **バッチの作成**: Datasetから8件ずつ取り出し、キーごとにテンソルを積み重ねて1つのバッチにまとめる(既定のデータコレータ)
- **損失の計算**: 通常は、`labels` を含むバッチをモデルに渡すと、モデル自身が(重みなしの)交差エントロピー損失を計算して返す。
  このコードでは `Trainer` を継承した `WeightedTrainer` で `compute_loss()` を上書きしている([L95](train_model.py#L95))。
  まずバッチから `labels` を取り出し(`inputs.pop("labels")`)、モデルには損失を計算させずにロジットだけを出力させる。
  そのうえで、クラス重み付きの損失を自分で計算している。このように、**一部の処理だけを差し替えられる**のが `Trainer` の特徴
- **検証**: `eval_dataset` 全体をモデルに通して(勾配は計算しない)、ロジットと正解ラベルを集める。
  それを `compute_metrics()` に渡して指標を得る。返した指標名には `eval_` が付く(例: `f1` → `eval_f1`)
- **チェックポイントと最良モデル**: 各エポック末に `reminder_classifier/checkpoints/checkpoint-<更新回数>/` へ保存する。
  `save_total_limit=1` で古いものを削除するが、`load_best_model_at_end=True` のときは最良のチェックポイントは削除対象から外れる。
  学習終了時には、`eval_f1` が最も高かったチェックポイントの重みをモデルに読み戻す
- **学習条件の保存**: `TrainingArguments` の内容を `training_args.bin` として保存する(`reminder_classifier/` に含まれている同名ファイル)

### 学習条件(`TrainingArguments`)

| 設定 | 値 | 意味 |
|---|---|---|
| `num_train_epochs` | 5 | 学習用データ全体を5周する |
| `per_device_train_batch_size` | 8 | 8件ずつまとめて重みを更新する(1エポック ≒ 146回、全体で約730回の更新) |
| `learning_rate` | 2e-5 | 1回の更新で重みを変える大きさ。事前学習済みの重みを壊さないよう小さめにしている |
| `eval_strategy` / `save_strategy` | `"epoch"` | 各エポックの終わりに検証用データで評価し、チェックポイントを保存する |
| `save_total_limit` | 1 | チェックポイントは1つだけ残す |
| `load_best_model_at_end` + `metric_for_best_model="f1"` | — | 学習の終了時に、**検証F1が最も高かったエポックのモデル**に戻す |
| `seed` | 42 | 学習中の乱数(Dropout、データのシャッフル順など)を固定する |

コードで明示していない設定には、`Trainer` の既定値が使われる。
学習時に実際に使われた値を、保存済みの `training_args.bin` から確認した結果は次のとおり。

| 設定 | 値 | 意味 |
|---|---|---|
| `optim` | `adamw_torch_fused` | 最適化手法はAdamW(PyTorch実装。下記参照) |
| `lr_scheduler_type` | `linear` | 学習率を、2e-5 から最後の更新で0になるよう直線的に下げていく |
| `warmup_steps` | 0 | ウォームアップ(学習初期に学習率を0から徐々に上げる処理)なし |
| `weight_decay` | 0.0 | 重み減衰なし |
| `adam_beta1` / `adam_beta2` / `adam_epsilon` | 0.9 / 0.999 / 1e-8 | AdamWの内部パラメータ(下記参照) |
| `max_grad_norm` | 1.0 | 勾配クリッピング。全パラメータの勾配をまとめたベクトルの大きさ(ノルム)が1.0を超えたら、1.0になるよう縮める。まれに発生する極端に大きな勾配で、学習が不安定になるのを防ぐ |
| `logging_steps` | 20 | 20回の更新ごとに損失をログに出力する |
| `fp16` / `bf16` | False | 半精度計算は使わない(32ビット浮動小数点で計算) |

### 最適化手法: AdamW

**最適化手法の役割**

学習とは、「損失(予測の間違いの大きさ)が小さくなる方向へ、重みを少しずつ動かす」ことの繰り返しである。
誤差逆伝播で求まるのは、各重みについて「どちらに動かすと損失が減るか」を表す**勾配**だけ。
実際に**どれだけ動かすか**を決めるのが最適化手法(オプティマイザ)の役割になる。

最も単純な方法(確率的勾配降下法、SGD)は、全ての重みを同じ倍率で動かす。

```
重み ← 重み − 学習率 × 勾配
```

ただし、この方法には弱点がある。勾配の大きさは重みごとに大きく異なり、バッチごとの勾配もばらつく。
そのため、BERTのように重みが約1億個あるモデルでは、学習率を1つに決めるのが難しい。

**Adam: 重みごとに歩幅を自動調整する**

Adamは、重みごとに次の2つの値を記録しておく。

| 記録する値 | 意味 | 効果 |
|---|---|---|
| m: 勾配の移動平均(β1 = 0.9) | 最近の勾配の「平均的な向き」 | バッチごとのばらつきがならされ、向きが安定する(モメンタム) |
| v: 勾配の2乗の移動平均(β2 = 0.999) | 最近の勾配の「大きさの目安」 | 勾配が大きい重みは歩幅を小さく、小さい重みは歩幅を大きくする |

更新式は次のとおり(m̂, v̂ は、学習の初期に m, v が0に偏るのを補正した値)。

```
m ← β1 × m + (1 − β1) × 勾配
v ← β2 × v + (1 − β2) × 勾配²
重み ← 重み − 学習率 × m̂ / (√v̂ + ε)
```

`m̂ / √v̂` は「向きの平均 ÷ 大きさの目安」なので、1回の更新幅は勾配の大きさによらず、おおむね**学習率程度**に揃う。
ε(1e-8)は、0で割るのを防ぐための小さな値。
この性質により、学習率の設定が比較的容易で安定して学習できるため、BERTなどTransformer系モデルの学習で標準的に使われている。

**AdamW: 重み減衰をAdamから切り離したもの**

「重み減衰(weight decay)」は、毎回の更新で重みを少しだけ0に近づける処理で、過学習を抑える正則化の一種。

- **Adam**: 重み減衰を勾配に足し込んで実装していた。その結果、上記の「大きさの目安で割る」処理によって、減衰の効き方が重みごとにばらついてしまう
- **AdamW**: 重み減衰を勾配とは**別に**、全ての重みに一律にかける(decoupled weight decay)

```
重み ← 重み − 学習率 × ( m̂ / (√v̂ + ε) + 重み減衰率 × 重み )
```

**このコードでの設定**

- 重み減衰率は既定値の **0.0** なので、AdamW固有の部分(重み減衰)は**働いておらず、実質的にはAdamと同じ動作**になっている。
  BERTの原論文のファインチューニングでは0.01が使われている。過学習が気になる場合は、`TrainingArguments(weight_decay=0.01)` と指定して試せる
- 学習率は2e-5から始まり、`linear` スケジュールにより約730回の更新で0まで直線的に下がる。学習の後半ほど重みの変化が小さくなり、細かい調整になる
- `adamw_torch_fused` は、PyTorchのAdamWを高速化した実装。計算内容は通常のAdamWと同じ

### 学習中に行われる処理(`trainer.train()`)

1. 学習用データをシャッフルし、8件ずつ取り出す
2. モデルに入力し、2クラスのスコア(ロジット)を得る
3. `compute_loss()` で、クラス重み付きの損失を計算する
4. 誤差逆伝播で、全ての重みについて勾配を計算する
5. 勾配が大きすぎる場合は、ノルム1.0に収まるよう縮める(勾配クリッピング)
6. AdamWで、**BERT本体と分類層の両方**の重みを更新する(フルファインチューニング。凍結している層はない)
7. 学習率スケジューラで、学習率を少し下げる
8. 1エポック終わるごとに、検証用データで `compute_metrics()`([L107](train_model.py#L107))を呼び、precision・recall・F1を計算する

`compute_metrics()` は `np.argmax(logits)`([L122](train_model.py#L122))で予測クラスを決めている。
これは**確率0.5を境に判定**するのと同じで、アプリでの運用しきい値(0.9)とは異なる基準で最良エポックを選んでいることになる。

## ⑦ 評価と保存([L195](train_model.py#L195)〜[L201](train_model.py#L201))

- `trainer.evaluate()` で、最良エポックのモデルを検証用データでもう一度評価し、結果を表示する
- `trainer.save_model()` と `tokenizer.save_pretrained()` で、`reminder_classifier/` にモデルとトークナイザを保存する(既存のモデルは上書き)
- 推論時は [`predict.py`](predict.py) がこのフォルダを読み込み、softmaxで変換した「1」の確率をスコアとして返す

## コードから読み取れる注意点

- **最終評価の値はやや楽観的になる。**
  検証用データを「最良エポックの選択」と「最終評価」の両方に使っているため、表示されるF1は未知のデータでの性能より高めに出る可能性がある。
  独立した評価には、学習・検証とは別のテスト用データが必要
- **再現性**: 分割・学習ともシードを固定しているため、同じ環境・同じデータなら基本的に同じモデルになる。
  ただし、GPUの種類やライブラリのバージョンが変わると、結果がわずかに変わることがある
- **出力先にチェックポイントが残る設定になっている。**
  チェックポイントの保存先は `reminder_classifier/checkpoints/` で、学習後もここに1つ残る。
  Blob Storageへアップロードする際の対象は、`predict.py` の `MODEL_FILES` に列挙された5ファイルだけ
