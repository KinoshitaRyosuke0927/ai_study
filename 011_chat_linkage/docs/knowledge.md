## 作成に至った経緯

- 毎月のAIMアジェンダにまとめる情報を手作業で収集するのが手間
- アジェンダ作成が誰でも(機械的に)できるようにしたい

## ツール紹介
AIMのアジェンダ作成のために、これまで次の作業を手作業で行っていました。

- Mattermostの連絡用チャンネルを1か月分さかのぼって読む
- GROUPSESSIONの新着記事を読む
- 共有すべき内容を選んで要約し、元の投稿・記事へのリンクを貼る
- 完成したアジェンダを社内wikiに転記する

そこでこのツールでは、アジェンダ作成の流れを**投稿取得 → アナウンス対象選択 → AI生成 → wiki公開**の4ステップで終えられるようになっています。

## 業務フロー
### STEP 1. 投稿・記事を取得する
取得開始日・取得終了日を指定し、**「履歴・新着記事を取得」** をクリックすると、2種類のデータ取得が**並行して**実行されます。

**Mattermost**

- 設定ファイルで指定したチャンネルをすべて対象にします(例: `AIビジネス連絡事項, AIC 連絡事項`)。
- Mattermost API v4(`/api/v4/channels/{id}/posts`)を、新しい投稿から順にページ単位で呼び出します。
- 入退室通知などのシステムメッセージや削除済みの投稿は取り除きます。
- 各投稿について、投稿者名と**投稿へのパーマリンク(URL)**を付けておきます。このURLは後でアジェンダのリンクになります。

**GROUPSESSION**

- 設定ファイルで指定したフォーラム(例: 全社連絡用、関東全体の情報共有)を対象にします。
- 画面から入力したID・パスワードでログインし、掲示板のJSON APIからスレッド一覧を取得します。対象期間に入るスレッドについては、本文と添付ファイルも取得します。
- 本文はHTMLからテキストに変換し、「タイトル + 本文」を1件のメッセージとしてまとめます。

---

### STEP 2. AIモデルで「共有すべきもの」に絞り込む
1か月分の投稿をすべて並べると、雑談や「了解です」のような返信も含まれ、一覧が長くなりすぎます。そこで、取得した各投稿・記事を**ローカルで動作する学習済みモデル**に入力します。

- モデル: 日本語BERT(`cl-tohoku/bert-base-japanese-v3`)を、Mattermostの投稿過去1年分に「対応・周知が必要か(0/1)」のラベルを付けたデータでファインチューニングしたもの
- 出力: 各投稿の「リマインド・共有が必要そうか」スコア(0〜1)
- スコアがフィルタ強度**以上**の投稿・記事だけを一覧に表示します

---

### STEP 3. アジェンダに載せる項目を選ぶ
アジェンダに載せたい項目の**チェックボックス**にチェックを入れます。
AIによる絞り込みは「候補を出す」ところまでで、**最終的に何を載せるかは人が選びます**。1件以上チェックすると「アジェンダを作成」ボタンが押せるようになります。

---

### STEP 4. AIで「全体共有事項」を生成する
チェックした項目を Azure OpenAI(`gpt-5.4-mini`)に渡し、「全体共有事項」欄の箇条書きを生成させます。生成時の主なルールは次のとおりです。

- 1項目ずつ `- ` の箇条書きで簡潔にまとめる
- 締め切り・実施日時・提出先などの重要な情報は省略しない
- 補足情報(期間・場所・金額など)はネストした箇条書きで書く
- 関連する項目はまとめてもよい

**リンクの扱い**

AIに実際のURLを書かせると、URLを1文字間違えたり、存在しないURLを作ったりするおそれがあります。そこで、

1. 各項目のURLを `{{URL_0}}`、`{{URL_1}}` … という**プレースホルダー**に置き換えてからAIに渡す
2. AIには `[タイトル]({{URL_0}})` の形でリンクを書かせる
3. 生成後に、アプリ側でプレースホルダーを本物のURLに置き換える

という方法で、リンク先を必ず正しいURLにしています。

**ひな形への埋め込み**

生成した箇条書きは、別ファイルで持っているテンプレートの `{{AGENDA_BODY}}` の位置に埋め込みます。`{{YEAR}}` と `{{MONTH}}` には当月の値が入ります。

```markdown
# {{YEAR}}年{{MONTH}}月度アジェンダ
- 実施日時：{{YEAR}}/{{MONTH}}/dd 15:00-16:00

## 第一部
#### 役員会の共有

#### 全体共有事項
{{AGENDA_BODY}}

## 第二部
#### 進捗報告
...
```

ひな形はテキストファイルなので、プレースホルダー以外は自由に書き換えられます。ファイルは毎回読み込み直すため、アプリを再起動する必要はありません。

**生成例**(一部抜粋)

```markdown
#### 全体共有事項
- 勤怠・交通費申請 　期限：7/2(木)
- [健康診断実施について](https://gs.jbdcl.com/gsession/...)
    - 検診実施後には、Excel上に受診日を記入すること
- [ストレスチェック](https://gs.jbdcl.com/gsession/...)
    - メールアドレス宛に案内が届く
    - 実施期間：7/1(水)～7/31(金)
- [AICインターネット回線の断線について](https://chat.jbdcl.com/jbd/pl/...)
    - 日程：2026年7月16日（木）11:00～13:00　※うち60分間の通信断
```

GROUPSESSION記事とMattermost投稿が1つのリストにまとまり、どの項目からも元の情報へ直接移動できます。

---

### STEP 5. GROWI(社内wiki)に公開する
設定ファイルで指定したパスの下に、`/{年}/{月}` というパスでページを作ります(例: `…/100_AIM/2026/06`)。
- 同じ年月のページがすでにあれば、上書きして更新します。
- 完了すると、公開したページのURLが表示されます。

> 既存ページを「自分のみ公開」に切り替えて公開した場合は、GROWIのAPIの制約でページを作り直すため、**URLが変わります**。

まず「自分のみ公開」で下書きとして置き、内容を確認してから「公開」に切り替える使い方もできます。

## 今後の展望

- 毎月自動でデータ取得 ⇒ アジェンダ作成まで行い、Mattermostに通知してくれるように自動化
- 作成するアジェンダの品質向上

## おまけ
アジェンダ作成とは別に、**Mattermostにスラッシュコマンドを投稿するだけで、対応が必要そうな投稿を一覧にして返信してくれる**仕組みをAzure上で動かしています。
今回は**個人のアクセストークンだけで動かす**ため、`/nightrain remind` を「普通のメッセージ」として投稿してもらい、それを定期的なポーリングで見つける方式にしました。そのため、返信までに最大で5分ほどかかります。

**使い方**

監視対象のチャンネル(またはDM)に、次の1行を投稿します。

```
/nightrain remind
```

数分以内に、その投稿へのスレッド返信で次のような表が届きます。

| 投稿日時 | 元の投稿へのリンク | 投稿内容要約 |
| --- | --- | --- |
| 2026-06-10 09:12 | [投稿を見る](#) | 勤怠・交通費申請の提出期限は7/2(木)まで。 |
| 2026-06-15 14:30 | [投稿を見る](#) | ストレスチェックを7/1〜7/31の期間内に受検すること。 |

「締め切りがある連絡、何があったっけ？」と思ったときに、チャンネルをさかのぼらなくても未対応になりそうな連絡をまとめて確認できます。

**処理概要**

1. **コマンドの検知**: Azure Functions のタイマートリガーが**5分おき**に起動し、監視対象チャンネル・DMの新着投稿を取得します。本文がちょうど `/nightrain remind` の投稿があれば処理を始めます。
2. **投稿の取得**: 設定ファイルで指定したチャンネル(複数可)から、直近1週間分の投稿を取得します。
3. **絞り込み**: アジェンダ作成のSTEP 2と同じ日本語BERTモデルでスコアを付け、しきい値(0.9)以上の投稿だけを残します。
4. **要約**: 残った投稿を1件ずつ Azure OpenAI(`gpt-5.4-mini`)で1文に要約します。締め切りや提出先などの重要な情報は残すように指示しています。
5. **返信**: 投稿日時順に並べてMarkdownの表にし、コマンドを投稿したスレッドに返信します。

**Azure上での工夫**

- **どこまで処理したかを覚えておく**: Azure Functions は実行が終わるとメモリの内容が消えるため、チャンネルごとに「最後に処理した投稿の時刻・ID」を Blob Storage に保存しています。同じコマンドに二重に返信したり、見落としたりしないようにしています。
- **モデルはデプロイパッケージに含めない**: 学習済みモデル(約425MB)をパッケージに入れるとデプロイに失敗するため、モデルは Blob Storage に置き、初回起動時だけダウンロードしてキャッシュしています。
- **従量課金プラン**: Consumption プランで動かしているため、5分おきに起動しても料金がかかるのは実行していた時間分だけです。
- **画面(UI)はAzureに置かない**: 手動操作用の画面はセキュリティを考慮してexeでの配布のみとし、Azure上にはポーリング処理だけを置いています。

> 同じ仕組みで `/nightrain agenda` と投稿すると、アジェンダの作成からGROWIへの公開までを自動で行います。人が内容を確認していないため、この場合は「自分のみ公開」で公開されます。
