# 上司レビュー再現型 PowerPoint レビューアプリ 詳細設計（ローカルプロトタイプ版）

## 1. 文書の目的

本ドキュメントは、**「マルチモーダル LLM を土台に、過去レビュー RAG で事例記憶を補い、上司嗜好を pairwise reward model で学習し、最後に critic で根拠検証する多段階アーキテクチャ」**を、まずは**ローカルで起動するプロトタイプ**として実装するための詳細設計をまとめたものである。

前提として、最終的なデプロイ先は Azure とするが、初期段階では以下の方針を採る。

- ローカル PC で動かせることを優先する
- 必要に応じて Azure OpenAI や Azure の DB / Storage を使ってよい
- ただし、**全コンポーネントを Azure に寄せ切る必要はない**
- 将来 Azure へ移行しやすいよう、**インターフェースを明確化して疎結合に設計する**

---

## 2. このアプリで再現したいもの

再現したいのは単なる「レビューコメント」ではなく、**特定の上司が資料を見たときの確認の仕方**である。ここでいう確認の仕方には、最低でも次の 4 要素が含まれる。

1. **何を見るか**
   - 数字の根拠
   - ストーリーの通り方
   - 結論の先出し
   - 意思決定に必要な前提
   - 視認性や言い回し

2. **何を優先するか**
   - 色味より数字の妥当性を重視する
   - 誤字より結論の弱さを重視する
   - 経営層向けでは詳細よりメッセージ性を重視する

3. **どう指摘するか**
   - 厳しめか、柔らかめか
   - Why を先に言うか、修正案を先に言うか
   - 一言で済ませるか、背景込みで説明するか

4. **どの条件でその指摘を出すか**
   - 会議の種類
   - 相手の職位
   - 資料の用途
   - 前後スライドとの関係

したがって必要なのは、単一の「良い/悪い」分類器ではなく、**文脈条件付きのレビュー選好モデル**である。個人化 LLM の研究では、人間の嗜好を一様分布として扱う通常の RLHF では個人差を捉えにくく、軽量なユーザモデルを併用する設計が有効とされている。これは上司固有レビュー再現と整合する。

---

## 3. ローカルプロトタイプのゴール

ローカルプロトタイプでは、以下を達成できれば十分成功とみなす。

### 3.1 機能ゴール
- PPTX または PDF を入力できる
- スライド画像とテキストを抽出できる
- 各スライドに対する**汎用的な指摘候補**を複数生成できる
- 過去レビューの RAG により、似た事例を補助コンテキストとして引ける
- 上司嗜好の reranker / reward model で候補を再順位付けできる
- critic により、根拠が薄い指摘を落とせる
- UI または API 出力として、以下を返せる
  - 指摘内容
  - 該当スライド
  - 根拠
  - 修正提案
  - 重要度
  - 上司らしさスコア

### 3.2 非機能ゴール
- ローカルで 10〜30 枚程度の資料を数分以内に処理できる
- Azure リソースの ON/OFF を `.env` レベルで切り替えられる
- 将来 Azure へ移行する際に、ストレージ・ベクトル DB・LLM 呼び出しを差し替えやすい

## 4. 全体アーキテクチャ詳細

```text
[Upload PPTX/PDF]
      |
      v
[Ingestion Pipeline]
  - ファイル保存
  - スライド画像化
  - テキスト抽出
  - ノート抽出
  - 図表/表/見出しの構造化
      |
      v
[Multimodal Understanding]
  - slide summary
  - deck summary
  - claims / numbers / evidence candidates
  - slide role inference
      |
      +---------------------+
      |                     |
      v                     v
[Review Memory RAG]   [Generic Candidate Generator]
  - 類似スライド検索      - 指摘候補 n 件生成
  - 類似コメント検索      - severity 初期推定
  - 修正前後事例取得      - suggestion 生成
      |                     |
      +----------+----------+
                 |
                 v
     [Manager Preference Ranker / Reward Model]
     - 上司らしさスコア
     - 重要度スコア
     - top-k 採択
                 |
                 v
            [Critic / Verifier]
            - 根拠スパン検証
            - 幻覚検知
            - 重複統合
            - 不確実性判定
                 |
                 v
          [API/UI Response + Logging]
```

この構造は、レビュー品質向上において**構造化された検討手順と根拠ベースの出力**が有効であるという流れと一致する。

## 6. file_ingestion 設計

### 6.1 役割
- ユーザがアップロードした PPTX / PDF を受け取り保存する
- 解析ジョブを起動する
- プロトタイプではローカルファイル保存を基本とする

### 6.2 必要データ
#### 入力
- `file_id`
- `original_filename`
- `mime_type`
- `local_path`
- `uploaded_at`
- `uploader_id`（将来用。ローカル試作では固定でもよい）

#### 出力
- 保存済みファイルパス
- 解析ジョブ ID
- プレゼンテーション ID

### 6.3 保存先
#### ローカルプロトタイプ
- `./data/uploads/`
- `./data/derived/`

#### Azure 移行時
- `Azure Blob Storage`

### 6.4 実装候補
- `FastAPI` の upload endpoint
- 非同期実行は、最初は単純にバックグラウンドタスクで良い
- 将来は `Celery` / `RQ` / Azure Functions に移行可能

## 7. slide_parser 設計

### 7.1 役割
- PPTX / PDF からスライド単位の構造化データを作る
- 画像、テキスト、ノート、可能なら図表/表の存在を抽出する

### 7.2 必要なデータ
#### スライド単位で最低限必要な項目
```json
{
  "presentation_id": "pres_001",
  "slide_id": "pres_001_s03",
  "slide_no": 3,
  "image_path": "data/derived/pres_001/slides/003.png",
  "raw_text": "...",
  "speaker_note": "...",
  "layout_text_blocks": [...],
  "shapes": [...],
  "tables": [...],
  "charts": [...],
  "page_size": {"width": 1920, "height": 1080}
}
```

### 7.3 抽出すべき情報
#### A. テキスト系
- タイトル
- 箇条書き本文
- 脚注
- 注釈
- 出典表記
- 発表者ノート

#### B. 視覚構造系
- テキストブロックの位置
- グラフの有無
- 表の有無
- アイコン / 図解の有無
- 強調色、囲み、矢印

#### C. 資料文脈系
- スライド役割候補
  - 表紙
  - 目次
  - 結論
  - 背景
  - 課題
  - 市場
  - 数値根拠
  - 施策
  - 実行計画
  - 収支
  - 補足

### 7.4 ローカル実装案
#### PPTX の場合
- `python-pptx` でテキスト / ノート / shape 情報取得
- LibreOffice headless で PDF 化 or 画像化
- 画像化が必要なら `soffice --headless --convert-to pdf` の後 `PyMuPDF` で各ページ PNG 化

#### PDF の場合
- `PyMuPDF` でテキストと画像レンダリング
- より構造化が必要なら Azure Document Intelligence を任意使用

### 7.5 ローカルで十分な理由
初期段階では、完璧な PowerPoint 構造復元よりも、**後段の LLM が解釈可能な粒度で slide JSON を作ること**が重要である。

## 8. multimodal_understanding 設計

### 8.1 役割
- スライド画像と抽出テキストを統合し、各スライドの意味表現を作る
- スライド単体と資料全体の両方を要約する
- 後段で使う、レビューに効く特徴を構造化する

### 8.2 この層で必要なデータ
#### 入力
- スライド画像
- raw text
- speaker note
- slide position（何枚目か）
- 前後スライド要約
- deck metadata（資料目的、想定 audience など）

#### 出力
```json
{
  "slide_id": "pres_001_s03",
  "slide_summary": "市場規模と成長率を示し、事業機会の大きさを説明するスライド",
  "slide_role": "evidence_market",
  "main_message": "市場が成長しているため参入余地がある",
  "claims": [
    "国内市場は成長している",
    "当社が参入可能な余地がある"
  ],
  "numbers": [
    {"label": "TAM", "value": "1200億円"},
    {"label": "CAGR", "value": "12%"}
  ],
  "missing_evidence_candidates": [
    "市場規模の出典が見当たらない"
  ],
  "visual_observations": [
    "棒グラフがある",
    "脚注領域が空白に近い"
  ],
  "review_risk_hints": [
    "数値の根拠不足",
    "SAM/SOM に分解されていない可能性"
  ]
}
```

### 8.3 必要な特徴量の観点
この層では、単なる要約ではなく、**レビューしやすい特徴量**を作る必要がある。最低限ほしいのは以下。

#### 論理系
- main message
- supporting evidence
- conclusion-first かどうか
- 前後スライドとの接続
- 重複/飛躍

#### 数字系
- 数値の一覧
- 単位
- 比較対象
- 期間
- 出典の有無
- 推計か実績か

#### 意思決定系
- 経営判断に必要な前提があるか
- KPI / 成功条件が示されているか
- 代替案比較があるか
- リスクと対策があるか

#### 表現系
- 1 スライド 1 メッセージになっているか
- タイトルが結論になっているか
- 文字量過多か
- 見出しと本文の関係が明確か

### 8.4 実装方式
#### Option A: Azure OpenAI を使う
- 画像 + テキストを入力できるマルチモーダルモデルを使用
- スライドごとに JSON Schema 準拠で構造化出力

#### Option B: ローカル / 他 API を使う
- 画像理解対応モデル + 独自パーサ
- ただし Azure 移行性を考えると、**LLM client インターフェースを抽象化**する

### 8.5 必須インターフェース
```python
class MultimodalAnalyzer(Protocol):
    def analyze_slide(self, slide: SlideInput, context: DeckContext) -> SlideAnalysis:
        ...

    def summarize_deck(self, slides: list[SlideAnalysis]) -> DeckAnalysis:
        ...
```

## 9. review_memory_rag 設計

### 9.1 役割
- 過去の上司レビューを検索し、今回のレビューの参考事例として与える
- 「似たスライドで、過去に何を問題視したか」をコンテキストに注入する

### 9.2 必要データ
RAG の質は、何を保存するかでかなり決まる。最低限、以下の 4 種類を保持したい。

#### A. 過去スライド情報
- スライド画像 or サムネイル
- 抽出テキスト
- スライド要約
- スライド役割
- 資料種別

#### B. 過去レビューコメント
- 生コメント
- 正規化コメント
- 該当スライド ID
- severity
- 会議種別
- コメント発話者
- コメント理由（あるなら）

#### C. 修正前後差分
- 修正前スライド
- 修正後スライド
- どの指摘に対する修正か
- 修正が受け入れられたか

#### D. レビューセッションメタデータ
- 会議名
- 対象 audience
- 資料の目的
- 上司名
- 作成者レベル

### 9.3 推奨チャンク設計
RAG のチャンクは「固定 500 文字」ではなく、意味単位で分ける。

#### `slide_chunk`
```json
{
  "chunk_type": "slide",
  "slide_id": "pres_old_014_s05",
  "slide_summary": "収支見通しと投資回収のスライド",
  "role": "financial_projection",
  "text": "...",
  "metadata": {
    "presentation_type": "investment_review",
    "audience": "executive",
    "reviewer": "manager_a"
  }
}
```

#### `comment_chunk`
```json
{
  "chunk_type": "comment",
  "comment_id": "cmt_001",
  "slide_id": "pres_old_014_s05",
  "normalized_comment": "投資回収年数の前提条件が不足しており、意思決定できない",
  "severity": "high",
  "category": "decision_basis",
  "metadata": {
    "reviewer": "manager_a",
    "meeting_type": "exec_review"
  }
}
```

#### `revision_pair_chunk`
```json
{
  "chunk_type": "revision_pair",
  "before_slide_id": "...",
  "after_slide_id": "...",
  "fix_summary": "感度分析表と前提条件を追加",
  "linked_comment": "投資回収の根拠不足",
  "metadata": {
    "accepted": true
  }
}
```

### 9.4 Retrieval 戦略
単純なベクトル検索 1 本だと、上司っぽさが弱い。以下の複合検索を推奨する。

1. **slide semantic retrieval**
   - 今回スライドと意味的に似た過去スライドを取得
2. **comment retrieval**
   - 類似スライドに紐づく過去コメントを取得
3. **revision retrieval**
   - そのコメントがどう修正されたか取得
4. **metadata filter**
   - 同じ会議種別、同じ audience を優先

### 9.5 スコアリング方針
総合スコア例:

```text
retrieval_score =
  0.45 * slide_embedding_similarity +
  0.25 * role_match +
  0.15 * meeting_type_match +
  0.10 * reviewer_match +
  0.05 * accepted_fix_bonus
```

### 9.6 ローカル実装候補
- 最初は `FAISS` or `Qdrant(local)`
- RDB は `SQLite` or `PostgreSQL`
- Azure 移行時は `Azure AI Search` に差し替え可能

### 9.7 必須インターフェース
```python
class ReviewMemory(Protocol):
    def index_slide(self, slide_doc: SlideRagDocument) -> None:
        ...

    def index_comment(self, comment_doc: CommentRagDocument) -> None:
        ...

    def retrieve(self, query: RagQuery) -> RagResult:
        ...
```

## 10. candidate_generator 設計

### 10.1 役割
- 汎用的なレビュー候補を複数出す
- この段階では「上司らしさ」よりも、**漏れなく候補を出すこと**を優先する

### 10.2 入力
- 現在スライドの `SlideAnalysis`
- 資料全体要約 `DeckAnalysis`
- RAG で取得した過去類似スライド / コメント / 修正事例
- レビュー対象会議種別
- 出力件数 `n_candidates`

### 10.3 出力
```json
[
  {
    "candidate_id": "cand_01",
    "issue": "市場規模の数値に出典がない",
    "category": "evidence",
    "severity_guess": "high",
    "why_it_matters": "投資判断の根拠として弱い",
    "suggestion": "出典と算出方法を脚注に明記する",
    "evidence_hint": ["slide_3 chart", "footnote area empty"]
  },
  {
    "candidate_id": "cand_02",
    "issue": "TAM/SAM/SOM の切り分けがなく、狙う市場が不明瞭",
    "category": "logic",
    "severity_guess": "medium",
    "why_it_matters": "参入余地の説明として不足",
    "suggestion": "狙う対象市場を分解して示す",
    "evidence_hint": ["market size only TAM shown"]
  }
]
```

### 10.4 候補生成時の注意
- 1 発で最終回答を出させない
- 事実観察と指摘を分ける
- 各候補に evidence hint を持たせる
- 重複候補が出てもよい。後段で統合する

### 10.5 生成観点
固定ルールではなく、最低限以下の観点を広く探索する。

- 論理構成
- メッセージ性
- 数字の根拠
- 意思決定に必要な情報
- リスクと前提
- audience 適合性
- 視認性
- 言い回し

### 10.6 実装方針
- LLM structured output で JSON を返す
- 1 スライドごとに 5〜10 件生成
- 重要なのは再現率。precision は後段で上げる

## 11. manager_preference_ranker 設計

### 11.1 役割
- candidate_generator が出した候補の中から、**この上司が実際に言いそうなものを上位化**する
- 上司らしさと重要度を学習する

### 11.2 なぜ reward model / pairwise か
ローカルプロトタイプ段階では、実データ数がそれほど多くない可能性が高い。その場合、絶対スコア学習よりも、

- 候補 A と B のどちらが上司らしいか
- 候補 A と B のどちらが重大か

の比較学習のほうが作りやすく、ラベルぶれも少ない。個人化研究でも、個人の嗜好を明示/暗黙フィードバックから学ぶ考え方が中心である。 [P-RLHF](https://arxiv.org/abs/2402.05133)

### 11.3 必要データ
#### 学習 1 サンプルの最小単位
```json
{
  "slide_context": {
    "slide_summary": "市場規模を示すスライド",
    "slide_role": "evidence_market",
    "deck_goal": "新規事業提案",
    "meeting_type": "exec_review"
  },
  "candidate_a": {
    "issue": "市場規模の出典がない",
    "category": "evidence"
  },
  "candidate_b": {
    "issue": "配色がやや単調",
    "category": "visual"
  },
  "preferred": "a",
  "preference_type": "manager_likeness",
  "reviewer": "manager_a"
}
```

### 11.4 どんなデータを集めるべきか
#### 必須データ
- 実際の上司コメント
- コメント対象スライド
- 会議文脈
- 資料タイプ

#### あると強いデータ
- 修正が採用されたか
- 上司が複数の候補の中で何を優先したか
- 同じスライドに対する見送られた指摘
- 上司が重要と言った順序

#### 半自動で作れるデータ
- 実コメント vs LLM 候補コメント
- 受け入れられた修正コメント vs 受け入れられなかったコメント
- 同一スライドで severity の異なる候補対

### 11.5 ラベル種類
少なくとも 2 軸で持つとよい。

#### A. manager_likeness
- その上司が言いそうか

#### B. business_priority
- 実務上どれがより重大か

この 2 軸は一致することも多いが、完全には同一ではない。たとえば上司は細かい表現を気にしがちでも、実務上は数字根拠のほうが重大というケースがある。

### 11.6 モデル構成
#### MVP
- `cross-encoder` ベースの reranker
- 入力: `[slide context] + [candidate]`
- 出力: score

#### 学習方法
- Pairwise hinge loss / logistic loss
- あるいは pointwise 回帰 + pairwise 併用

#### ローカルプロトタイプ向け候補
- `sentence-transformers` の reranker 系
- `bge-reranker` 系の微調整
- 小型 Transformer を LoRA 微調整

### 11.7 推論時出力
```json
{
  "candidate_id": "cand_01",
  "manager_likeness": 0.91,
  "business_priority": 0.88,
  "final_rank_score": 0.90
}
```

### 11.8 スコア統合
```text
final_rank_score =
  0.60 * manager_likeness +
  0.25 * business_priority +
  0.15 * rag_support_score
```

## 12. critic_verifier 設計

### 12.1 役割
- rerank 後の候補が、本当に資料根拠に基づくかを検証する
- 幻覚や重複を減らす
- 必要なら confidence を下げる

LLM の批評能力は自明ではなく、自己批評だけでは不十分なことが示されているため、**根拠確認を明示的な段として設ける**のが重要である。 [Critique Ability of LLMs](https://arxiv.org/abs/2310.04815) [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html)

### 12.2 critic に必要な入力
- 上位 candidate
- 元の slide analysis
- 該当スライドの raw text
- 画像観察結果
- deck context
- RAG 参照根拠

### 12.3 critic の検証観点
1. **根拠性**
   - 指摘に対応する evidence がスライド内にあるか
2. **外挿しすぎていないか**
   - スライドにない事実を仮定していないか
3. **重複性**
   - 他候補と実質同じか
4. **修正可能性**
   - suggestion が具体的か
5. **文脈整合性**
   - 資料全体から見て誤読していないか

### 12.4 critic 出力
```json
{
  "candidate_id": "cand_01",
  "verdict": "keep",
  "evidence_spans": [
    {"type": "text", "value": "TAM 1200億円"},
    {"type": "visual", "value": "footnote area has no source"}
  ],
  "critic_confidence": 0.86,
  "critic_comment": "出典不足の指摘は妥当。数値はあるが根拠表記が確認できない。",
  "dedup_group": "grp_03"
}
```

### 12.5 ローカルプロトタイプでの現実的実装
- 最初は LLM critic + ルール補助でよい
- ルール例
  - 出典文字列パターンが無ければ source risk を加点
  - 文字数が多すぎる場合は readability risk を加点
- 将来は NLI ベース検証器や専用判定モデルへ拡張可能

## 16. ベクトルストア設計

### 16.1 何を埋め込むか
最低 3 種類の埋め込みを持つとよい。

1. **slide semantic embedding**
   - スライド要約 + main message + role
2. **comment embedding**
   - normalized comment + category + rationale
3. **revision embedding**
   - 修正内容要約 + linked comment

### 16.2 なぜ分けるか
スライドの類似性と、コメントの類似性は別物である。例えば、同じ市場規模スライドでも、ある上司は「数字の出典」を気にし、別の上司は「結論の弱さ」を気にする。したがって、**slide 検索 → comment 検索**の 2 段が必要になる。

### 16.3 ローカル実装
- `Qdrant` を Docker で立てるのが扱いやすい
- または `FAISS` + JSON メタデータでも MVP は可能

### 16.4 Azure 移行
- `Azure AI Search` に置換しやすいよう、Repository パターンを採る

## 25. 最終提案

ローカルプロトタイプとして最も現実的な実装は、次の構成である。

- **資料理解**: Python で PPTX/PDF を解析し、必要に応じて Azure OpenAI のマルチモーダルモデルで slide analysis を作る
- **事例記憶**: ローカル PostgreSQL + Qdrant/FAISS で過去レビュー RAG を構成する
- **上司再現**: 実上司コメントから pairwise preference データを作り、cross-encoder 型 reranker を学習する
- **信頼性担保**: LLM critic + ルール補助で根拠確認を行う
- **Azure 移行性**: LLM / Storage / Vector DB / Metadata DB を抽象化し、後で Azure サービスへ差し替え可能にする

特に重要なのは、**必要なデータを最初から「学習に使える形」で保存すること**である。すなわち、スライド・コメント・会議文脈・修正採否・候補比較の 5 点セットを蓄積できる設計にしておくべきである。これができていれば、最初は単純な reranker でも、将来的には reward model や DPO 的な改善へ発展しやすい。

また、レビュー自動化研究では、構造化されたレビュー手順や根拠ベースの検証が有効であり、単純な一発生成よりも多段階アーキテクチャのほうが安定しやすい。 [DeepReview](https://aclanthology.org/2025.acl-long.1420/) [CRITIC](https://proceedings.iclr.cc/paper_files/paper/2024/hash/fef126561bbf9d4467dbb8d27334b8fe-Abstract-Conference.html)

個人化の観点でも、個人の嗜好を別レイヤで持つ設計は妥当であり、今回の「上司レビュー再現」と非常に相性が良い。 [P-RLHF](https://arxiv.org/abs/2402.05133)
