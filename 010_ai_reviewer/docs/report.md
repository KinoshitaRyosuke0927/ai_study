## STEP2 技術調査

### 技術概要

`.pptx` をLibreOfficeでPDF化し、popplerでスライドごとの画像に変換する。変換した画像とスライドごとの「伝えたいこと」をAzure OpenAIに渡し、あらかじめCSVで定義したレビュー観点ごとにQ&A形式でレビューさせ、その結果を自然な日本語文章に集約する。さらに集約結果をもとに、スライドごとの具体的な修正方針をJSON形式で提案させる。

### どのような課題を解決できるか

| 課題 | 解決内容 |
|---|---|
| 既存AI任せのレビューだと、雰囲気的(一般的)な指摘しか挙げられない | 実際のレビュー内容から特定個人のレビュー観点を抽出する |
| 資料レビューに時間がかかる | AIが全スライドを一括でレビューし、観点別の集約結果を短時間で返す |
| 指摘だけ受け取っても具体的な直し方が分からない | 指摘をもとに、修正手順・差し替え文案・期待される状態までAIに提案させる |

### 代表的なAPI・ツール・ライブラリ

| 名称 | 概要 | 特徴 |
|---|---|---|
| python-pptx | `.pptx` の読み込み・更新・構造解析ライブラリ | Pythonで扱いやすい／既存資料の構造解析が可能／MVPで試しやすい |
| Open XML 直接解析 | `.pptx` の低レベル構造解析 | 形式理解として本質的だが実装コストが高い |
| Aspose.Slides | 高精度な読み込み・変換・レンダリング | PDF・PNG・HTML等への出力が豊富で再現性が高いが商用ライセンスが前提 |
| LibreOffice 変換パイプライン | サーバーでのPDF化・画像化 | 自前環境で画像化しやすくサーバーバッチに組み込みやすいが、完全な描画一致は保証されない |
| Azure OpenAI | マルチモーダルLLM | 画像＋テキストを同時入力可能／JSONモードで構造化出力ができる |

### 調査して感じた疑問点・気になる点

- LibreOfficeでのPDF変換がPowerPoint本来の見た目（フォント・アニメーション等）とどこまで一致するか
- スライド単体ではなく全体を通しての一貫性（用語統一・流れ）をAIにどう評価させるべきか
- レビュー観点が多くなるほどプロンプトが長大化し、レイテンシ・コストが増加する点をどう緩和するか
- 「判断ができません」という回答をAIがどの程度の粒度で使い分けられるか

### 選んだプロトタイプ

1. スライド画像化＋観点別レビュー＋修正方針提案までを行うWebアプリ

### 作成計画

**目標**

- 特定のレビュー者の観点に基づいてレビューできるようにする
- 実際に発表する前に、セルフレビューの道具として使用できる

**目的（何を確かめたいか）**

Azure OpenAIのマルチモーダル機能を使って、スライド画像とレビュー観点から実務で使える水準の指摘・改善提案を生成できるかを検証する。

**成功基準の定義**

- セルフレビューにこのアプリケーションを使用することで、指摘事項が事前に解消され、実際のレビュー時の指摘量が軽減される
- 既存のAIを使用したレビューと比較して、少ない入力情報でも実務で使える水準のレビューが行える
- 多数のレビュー観点に対しても、並列処理によりレビュー処理が実用的な応答時間(1~3分)に収まる
- 多数の指摘事項に対しても、並列処理により修正方針提案処理が実用的な応答時間(1~3分)に収まる

## STEP4 開発環境決定

### 使用するライブラリやAPI、モデルの比較

| 項目 | python-pptx | Open XML 直接解析 | Aspose.Slides | LibreOffice 変換パイプライン |
|---|---|---|---|---|
| 実装コスト | ◎ 低い | △ 高い | ○ 低いが商用ライセンス前提 | ○ 中程度 |
| 見た目の再現性 | △ 構造解析中心で見た目再現は別問題 | △ レンダリングは別途必要 | ◎ 比較的高い | ○ 完全一致ではないが実用十分 |
| サーバーサイド組込みやすさ | ○ | ○ | ○ | ◎ バッチ処理に組み込みやすい |
| コスト | ◎ 無料 | ◎ 無料 | △ 商用ライセンス($999/月) | ◎ 無料 |

### 選んだ環境

- **スライド画像化**: LibreOffice（headless）+ poppler（pdf2image）
  - `.pptx` → PDF → PNG/JPEG の変換パイプラインをサーバーサイドで完結でき、実装コストが低い
- **AIモデル**: Azure OpenAI（GPT-4o）
  - 画像とテキストを同時に扱えるマルチモーダル対応と、JSONモードによる構造化出力が決め手
- **レビュー観点管理**: CSV（`review_point.csv`）
  - `role` / `perspective_type` / `detail` で観点を管理し、観点の追加・細分化をコード変更なしで行える
- **Webフレームワーク**: FastAPI + 素のHTML/CSS/JavaScript
  - Pythonで統一し、非同期処理（`asyncio.gather`）で観点別レビューを並列実行しやすい
- **データ永続化**: なし（都度アップロード・都度レビュー）
  - PoC段階では保存要件がないため、ステートレスな構成として実装コストを最小化

## STEP6 学習内容まとめ

### できたこと

**スライド画像化**

- LibreOffice + poppler によるパイプラインで `.pptx` をPDF経由でPNG/JPEGに変換し、ブラウザ上にスライド一覧・拡大表示できるようにした

**レビュー機能**

- 実際のレビュー時の指摘事項をもとにレビュー観点を抽出し、CSVで一元管理して `perspective_type`（構成・計画・課題設定・優先度・実現可能性・評価等）ごとにプレゼンテーション全体を評価する方式にした
- 抽出した観点に基づいてAIにレビューをさせることができた。「判断ができません」「指摘事項はありません」を明示的なルールとしてプロンプトに組み込み、無理な指摘の生成を抑制した
- Q&A形式のレビュー結果を、観点ごとに自然な日本語の集約文章へ変換する2段階のプロンプト構成にした
- レビュー作業を観点ごとに分割し、`asyncio.gather` + `asyncio.to_thread` でAIへの送信データを分割・並列実行することで、観点数が増えても処理時間を短縮できた

**修正方針提案機能**

- 観点別レビュー結果（指摘事項）とスライド画像をもとに、スライドごとに `summary` / `issues` / `actions` / `example_text` / `expected_outcome` を含む構造化JSONで修正方針を提案する機能を追加した
- プロンプトに「悪い例／良い例」を明記することで、抽象的な助言（「わかりやすくする」等）ではなく具体的な修正指示が返るように調整した

### できなかったこと

| 項目 | 理由 |
|---|---|
| レビュー対象観点の絞り込み | 常にすべての観点でレビューを行ってしまうため、本来レビュー対象ではない観点についても指摘が生成され、ノイズになってしまう |
| 指摘事項の可読性 | 観点ごとの指摘事項が長文になりやすく、内容を理解する際に利用者の負担が大きい |
| 観点間での指摘の重複排除 | 異なる観点でレビューしているにもかかわらず、内容がほとんど同じ指摘が複数の観点にまたがって生成されてしまう |
| 修正方針の提示方法 | 修正方針が文字情報のみで提示されるため、利用者が内容を理解する際に負担が生まれてしまう |

### 気づいたこと・学んだこと

- レビュー観点をCSVで外出しすることで、コードを変更せずに観点の追加・細分化ができ、観点数が増えても運用上の負担が小さかった
- スライド単位のレビューは一見自然に思えたが、資料全体の一貫性（用語統一・構成の流れ）を評価する目的とは相性が悪く、全体レビューへの一本化がより実用的だった
- 観点別レビューを並列化（`asyncio.gather`）するだけで、観点数に比例して増えていた応答時間を大幅に短縮でき、体感的な使い勝手が大きく改善した

### 次回やってみたいこと・改善したいこと

- レビュー結果・修正方針の履歴を保存し、資料の改訂前後を比較できるようにしたい
- 修正方針の提案を反映した後のPowerPointイメージを出力できるようにしたい
- 特定個人の口調や口癖を表現できるようにしたい
- 実際に口頭で発表練習を行いながら、同期的にレビューしてもらえるようにしたい
