## STEP2 技術調査

### 技術概要

Azure OpenAIのChat CompletionsをJSONモードで呼び出し、AIの発言に加えて「選択肢」「資料スタイル案」「ヒアリング完了フラグ」「スライド構成案」を含む構造化データとして返させる。資料スタイル案・スライド画像はgpt-image-2のtext-to-image / image-to-image APIで生成し、完了したものから順にSSEでフロントエンドへ返す。

### どのような課題を解決できるか

| 課題 | 解決内容 |
|---|---|
| 資料作成をAIに一任すると、意図と異なる資料ができあがる | AIが質問・選択肢提示を重ねながら段階的に方向性を確認する対話フローにする |
| 文章だけのやり取りだと、方針が合っているか判断しづらい | スタイル案・スライド案を画像として提示し、視覚的に確認・選択できるようにする |
| 画像生成APIの応答が遅く、待ち時間が長く感じる | 生成処理をSSEストリーミングで分割し、完成したものから順次表示する |

### 代表的なAPI・ツール・ライブラリ

| 名称 | 概要 | 特徴 |
|---|---|---|
| Azure OpenAI Chat Completions（JSONモード） | 構造化出力に対応したチャットAPI | `response_format={"type":"json_object"}`でスキーマに沿ったJSONを返させられる |
| gpt-image-2（generate） | text-to-imageの画像生成API | プロンプトのみから新規画像を生成できる（スタイル案の生成に使用） |
| gpt-image-2（edit） | image-to-imageの画像編集API | 元画像＋指示文で画像を編集できる（スタイル画像を元にしたスライド生成・修正に使用） |
| FastAPI StreamingResponse | SSE（Server-Sent Events）配信 | 完了した処理から順にフロントエンドへ逐次送信できる |
| KaTeX | 数式（LaTeX）レンダリングライブラリ | チャット内の数式表記をブラウザ上で描画できる |

### 調査して感じた疑問点・気になる点

- JSONモードでも、まれにJSONオブジェクトの後に余分な文字列が付与されることがあり、パース処理をどこまで堅牢にすべきか
- 画像生成AIへの指示文（プロンプト）の書き方次第で、スライドごとの見た目の一貫性がどこまで保てるか
- ヒアリングをどのタイミングで打ち切り「画像生成に進めてよい」と判断させるか、プロンプト側の設計基準

## STEP3 作成するもの決定

### 作成するプロトタイプ案

1. AIとのヒアリング対話でスライドイメージを段階的に作成するチャットアプリ
2. アップロード済みの構成案テキストから一括でスライド画像を生成するツール
3. スライドのテキスト構成案のみを提案するチャットボット

### 選んだプロトタイプ

1. AIとのヒアリング対話でスライドイメージを段階的に作成するチャットアプリ

### 作成計画

**目的（何を確かめたいか）**

Azure OpenAIの構造化出力と画像生成/編集APIを組み合わせて、対話をとおして要件を固めながら資料イメージを段階的に作り上げる体験が実現できるかを検証する。

**成功基準の定義**

- AIが一度に資料を完成させるのではなく、ヒアリングを重ねながら方向性を段階的に確定できる
- スタイル案・スライド案が画像として提示され、クリック操作だけで選択・意思決定できる
- スライドごとに個別の修正指示を出し、該当スライドのみ再生成できる
- 主要な処理（スタイル提示〜画像生成）の体感待ち時間が改善される設計になっている

## STEP4 開発環境決定

### 使用するライブラリやAPI、モデルの比較

| 項目 | 同期レスポンス方式 | SSEストリーミング方式 |
|---|---|---|
| 実装コスト | ◎ 低い | ○ やや高い（イベント設計が必要） |
| 体感速度 | △ 全処理完了まで無応答 | ◎ 完了した項目から順次表示 |
| 途中経過の可視化 | △ できない | ◎ 生成中/完了/失敗を個別に表示可能 |

| 項目 | gpt-image-2 generate（text-to-image） | gpt-image-2 edit（image-to-image） |
|---|---|---|
| 用途 | 参照画像なしでの新規生成 | 既存画像をベースにした編集 |
| 本アプリでの利用箇所 | 資料スタイル案の生成 | スタイル画像を元にしたスライド生成・修正依頼 |
| スタイルの一貫性 | △ 案ごとにばらつきが出やすい | ◎ 元画像の雰囲気を保ったまま編集できる |

### 選んだ環境

- **AIモデル**: Azure OpenAI（チャット: `gpt-5.4-mini` / 画像生成・編集: `gpt-image-2`）
  - 010_ai_reviewer で実績のある構成をそのまま踏襲し、チャットのJSONモードと画像編集APIを組み合わせて利用
- **構造化出力**: Chat Completions JSONモード
  - AIの発言に加えて「選択肢」「スタイル案」「ヒアリング完了フラグ」「スライド構成案」を1つのJSONスキーマで受け取れるようにし、フロントエンド側の分岐をシンプルにした
- **ストリーミング方式**: FastAPI `StreamingResponse` によるSSE
  - 010_ai_reviewer の修正方針提案機能と同じ設計を流用し、画像生成のたびに個別のHTTPリクエストを都度発行せずに済むようにした
- **Webフレームワーク**: FastAPI + 素のHTML/CSS/JavaScript
  - 010_ai_reviewer・011_chat_linkage と構成を統一し、デザインシステム（2カラムパネルレイアウト）も踏襲した
- **データ永続化**: なし（ブラウザ内state限定）
  - プロトタイプ段階のため、チャット履歴・生成画像はページを離れると破棄される設計にした

## STEP6 学習内容まとめ

### できたこと

**チャット・ヒアリング機能**

- AIの発言に加えて「選択肢」「資料スタイル案」「ヒアリング完了フラグ」「スライド構成案」をJSONスキーマとして返させる構造化ヒアリングフローを実装できた
- チャット内にAIから選択肢をボタンとして提示し、クリックだけで回答を送信できるUIを実装できた
- チャット内の簡易Markdown（見出し・箇条書き・強調・コード）とKaTeXによる数式表示に対応させた

**スタイル・スライド画像の生成**

- ヒアリングで固まった資料の目的をもとに、AIが資料全体の雰囲気スタイルを3案、画像イメージとして生成する機能を実装できた
- 選択したスタイル画像をベースに、スライド構成案（タイトル・記載内容）ごとに画像編集AIでスライドイメージを一括生成し、完成したものから順にカード表示できた

**修正・出力機能**

- スライドごとのカードに修正指示欄を設け、「修正依頼」ボタンで入力済みのスライドのみ一斉に再生成する機能を実装できた（未入力のスライドは元画像のまま維持）
- カード画像のクリックによる拡大表示（ライトボックス）を実装できた
- 生成済みの資料イメージをまとめてPDFとしてダウンロードする機能を実装できた（010_ai_reviewer のPDF出力処理を流用）

**応答速度の改善**

- 当初は「AIの発言取得」と「3案分の画像生成」を1つの同期リクエストにまとめていたため、AIの発言が表示されるまで数十秒待たされていた
- スタイル案の画像生成をSSEストリーミングの別エンドポイントに分割し、AIの発言（約4秒）をすぐ表示したうえで、各スタイル案の画像を完成したものから順にプレースホルダーへ反映する構成に改善した

### できなかったこと

| 項目 | 理由 |
|---|---|
| 生成したスライド画像のPPTX形式でのエクスポート | 今回は画像イメージの確認までをスコープとし、編集可能なPPTX出力は範囲外とした |
| チャット履歴・生成画像の保存 | プロトタイプ段階のため永続化を行っておらず、ページを離れると内容が失われる |
| スライド間の内容重複・一貫性チェック | スライドごとに個別で画像編集を行う設計のため、資料全体を通した一貫性の検証は行えていない |
| JSONパース失敗時の根本対応 | AIが稀にJSONの後に余分な文字列を付加する事象があり、先頭のJSONオブジェクトのみ救済する対症療法にとどまっている |

### 気づいたこと・学んだこと

- 構造化出力（JSONモード）を使うことで、「AIの発言」「選択肢」「次の処理に進めるかどうかの判断」をフロントエンドが機械的に分岐できるようになり、対話フローの実装がシンプルになった
- 画像生成AIを「新規生成（generate）」と「編集（edit）」で使い分けることで、スタイル案は自由度高く複数パターンを、スライドごとの画像は元のスタイルの雰囲気を保ったまま量産する、という異なる目的を両立できた
- 同期処理をSSEストリーミングに分割するだけで、実際の総処理時間はほぼ変わらなくても体感の待ち時間が大きく改善されることを実感した。「最初の反応を早く返す」設計の重要性を学んだ
- 010_ai_reviewer で実装済みのSSEストリーミング・ライトボックス・PDF出力の設計をそのまま流用できたため、実装期間を大きく短縮できた。既存資産の再利用性の高さを実感した

### 次回やってみたいこと・改善したいこと

- 完成した資料イメージからPPTXファイルを直接出力できるようにしたい
- チャット履歴・生成済みスライドをファイルまたはDBに保存し、途中から作業を再開できるようにしたい
- スライド間の内容重複や一貫性をAIにチェックさせる機能を追加したい
- JSONパースの安定性向上（Structured Outputs等、より厳密なスキーマ強制の仕組みの導入）を検討したい
