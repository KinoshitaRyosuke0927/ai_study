# 「今月、水何本頼む？」をAIに任せてみた話

## はじめに

うちの職場にはウォーターサーバーがあります。

毎月誰かが「今月何本頼む？」と決めているんですが、これが地味に難しい。少なすぎると月末に水がなくなるし、多すぎると翌月に持ち越してまた余る。しかも注文は20L単位で、締め切りは翌々月分を当月中に発注、という少しタイムラグのある仕組みです。

「これ、データがあれば予測できるんじゃないか？」と思ったのがきっかけです。

出社人数・営業日数・気温という3つのデータを組み合わせて、**Ridge回帰で翌月の推奨注文量を自動で出力するスクリプト** を作ってみました。

---

## 作ったもの

ひとことで言うと、**過去の実績データを読み込むと、翌月の推奨注文量（20L単位）をコンソールに出力するCLIスクリプト** です。

出力イメージはこんな感じです。

## 使ったデータ

予測に使ったのは以下の4種類のCSVです。社内のデータと外部APIを組み合わせています。

| データ | 内容 | 取得元 |
|---|---|---|
| `water_demand.csv` | 各月の水の注文量（L） | 手動で記録した実績値 |
| `jbd_calendar.csv` | 日ごとの営業日フラグ（1/0） | 社内カレンダー |
| `work_day.csv` | 社員ごとのAIC出社フラグ（1/0） | 社内カレンダー |
| `weather_data.csv` | 日ごとの平均・最低・最高気温 | Meteostat API |

気象データだけは外部APIを使っています。事務所の緯度経度を指定するだけで日次の気象データが取れるので便利でした。

## 実装のポイント

### 1. 複数CSVを組み合わせて月次特徴量を作る

「水の消費量が多い月」ってどんな月でしょうか。おそらく「人が多く来て、暑い日が続く月」ですよね。

そこで使う特徴量として以下の3つを選びました。

| 特徴量 | 計算方法 |
|---|---|
| `business_days`（月の営業日数） | JBDカレンダーの営業日フラグを月ごとに合計 |
| `attendance_rate`（1日あたり平均出社人数） | 月間延べ出社人数 ÷ 営業日数 |
| `tavg_mean`（月平均気温） | 日次気温の月平均 |

複数のCSVを `year_month`（年月）キーで結合して、月次の特徴量テーブルを作っています。

```python
# 月ごとの延べ出社人数を集計
work_day["daily_attendance"] = work_day[emp_cols].sum(axis=1)
# 営業日フラグを掛けて休日出社をゼロに
work_day["daily_attendance"] *= work_day["business_day_flag"].fillna(0)

# 1日あたり平均出社人数
df["attendance_rate"] = df["total_attendance"] / df["business_days"]
```

休日にAICに来ている人がいてもカウントしないよう、営業日フラグを掛けるのがポイントです。

### 2. LOO-CVでalphaを選ぶ

月次データなので、学習データが10件前後しかありません。こういうとき、通常の5分割CVだと「2件で検証」みたいなことになって評価が不安定になります。

そこで **LOO-CV（Leave-One-Out Cross Validation）** を使いました。1か月分だけ除いてモデルを学習 → 除いた月を予測、という操作を全月分繰り返します。データが少ない場面での汎化評価に向いています。

```python
for alpha in [0.01, 0.1, 1.0, 10.0, 50.0, 100.0]:
    ridge = Ridge(alpha=alpha)
    loo   = LeaveOneOut()
    scores = cross_val_score(ridge, X, y, cv=loo, scoring="neg_mean_absolute_error")
    mae = -scores.mean()
```

これで「このalphaだと平均何L外れるか」が候補ごとに出るので、一番MAEが小さいものを採用しています。

### 3. 翌月の気温が分からない問題

Ridge回帰で予測するには翌月の気温が必要ですが、当然まだ分かりません。

今回は **「前年同月の実績気温」で代替する** というアプローチを取っています。

```python
# 予測月の前年を計算
prev_year_period = pd.Period(next_month_dt - pd.DateOffset(years=1), "M")
# 前年同月の平均気温を取得
tavg_prev_year = monthly_weather.loc[
    monthly_weather["year_month"] == prev_year_period, "tavg_mean"
]
```

完全な解決策ではないですが、「去年の6月と今年の6月はだいたい似たような気温」という仮定のもとで動いています。天気予報APIが使えれば精度がもっと上がるはずで、改善の余地が一番大きい部分です。

### 4. 推奨注文量は20L単位に切り上げ

回帰モデルの出力は連続値（例：112.3L）なので、そのままでは注文できません。ウォーターサーバーの水は20L単位なので、最後に切り上げ処理をしています。

```python
prediction_rounded = np.ceil(prediction / 20) * 20
```

「足りなくなるより少し多めに頼む」という運用方針で切り上げにしています。

### 5. 気象データは外部APIで自動取得

過去の気象データは **Meteostat API**（RapidAPI 経由）を使って取得しています。事務所の緯度・経度を指定するだけで、指定期間の日次気象データ（平均・最低・最高気温）が返ってきます。

```python
AIC_LAT = 35.698568
AIC_LON = 139.779358

params = {
    "lat": AIC_LAT,
    "lon": AIC_LON,
    "start": "2024-10-01",
    "end":   "2026-05-31",
}
```

月500リクエストまで無料なので、今回の用途では十分です。取得結果はCSVに保存して、以降はローカルのファイルを読み込む構成にしました。

## やってみてわかったこと

**よかった点**

- LOO-CVはデータ件数が少ない月次データでも評価が安定していた。学習データMAEよりLOO-CV MAEが少し大きく出る（過学習の検知）という想定どおりの挙動が確認できた
- Ridge回帰は特徴量が3つしかないシンプルな構成でも、感覚的な注文量より安定した予測を出してくれた。係数を確認すると「気温が高いほど注文量が増える」という直感と一致していた
- Meteostat APIは緯度・経度で地点を指定できるため、気象観測所の場所を気にする必要がなく便利だった

**課題**

- 翌月の気温を前年同月で代替しているため、例年より暑い・寒い年では誤差が大きくなりやすい。天気予報APIとの連携が最優先の改善項目
- 前月の残水量（飲み残し）をデータとして持っていないため、繰越分が多い月は注文量が少なくなるはずなのにモデルが考慮できていない
- 翌月の出社状況（work_day.csv）が確定していないと予測できない。出社予定が未入力の場合のフォールバック処理が未実装
