## STEP2 技術調査

### 技術概要

月次の水の注文量実績・JBD営業日カレンダー・社員別出社カレンダー・気象データを組み合わせて月ごとの特徴量を作成し、Ridge回帰で翌月の注文量を予測する。

外部APIとして Meteostat API（RapidAPI 経由）を使って事務所（AIC）の日次気象データを自動取得する。
LOO-CV（Leave-One-Out Cross Validation）でデータ件数が少ない状況でも汎化性能を適切に評価する。

### どのような課題を解決できるか

| 課題 | 解決内容 |
|---|---|
| 注文量が感覚頼りになっている | 過去データと回帰モデルで定量的な推奨注文量を算出する |
| 注文が多すぎて在庫が余る・少なすぎて不足する | 20L単位の切り上げ推奨量を提示することで過不足を最小化する |
| 翌月の気温データが事前に入手できない | 前年同月の実績気温を代替値として使用する |
| 気象データの取得が手動で手間がかかる | Meteostat API で期間指定による自動取得を実装する |

### 代表的なAPI・ツール・ライブラリ

| 名称 | 概要 | 特徴 |
|---|---|---|
| scikit-learn（Ridge） | Pythonの機械学習ライブラリ | 正則化付き線形回帰・LOO-CV実装が容易 |
| scikit-learn（LeaveOneOut） | LOO-CV実装 | データ件数が少ない場合の汎化評価に有効 |
| Meteostat API | 地点指定で気象データを取得できるAPI | 緯度経度で日次気象データを取得可能・月500回まで無料 |
| pandas | データ処理ライブラリ | 複数CSVの結合・期間集計・型変換が容易 |
| numpy | 数値計算ライブラリ | 切り上げ計算（np.ceil）等に使用 |

### 調査して感じた疑問点・気になる点

- LOO-CVはデータ件数が少ない（10件程度）場合に特に有効とされているが、月次データで十分機能するか
- Ridge回帰の正則化パラメータ alpha の候補範囲をどの程度広げるべきか
- 前年同月の気温を代替値として使う場合、年ごとの気候変動で誤差がどの程度発生するか
- 翌月の出社状況が未確定な場合、どのデータを予測の入力として使用すべきか
- 湿度が水の消費量に与える影響は実際に大きいか（現在のAPIでは取得不可）

## STEP4 開発環境決定

### 使用するライブラリやAPI、モデルの比較

| 項目 | Ridge回帰 | Lasso回帰 | Random Forest |
|---|---|---|---|
| データ件数が少ない場合 | ◎ 安定 | ○ 係数がゼロになりすぎる場合あり | △ 過学習しやすい |
| 説明性 | ◎ 係数から解釈可能 | ◎ スパース性あり | △ ブラックボックス |
| ハイパーパラメータ | ◎ alphaのみ | ◎ alphaのみ | △ 複数（木の深さ等） |
| 実装コスト | ◎ 低い | ◎ 低い | ○ やや高い |

| 項目 | Meteostat API | 気象庁API | Open-Meteo |
|---|---|---|---|
| 緯度経度指定 | ◎ 可能 | △ 地点コード指定 | ◎ 可能 |
| 無料枠 | ○ 500回/月 | ◎ 無制限 | ◎ 無制限 |
| 日本語ドキュメント | △ 英語のみ | ◎ 日本語 | △ 英語のみ |
| 取得できる項目 | ○ 気温・降水量等（湿度なし） | ○ 気温・湿度等 | ◎ 気温・湿度等 |

### 選んだ環境

- **回帰モデル**: Ridge回帰（scikit-learn）
  - データ件数が少ない月次データでも安定して機能し、係数から特徴量の影響を解釈しやすい
- **ハイパーパラメータ選定**: LOO-CV（LeaveOneOut + cross_val_score）
  - データが少ない場合に汎化性能を最大限活用できる交差検証手法
- **気象データ取得**: Meteostat API（RapidAPI 経由）
  - 緯度経度で事務所（AIC）の日次気象データを取得可能・無料枠で十分
- **データ処理**: pandas + numpy
  - 複数CSV結合・月次集計・欠損補完の実装コストが低い
- **実行環境**: Python CLIスクリプト（UIなし）
  - PoCとして環境構築コストを最小化

## STEP6 学習内容まとめ

### できたこと

- Meteostat API（RapidAPI 経由）を使って、AIC所在地（緯度・経度指定）の日次気象データを自動取得し、CSVに保存できた
- 月次の特徴量（営業日数・月間延べ出社人数・平均出社人数/日・月平均気温）を複数CSVから結合・集計して作成できた
- JBDカレンダーの営業日フラグを使って、休日の出社をカウント対象から除外する前処理を実装できた
- Ridge回帰 + LOO-CVで正則化パラメータ（alpha）を候補6種類から自動選定できた
- LOO-CVの月別誤差（実績値・絶対誤差）と学習データMAE・LOO-CV MAEを出力できた
- 翌月の営業日・出社予定・気温（前年同月代替）が揃っていれば翌月の推奨注文量を自動算出できた
- 推奨注文量を20L単位に切り上げて出力し、実業務の注文単位に合わせた結果を得られた

### できなかったこと

| 項目 | 理由 |
|---|---|
| 翌月の実気温を使用した予測 | 天気予報APIとの連携には至らず、現状は前年同月の実績値で代替している |
| 翌月の出社状況が未確定な場合の対応 | 翌月のwork_day.csvが存在しない場合は予測不可のメッセージを出力するのみで、過去平均などのフォールバック処理は未実装 |
| 前月繰越の残水量を考慮した予測 | 残水量（rest_quantity）のデータが未収集のため、モデルの特徴量に含められていない |
| 湿度を特徴量に追加すること | Meteostat APIでは湿度データが取得できないため断念した |
| モデルの可視化・グラフ出力 | CLIスクリプトとして最小構成で実装したため、特徴量の重要度や誤差分布のグラフ化は未対応 |

### 気づいたこと・学んだこと

- LOO-CVはデータ件数が少ない（月次10件程度）場合に特に有効で、k-分割CVよりも評価が安定した
- Ridge回帰の alpha は小さすぎても大きすぎてもMAEが悪化するため、LOO-CVでの選定が重要だと分かった
- 「前年同月気温」の代替は、気候変動の影響を受けるため年によって誤差が出やすい。最終的には天気予報APIから翌月予測気温を取得することが最も改善効果が高い
- 月次データの統合では、JBDカレンダーと出社カレンダーで「日付が存在しない場合は休日とみなす」という扱いが重要で、欠損補完の方針を明確にしないと出社人数が過剰にカウントされることに気づいた
- 特徴量が3つ（営業日数・平均出社人数・平均気温）と少ないため、モデルの挙動が直感的に解釈しやすかった。係数を確認することで「気温が高いほど消費が増える」という常識的な関係が数値で確認できた

### 次回やってみたいこと・改善したいこと

- 天気予報APIと連携して翌月の予測気温を入力することで、代替値の精度限界を解消したい
- 前月の残水量をデータとして記録し、特徴量に加えることで予測精度のさらなる向上を図りたい
- 湿度データが取得できる気象APIへの移行（Open-Meteo など）を検討し、湿度を特徴量に追加したい
- データ件数が増えた場合に、LOO-CVからk-分割CVへの切り替えを自動判定する仕組みを加えたい
- 予測結果をCSVに出力・蓄積し、実績との乖離を月次で追跡できるようにしたい
