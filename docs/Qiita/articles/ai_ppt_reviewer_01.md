# 「資料レビューで消耗したくない」を解決したくてAIにPowerPoint資料をレビューさせるアプリを作った話

## はじめに

前回、AIに複数の役割を演じさせて発表練習ができるアプリを作った話を書きました。

https://qiita.com/（前回記事のURLに差し替え）

今回はその続編です。発表練習の前段階、つまり **「資料そのものが企画会議で通用する完成度になっているか」** を、発表する前にAIにチェックしてもらうアプリを作りました。

きっかけは単純で、**資料レビューって地味にしんどい**んですよね。特に経営層向けの企画資料は、話の筋が通っているか・判断材料が揃っているか・用語がブレていないかなど、見る観点が多岐にわたります。レビューする側もされる側も時間を取られますし、何より「レビュー前に自分で気づけたはずの指摘」で時間を使ってしまうのがもったいない。

そこで今回は **FastAPI + LibreOffice + Azure OpenAI** を組み合わせて、PowerPoint資料を観点別にAIレビューし、さらに具体的な修正方針まで提案してくれるWebアプリを作りました。

---

## 作ったもの

ひとことで言うと、**「PowerPointをアップロード → 観点別にAIがレビュー → 指摘を踏まえた修正方針まで提案」** してくれるWebアプリです。

**主な機能**

- `.pptx` をアップロードするとLibreOffice経由でスライドを画像化し、ブラウザ上で一覧・拡大表示
- スライドごと／資料全体で「伝えたいこと」を入力できる
- 「構成・表現」「計画・戦略」「課題設定」「優先度・差別化」「実現可能性」「評価・検証」など、観点別にAIがレビューし、タブ切り替えで確認できる
- レビュー結果をもとに、スライドごとの具体的な修正方針（要約・課題・アクション・差し替え文案・期待される状態）を提案
- 指摘事項・修正方針をそれぞれMarkdownでダウンロード

## 技術スタック

```
フロントエンド  : HTML + JavaScript（最小構成）
バックエンド    : Python / FastAPI
スライド画像化  : LibreOffice（headless）+ poppler（pdf2image）
テキスト・画像解析 : Azure OpenAI（GPT-4o、マルチモーダル）
レビュー観点管理 : CSVファイル（review_point.csv）
データ保存      : なし（都度アップロード・都度レビューのステートレス構成）
```

前回の発表練習アプリと同じく、PoC段階ではDBを持たずステートレスに倒しています。

## アーキテクチャ

```
[ブラウザ]
  ↓ .pptxアップロード
[FastAPI /api/upload]
  ↓ LibreOfficeでPDF化 → popplerでスライド画像化（PNG/JPEG）
[ブラウザ]
  ← スライド一覧・拡大表示
  ↓ 「伝えたいこと」入力 → レビュー実行
[FastAPI /api/review]
  ↓ perspective_type（観点）ごとに並列でAzure OpenAIへ問い合わせ
  ↓ Step1: 観点ごとのQ&Aレビュー
  ↓ Step2: Q&A結果を自然文に集約
[ブラウザ]
  ← 観点別タブで指摘事項を表示
  ↓ 「修正方針を提示する」実行
[FastAPI /api/suggest]
  ↓ 指摘事項＋スライド画像をもとに、スライドごとに並列で修正方針(JSON)を生成
[ブラウザ]
  ← スライドごとの修正方針を表示
```

## 実装のポイント

### 1. レビュー観点をCSVで外出しする

このアプリの一番の狙いは、**「なんとなく良さそうなAIレビュー」ではなく、実際のレビュー経験から抽出した観点でレビューさせる**ことです。そこで、レビュー観点は `review_point.csv` に `role` / `perspective_type` / `detail` の3列で管理しています。

```csv
role,perspective_type,detail
emp_01,assignment,この製品がBtoBなのかBtoCなのかが明確になっているか。
emp_01,plan,開発プロセスとして記載しているスケジュールや作業工数の見積もりは現実的か。
common,overall,課題・解決策・効果の流れが伝わりやすい構成順になっているか。
...
```

`perspective_type` は「全体」「構成・表現」「計画・戦略」「課題設定」「優先度・差別化」「実現可能性」「評価・検証」の7種類に分類していて、コードを変更せずにCSVを編集するだけで観点の追加・細分化ができます。

```python
PTYPE_LABELS: dict[str, str] = {
    "overall":     "全体",
    "story":       "構成・表現",
    "plan":        "計画・戦略",
    "assignment":  "課題設定",
    "priority":    "優先度・差別化",
    "feasibility": "実現可能性",
    "evaluation":  "評価・検証",
}
```

### 2. スライド単位ではなく「資料全体」を観点別にレビューする

実は最初はスライドごとに個別レビューする作りにしていたのですが、途中で **「スライド単位のレビューをやめて、観点別に資料全体をレビューする」方式に一本化** しました。

理由は、企画資料でチェックしたいのは「用語が資料全体で統一されているか」「課題・解決策・効果の流れが一貫しているか」といった、**スライドをまたいだ一貫性**だったからです。スライド単位でレビューすると、この手の指摘がどうしても出しにくくなります。

そこで、`perspective_type` ごとに全スライド画像をまとめてAzure OpenAIに渡し、観点に沿ってQ&A形式でレビューさせてから、その結果を自然な日本語文章に集約する **2段階のプロンプト構成** にしています。

```python
def _review_perspective(ptype: str, pkg: dict) -> dict:
    # Step1: 観点ごとのQ&Aレビュー
    qa_result = call_review(pkg)
    reviews = qa_result.get("reviews", [])

    # Step2: Q&A結果を集約文章に変換
    label = PTYPE_LABELS.get(ptype, ptype)
    summary_result = call_review(build_overall_per_type_summarize_prompt_package(label, reviews))

    return {"type": ptype, "label": label, "summary": summary_result.get("summary", "")}
```

Q&A形式にしているのは、観点（レビュー項目）ごとに「該当なし」を判断させやすくするためです。プロンプトには次のルールを明示しています。

```
- インプットの情報からは判断がつかない場合には、「判断ができません」とだけ返してください。
- レビューした結果、問題がない場合は「指摘事項はありません」とだけ返してください。無理に指摘事項を挙げることはせず、他の文章を追加することも禁止です。
- 問題がある場合のみ、具体的な指摘内容を返してください。
```

これを入れないと、AIは律儀にどの観点にも何かしら指摘を作ろうとしてしまいます。「該当なし」を明示的に許可する一文が、無理な指摘を減らすのに地味に効きました。

### 3. レビュー処理を観点ごとに並列化する

観点が7種類もあると、素直に直列でAzure OpenAIを呼んでいては応答時間がどんどん伸びてしまいます。そこで、観点ごとの処理を **`asyncio.gather` + `asyncio.to_thread`** で並列実行するようにしました。

```python
@app.post("/api/review")
async def review_pptx(request: ReviewRequest) -> dict:
    packages = build_overall_per_type_prompt_packages_by_type(data)
    perspectives = await asyncio.gather(
        *(asyncio.to_thread(_review_perspective, ptype, pkg) for ptype, pkg in packages)
    )
    return {"presentation_summary": {"perspectives": list(perspectives)}, "slides": []}
```

`azure_ai_service.py` のAzure OpenAI呼び出しは同期関数なので、そのままでは並列化できません。そこで `asyncio.to_thread` でスレッドに逃がしてから `asyncio.gather` でまとめて待つ、という形にしています。これだけで、観点数に比例して伸びていた応答時間を大幅に短縮できました。

後述する修正方針提案（`/api/suggest`）も同じパターンで、スライドごとの処理を並列化しています。

```python
slide_suggestions = await asyncio.gather(
    *(asyncio.to_thread(_suggest_revision_for_slide, slide, findings_text) for slide in data["slides"])
)
```

図にすると、直列実行と並列実行の違いはこんなイメージです。

![観点別レビューの処理時間比較（直列 vs 並列）](/docs/Qiita/image/ai_ppt_reviewer_01/image_004.svg)
*Before: 7つの観点を1つずつ順番にAIへ問い合わせるため、応答時間は観点数に比例して伸びる／After: `asyncio.gather` + `asyncio.to_thread` で全観点を同時に問い合わせるため、応答時間は「一番遅い観点1つ分」で済む*

ポイントは、**AI呼び出しはCPUを回している時間よりも「Azure OpenAIからのレスポンス待ち」の時間の方が圧倒的に長い、I/Oバウンドな処理だ**という点です。Pythonには有名なGIL（Global Interpreter Lock）があり、複数スレッドが同時にPythonのコードを実行することはできませんが、ネットワークI/Oの応答待ちの間はGILが解放されるため、`openai` ライブラリの同期呼び出しをスレッドに逃がすだけで、実質的に複数のAzure OpenAIリクエストを同時に「待つ」ことができます。`asyncio.to_thread` はこの「同期関数をスレッドプールに投げて`await`可能にする」ためのラッパーで、`asyncio.gather` は投げた複数のコルーチン（＝スレッド上のタスク）が全部終わるのを待ち合わせる役割を担っています。

つまりコードの構造としては、

1. `perspective_type` ごとにプロンプトを組み立てる（`build_overall_per_type_prompt_packages_by_type`）
2. それぞれを `asyncio.to_thread(_review_perspective, ptype, pkg)` でスレッドに投げる
3. `asyncio.gather(*...)` で全スレッドの完了を待ち、結果をリストとして受け取る

という3ステップだけです。観点数が7から10に増えても、コード自体は1行も変える必要がなく、応答時間も「直列なら10倍」ではなく「並列なら（多少のオーバーヘッドはあるものの）ほぼ変わらない」まま保てます。修正方針提案（`/api/suggest`）側もスライド枚数分だけ同じ構造で並列化しているので、スライドが増えてもこのアプリの体感速度はあまり劣化しません。

### 4. 「指摘」で終わらせず「修正方針」まで出す

これが今回一番作り込んだ機能です。前回のレビュー系アプリでは「指摘して終わり」でしたが、指摘だけをもらっても実際にどう直せばいいか悩む場面が多かったので、**観点別レビュー結果をもとに、スライドごとの具体的な修正方針を提案する `/api/suggest` エンドポイント** を追加しました。

出力スキーマはこんな感じです。

```json
{
  "summary": "このスライドをどう修正すべきかを1〜2文で要約した文章",
  "issues": ["現状の問題点1", "現状の問題点2"],
  "actions": [
    {"type": "structure",  "instruction": "構成変更に関する具体的な修正指示"},
    {"type": "content",    "instruction": "内容追加・削除・整理に関する具体的な修正指示"},
    {"type": "expression", "instruction": "見出しや文言表現に関する具体的な修正指示"}
  ],
  "example_text": {
    "title": "修正後のスライドタイトル案",
    "lead": "修正後のスライド冒頭説明文案",
    "body": ["本文や箇条書きの差し替え文案1", "本文や箇条書きの差し替え文案2"]
  },
  "expected_outcome": "修正後にどのようなスライドになっているべきか"
}
```

ここで工夫したのは、プロンプトに **「悪い例」「良い例」を明記した**ことです。

```
9. 曖昧な表現を避けてください
   - 悪い例: わかりやすくする
   - 良い例: PoC対象と将来対応を表で分離し、優先順位が一目で分かる構成にする
```

これを入れる前は「わかりやすくしましょう」「情報を整理しましょう」といった、それっぽいけど結局何をすればいいか分からない助言が返ってきがちでした。悪い例をピンポイントで示すことで、抽象的な言い回しを避けて、実際に手を動かせるレベルの指示が返ってくるようになりました。

`example_text` に「スライドへそのまま貼れる文案」まで含めているのもポイントで、修正方針を読んだ後にすぐコピペで試せる状態を目指しています。

### 5. LibreOfficeでスライドを画像化する

`.pptx` をそのまま解析する方法（python-pptxでの構造解析など）も検討しましたが、AIにレイアウトやグラフ・図解も含めて見てもらいたかったので、**LibreOfficeでPDF化 → popplerで画像化** というパイプラインを採用しました。マルチモーダル対応のAzure OpenAIに画像をそのまま渡せるので、テキスト構造だけでは拾えない「見た目」の問題（情報の詰め込みすぎ、レイアウト崩れなど）も指摘対象にできます。

一覧表示用に軽量なJPEGサムネイル、拡大表示・AI入力用に高品質なPNGと、用途に応じて2種類の画像を生成しているのも地味なポイントです。

## やってみてわかったこと

**よかった点**

- レビュー観点をCSVで外出ししたことで、観点の追加・細分化がコード変更なしで行えた。実際にレビューをしながら「この観点が足りない」と気づいたら、CSVに1行足すだけで済む
- スライド単位のレビューをやめて資料全体を観点別に評価する方式に切り替えたことで、「用語の統一」「話の流れの一貫性」といった、スライドをまたいだ指摘が自然に出るようになった
- 観点ごと・スライドごとの処理を `asyncio.gather` + `asyncio.to_thread` で並列化するだけで、観点数・スライド数が増えても応答時間を実用的な範囲（1〜3分程度）に抑えられた
- 「悪い例／良い例」をプロンプトに書いておくことで、修正方針の抽象度をかなりコントロールできた

**課題**

- 常にすべての観点でレビューしてしまうため、本来対象外の観点についても無理に指摘が生成されてノイズになることがある。レビュー対象観点を絞り込む仕組みがまだない
- 観点ごとに独立してレビューしているため、異なる観点なのにほとんど同じ内容の指摘が重複して出てくることがある
- 観点別の指摘事項が長文になりやすく、読む側の負担がまだ大きい
