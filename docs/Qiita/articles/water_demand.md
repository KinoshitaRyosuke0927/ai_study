# 「今月、水何L頼む？」をAIに任せてみた話 〜CLIからWebアプリに進化させるまで〜

## はじめに

AICにはウォーターサーバーがあります。

毎月誰かが「今月何L頼む？」と決めているんですが、これが地味に面倒です。社員数や出社状況が変わるたびに消費量も変わるので、毎月手元のデータを確認しながら発注量を判断しなければなりません。しかも注文は20L単位でしか受け付けていないうえ、締め切りは翌々月分を当月中に発注という少しタイムラグのある仕組みです。少なすぎると月末に水がなくなるし、多すぎると翌月に持ち越してまた余る。

「毎月、社員数とともに消費量が変化するたびにいちいち確認して決めるのが面倒——これ、データがあれば予測できるんじゃないか？」と思ったのがきっかけで、まずはコンソール出力のCLIスクリプトを作りました。そこからさらに一歩進めて、**誰でもブラウザから使えるWebアプリ**にしたので、その記録を残しておきます。

---

## 作ったもの

出社人数・営業日数・気温という3つのデータを組み合わせて、**Ridge回帰で翌月の推奨注文量（20L単位）を予測するWebアプリ**です。

FastAPI + uvicornでサーバーを立て、Jinja2テンプレートで画面を作っています。予測に使うデータはすべてWebアプリからCSVに登録・管理できます。

## 使ったデータ

予測に使っているのは以下の4種類のCSVです。社内データと外部APIを組み合わせています。

| データ | 内容 | 取得元 |
|---|---|---|
| `water_demand.csv` | 各月の水の注文量（L） | Webアプリから手動で登録 |
| `jbd_calendar.csv` | 日ごとの営業日フラグ（1/0） | 社内カレンダー |
| `work_day.csv` | 社員ごとのAIC出社フラグ（1/0） | Webアプリから手動で登録 |
| `weather_data.csv` | 日ごとの平均・最低・最高気温 | Meteostat API |

気象データだけは外部APIを使っています。事務所の緯度経度を指定するだけで日次の気象データが取れるので便利でした。

## データの前処理：複数CSVを結合して月次特徴量を作る

モデルに渡す特徴量を作るまでが、実はこの実装の一番の肝です。

「水の消費量が多い月」ってどんな月でしょうか。おそらく「人が多く来て、暑い日が続く月」ですよね。そこで以下の3つを特徴量として選びました。

| 特徴量 | 計算方法 |
|---|---|
| `business_days`（月の営業日数） | JBDカレンダーの営業日フラグを月ごとに合計 |
| `attendance_rate`（1日あたり平均出社人数） | 月間延べ出社人数 ÷ 営業日数 |
| `tavg_mean`（月平均気温） | 日次気温の月平均 |

4つのCSVは日付の粒度がバラバラ（日次・月次混在）なので、まずすべてに `year_month`（年月Period）列を追加して、それをキーに結合します。

![データ結合の概念図](/docs/Qiita/image/water_demand/image_002.png)
*▲ 4つのCSVを年月キーで結合して月次特徴量テーブルを作るイメージ*

```python
# 各CSVに year_month 列を追加
water_demand["year_month"] = pd.to_datetime(water_demand["date_ym"]).dt.to_period("M")
jbd_calendar["year_month"] = pd.to_datetime(jbd_calendar["date"]).dt.to_period("M")
work_day_df["year_month"]  = pd.to_datetime(work_day_df["date"]).dt.to_period("M")
weather_data["year_month"] = pd.to_datetime(weather_data["date"]).dt.to_period("M")
```

出社人数を集計するときに、2種類のフラグを掛け合わせる処理が入っています。

- **JBDカレンダーの営業日フラグ**：会社自体が営業しているかどうかを示します
- **社員ごとの出社フラグ（work_day.csv）**：その日に社員がAICで業務をするかどうかのスケジュールです

この2つを掛け合わせているのは、**実際にAICにいてウォーターサーバーを使う可能性がある社員だけを抽出するため**です。会社の営業日であっても在宅勤務をしている社員や出張中でAICにいない社員は水を消費しません。逆に、社員のスケジュール上はAIC出社でも会社が休日（祝日など）なら実際には来ていません。両方の条件を満たす「会社が営業していて、かつAICにいる」社員だけをカウントすることで、水の消費量に直結する数字が得られます。

```python
# 日ごとの出社人数を集計（社員ごとのAIC出社フラグの合計）
work_day_df["daily_attendance"] = work_day_df[emp_cols].sum(axis=1)
# JBD営業日フラグを掛けて、会社が休みの日はゼロに
# → 「会社が営業 かつ AICにいる」社員数のみを残す
work_day_df["daily_attendance"] *= work_day_df["business_day_flag"].fillna(0)

# 月ごとに集計して1日あたりの平均に変換
df["attendance_rate"] = df["total_attendance"] / df["business_days"]
```

この前処理が正しくないと、モデルに渡す数字がおかしくなって予測精度が下がります。「モデルより前処理」という格言（？）を実感した部分です。

## モデルの学習：Ridge回帰 + LOO-CVでalphaを選ぶ

### なぜRidge回帰を選んだか

線形回帰に正則化（L2ペナルティ）を加えたRidge回帰を使いました。今回の特徴量は3つだけで、「人が多く来て気温が高い月ほど水を使う」という直感的に線形な関係が想定できます。**予測対象がシンプルなので、モデルもシンプルなものが合っている**と判断しました。

正則化を入れているのは、学習データが少ないときに係数が大きく振れすぎるのを防ぐためです。

### LOO-CVでalphaを最適化する

月次データなので学習サンプルが10件前後しかありません。通常の5分割CVだと「2件で検証」みたいなことになって評価が不安定になります。そこで **LOO-CV（Leave-One-Out Cross Validation）** を採用しました。

1か月分だけ除いてモデルを学習 → 除いた月を予測 → 全月分繰り返す、という手順です。評価指標には **MAE（Mean Absolute Error：平均絶対誤差）** を使っています。予測値と実績値の差の絶対値を全サンプルで平均したもので、「平均して何L外れるか」を直感的に表せます。「この正則化強度alphaだと平均何L外れるか」を候補ごとに比較して、最もMAEが小さいalphaを採用します。

```python
best_alpha, best_mae = None, float("inf")
for alpha in [0.01, 0.1, 1.0, 10.0, 50.0, 100.0]:
    scores = cross_val_score(
        Ridge(alpha=alpha), X, y, cv=LeaveOneOut(),
        scoring="neg_mean_absolute_error"
    )
    mae = -scores.mean()
    if mae < best_mae:
        best_mae, best_alpha = mae, alpha

# 最適alphaで改めて全データを使って学習
model = Ridge(alpha=best_alpha)
model.fit(X, y)
```

### 翌月の気温が分からない問題

Ridge回帰で予測するには翌月の気温が必要ですが、当然まだ分かりません。今回は **「前年同月の実績気温」で代替する** アプローチを取りました。

```python
# 予測月の1年前を計算
prev_year_period = pd.Period(next_month_dt - pd.DateOffset(years=1), "M")
# 前年同月の月平均気温を取得
tavg_row = monthly_weather.loc[
    monthly_weather["year_month"] == prev_year_period, "tavg_mean"
]
```

「去年の6月と今年の6月はだいたい似たような気温」という仮定のもとで動いています。完全な解決策ではなく、改善余地が最も大きい部分です。

### 推奨注文量は20L単位に切り上げ

回帰モデルの出力は連続値（例：112.3L）なので、そのままでは注文できません。ウォーターサーバーの水は20L単位なので、最後に切り上げ処理をしています。「足りなくなるより少し多めに頼む」という運用方針です。

```python
prediction_rounded = int(np.ceil(prediction / 20) * 20)
```

## WebアプリへのつなぎこみはFastAPIで

CLIスクリプトをWebアプリに移植する際、予測のコア処理を `_run_prediction()` という関数にまとめて、FastAPIのルートから呼び出す構成にしました。

```python
@app.post("/predict/run")
def predict_run():
    return JSONResponse(_run_prediction())
```

LOO-CVは計算に時間がかかるため、`async def` ではなく通常の `def` にしています。FastAPIは同期関数を自動的にスレッドプールで実行してくれるので、イベントループをブロックせずに済みます。

また、予測した推奨注文量を「実績として登録」ボタンでそのままCSVに書き戻せるようにしました。「予測 → 確認 → 登録」までブラウザ上で完結するので、翌月また予測するときの学習データが自然に増えていく仕組みになっています。

## やってみてわかったこと

### よかった点

**入力がシンプルだったからこそ、モデルもシンプルで済んだ**

水の消費量に影響する要因を整理したとき、「人が来る」「暑い」という2つの軸にほぼ集約できました。その結果、特徴量は3つだけ、モデルはRidge回帰という構成でも実用的な精度が出ました。

予測対象の構造がシンプルなら、複雑なモデルを使う必要はない——というのは頭では知っていましたが、今回のように「なぜシンプルで成立するのか」を整理した上で選ぶと、納得感が全然違いました。Ridge回帰の係数を確認すると「気温が高いほど注文量が増える」「出社人数が多いほど注文量が増える」という直感と一致していたのも安心感につながりました。

**LOO-CVはデータが少ない場面にはまった**

10件前後のサンプルでは、通常のk-fold CVは折ごとの検証データが数件になって評価が安定しません。LOO-CVは1件ずつ抜いて評価するので、サンプルサイズに依存せず安定した汎化誤差の推定ができました。学習データMAEよりLOO-CV MAEが少し大きく出る（過学習の検知）という想定どおりの挙動も確認できました。

### 課題

**学習データが少ないと、特徴量を増やすとかえって予測が悪くなる**

「湿度も追加したら精度上がるんじゃないか」「曜日の分布も入れたら？」と特徴量を増やしたくなるのですが、学習サンプルが10件前後しかない状態でそれをやると過学習が悪化します。

LOO-CVのMAEを見ながら試してみると、特徴量を追加するとむしろMAEが上がる（＝汎化性能が下がる）ケースが多く、今回の構成ではシンプルな3特徴量が最も安定していました。「データが少ないときは、特徴量を増やすよりデータを増やすことを先に考えるべき」という結論になりました。

**翌月の気温の代替精度が予測誤差の上限を決めている**

現状、前年同月の気温を代替に使っているため、例年より暑い・寒い年では誤差がそのまま大きくなります。他の特徴量の前処理や学習方法をどれだけ磨いても、この代替誤差が乗り続ける構造になっています。天気予報APIとの連携が最優先の改善項目です。
